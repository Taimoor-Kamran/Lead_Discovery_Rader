# v0.7.0 — CRM export (CSV + Airtable, swappable)

**Branch:** spec/v0.7.0-crm-export
**Depends on:** v0.6.0 (merged, tag `v0.6.0`)
**Estimate:** 2–3 working days
**Blueprint refs:** §2 Lead state 6 "CRM lead" (slide 9), User journey step 13 (slide 8), §7 CRM workflow (slide 38), Where approved leads land (slide 39), CRM lead required fields (slide 40), §8 Failure handling — CRM sync failure (slide 44)

## Goal
Approved leads leave the system — and **only** approved leads. A CRM adapter interface with three
implementations: **CSV export** (works today, no accounts), **Airtable** (ready the moment the client provides a
token), and a **fake** adapter for tests/demo. Sync is automatic after the undo window, retried on failure,
logged per attempt, deduplicated, and never overwrites what salespeople edit in the CRM. Do-not-contact
decisions propagate to records already in the CRM. HubSpot/GoHighLevel later = one new adapter module.

## Scope
- `CrmAdapter` protocol + registry; `CsvExportAdapter`, `AirtableAdapter`, `FakeCrmAdapter`
- One CRM record **per business** (not per opportunity), listing its approved services — so two reps never call the same business
- `crm_leads` + `crm_sync_attempts` tables; sync worker with retry/backoff and a "held" state
- Auto-sync after the review undo window; manual Send now / Retry / Sync all
- Field ownership: Radar-owned fields update, CRM-owned fields are set only on create
- Suppression propagation to already-synced records
- CSV export endpoint with formula-injection protection
- Airtable setup guide + `make crm-check` (and optional table bootstrap)
- UI: CRM status on My leads and lead detail; `/crm` page for crm_manager/admin
- Two small carry-overs from v0.6.0 review (see end of Design)

## Out of scope
- HubSpot, GoHighLevel, Pipedrive adapters (interface only; implement when the client chooses)
- Two-way sync (reading CRM changes back into Radar), webhooks from the CRM
- Sending emails/SMS or any outreach from Radar or via the CRM
- Owner/personal contact fields — business-level public phone and website only
- Deployment (v0.8.0)

## Human prerequisites
- **None to build or test** — CSV and fake adapters need no accounts; Airtable is tested with recorded responses
- For a live Airtable test (optional before merge, required before using it for real): the client creates an Airtable base (or gives you one), follows `docs/crm/airtable-setup.md` to create the **Leads** table, and creates a **personal access token** scoped to that base with `data.records:read`, `data.records:write` (and `schema.bases:read` for `make crm-check`; `schema.bases:write` only if you want `make crm-bootstrap-airtable`). Put `AIRTABLE_TOKEN`, `AIRTABLE_BASE_ID`, `AIRTABLE_TABLE` in `.env`
- Verify Airtable's current API limits (requests/second per base, records per request) and the upsert option against Airtable's docs; note what you confirmed under Implementation notes

Register models; register an `airtable` row in `sources` (`kind=api`, role `crm_destination`) so Airtable calls go through `core/http.py` (metered in `api_calls`, rate-limited, key never logged).

### Adapter contract
```python
class CrmAdapter(Protocol):
    name: str                                   # "csv" | "airtable" | "fake"
    def check(self) -> CrmHealth: ...           # config present, credentials valid, fields exist
    def upsert(self, record: CrmRecord, existing_external_id: str | None) -> CrmResult: ...
    def find_by_keys(self, radar_business_id: str, domain: str | None, phone: str | None) -> str | None: ...
    def mark_do_not_contact(self, external_id: str, note: str) -> CrmResult: ...
```
`CrmResult`: `external_id`, `action` (`created` | `updated` | `unchanged`), `external_url` (link to the record if the CRM has one). Errors: `CrmTransientError` (retry), `CrmAuthError`, `CrmConfigError` (field missing / bad table), `CrmRejectedError` (400 with message) — the last three are not retried and put the lead on **held**.
Active destination: `CRM_DESTINATION=csv|airtable|fake` (default `csv`; `fake` allowed only in local/development/ci).

### The CRM record (blueprint slide 40), one per business
| Field | Owner | Value |
|---|---|---|
| Radar Business ID | radar | business id (the upsert key) |
| Business name / Legal name | radar | survivorship values |
| Industry | radar | plain label |
| City, State, Postal code, Address | radar | |
| Website | radar | |
| Public phone | radar | formatted `(512) 555-0102` |
| Services | radar | approved services, plain labels, e.g. "Website redesign; Online booking" |
| Lead score | radar | highest approved score, 0–100 |
| Why this is a lead | radar | rule reasons of approved opportunities (plain text, ≤ 1 000 chars) |
| Top findings | radar | plain-language finding labels from the latest audit |
| Source / Source URL | radar | e.g. "Google Places" + the Maps link |
| Radar link | radar | `{APP_BASE_URL}/leads/{opportunity_id}` of the top opportunity |
| Date discovered / Date approved | radar | |
| Approved by | radar | reviewer email |
| Do not contact | radar | true/false — propagated from suppressions |
| Assigned rep | **crm** | set on create from `assigned_to`; never overwritten |
| Status | **crm** | `New` on create; never overwritten |
| Follow-up date | **crm** | empty on create; never overwritten |
| Notes | **crm** | reviewer approval note on create; never overwritten |
No personal/owner data, no emails other than the reviewer and assigned rep (internal users). Everything is text, rendered by the CRM — never HTML.

### Sync rules
- **Human gate (non-negotiable):** a business is eligible only if it has ≥ 1 `approved` opportunity **and** is not suppressed. Checked when enqueuing **and again immediately before every send**. Test that nothing else can ever reach an adapter
- **When:** after an approval, schedule the business's sync for `approved_at + CRM_SYNC_DELAY_MINUTES` (default = `REVIEW_UNDO_WINDOW_MINUTES` = 30) so undone approvals never reach the CRM. `sync_due()` runs every minute from the worker (RQ scheduler or a simple loop in the worker process — pick one, note it) and processes due items. `CRM_AUTO_SYNC=true` by default
- **Undo:** if the approval is undone before the sync, the scheduled sync is cancelled. If it was already synced, the CRM record is updated (the service is removed from Services; if no approved services remain, set Status only if it is still `New` to `Withdrawn` — otherwise leave CRM-owned fields alone and add nothing)
- **Later approvals** of other services for the same business update the same CRM record (Services, score, reasons); CRM-owned fields untouched
- **Dedupe:** use the stored `external_id`; if none, `find_by_keys` (Radar Business ID first, then domain, then phone) — link to an existing record instead of creating a duplicate, and log that it was linked
- **Unchanged payload** (same hash as last successful sync) → no API call, `action = unchanged`
- **Retry:** `CrmTransientError` / 429 / 5xx → exponential backoff, max 3 attempts, honour `Retry-After`. Then status `held` with the error. Auth/config/rejected errors → `held` immediately. Held leads show on `/crm`, with Retry
- **Suppression after sync:** a do-not-contact on a business already in the CRM calls `mark_do_not_contact` (sets the Do not contact field; never deletes the CRM record). Lifting the suppression sets it back to false
- **Every attempt** writes `crm_sync_attempts` (action, status, http status, error, duration) and an audit log row

### CSV adapter
- `GET /crm/export.csv` (crm_manager, admin): streams eligible businesses with the same columns as the table above. `?scope=new` (default: not yet exported) or `?scope=all`. Exporting marks those rows `synced` with `destination=csv` and an export batch id
- **CSV/formula injection protection:** any cell starting with `=`, `+`, `-`, `@`, tab or carriage return is prefixed with `'`. Test with a business name like `=HYPERLINK(...)`
- UTF-8 with BOM (opens correctly in Excel), RFC 4180 quoting, header row, filename `radar-leads-YYYYMMDD-HHMM.csv`
- `check()` always healthy; `find_by_keys` uses previous export records

### Airtable adapter
- Personal access token in `Authorization: Bearer`, via `core/http.py` (metered, rate-limited per `airtable` source; default 4 req/s, confirm the real limit)
- Upsert by `Radar Business ID` using Airtable's upsert option (`performUpsert.fieldsToMergeOn`) if confirmed; else find-then-create/update. Batch up to the documented per-request limit (confirm; commonly 10)
- CRM-owned fields are sent **only** on create — on update the payload omits them
- Field names come from `crm_field_map.airtable.json` (checked in, editable) so the client can rename columns without code changes
- `make crm-check` → `check()`: token valid, base + table reachable, every mapped field exists with a compatible type; prints a clear table of OK/missing
- Optional `make crm-bootstrap-airtable`: creates the Leads table with all fields (needs `schema.bases:write`); refuses if the table already exists
- `docs/crm/airtable-setup.md`: step-by-step for the client — create base, create table (or run bootstrap), field names/types, create the token with the exact scopes, what to send you

### Fake adapter
Stores records in `crm_fake_records` (dev/test only) so the whole flow can be exercised end to end in the demo; `/crm` shows "Destination: fake (demo)".

### Data model — migration `0007_crm`
- `crm_leads`: `id uuid pk`, `business_id fk`, `destination text`, `external_id text null`, `external_url text null`,
  `status enum[scheduled, syncing, synced, held, cancelled, withdrawn]`, `due_at timestamptz null`, `attempts int`,
  `last_error text null`, `payload_hash text null`, `last_synced_at null`, `export_batch_id text null`, `created_at`, `updated_at`
  unique (`business_id`, `destination`)
- `crm_lead_opportunities`: (`crm_lead_id`, `opportunity_id`) — which approved opportunities the record currently carries
- `crm_sync_attempts`: `id bigserial`, `crm_lead_id fk`, `action enum[create, update, link, unchanged, mark_dnc, withdraw, export]`, `status enum[ok, failed]`, `http_status int null`, `error text null`, `duration_ms int`, `created_at`
- `crm_fake_records` (dev/test): `id uuid`, `fields jsonb`, `created_at`, `updated_at`

### Endpoints (under `/api/v1`)
- `GET /crm/status` — destination, health (`check()`), counts by status (crm_manager, admin, tech_admin)
- `GET /crm/leads?status=held|scheduled|synced` — list with business name + city, attempts, last error (crm_manager, admin)
- `POST /crm/leads/{id}/retry`, `POST /crm/businesses/{business_id}/sync-now` (crm_manager, admin; sync-now still enforces the human gate)
- `POST /crm/sync-all` — enqueue every eligible, due-or-held business (crm_manager, admin)
- `GET /crm/export.csv` (crm_manager, admin)
- `GET /crm/leads/{id}/attempts`
- `GET /leads` and `GET /leads/{opportunity_id}` gain `crm: {status, external_url, last_synced_at}`

### Tests
- Human gate: pending / rejected / not_a_fit / needs_enrichment / suppressed / undone opportunities never reach any adapter (parametrized over all adapters)
- Delay: approval then undo within the window → nothing sent; approval → sent after the delay; sync-now bypasses the delay but not the gate
- One record per business: two approved services → one CRM record with both; a third later updates the same record
- Field ownership: update payload never contains Assigned rep / Status / Follow-up / Notes
- Dedupe: existing Airtable record with the same Radar Business ID or domain is linked, not duplicated
- Unchanged payload → no HTTP call
- Retry/backoff on 429 and 5xx with `Retry-After`; 401/403 and unknown-field 422 → held immediately; retry from held works
- Suppression after sync → `mark_do_not_contact` called; lift → flag reset; CRM record never deleted
- CSV: columns, BOM, quoting, formula-injection prefix, scope=new vs all, export marks rows
- Airtable token never appears in logs, errors, `api_calls` or attempts (sentinel test)
- RBAC for every endpoint; sales_rep sees CRM status only for their own leads
- Frontend: badges, `/crm` page, Retry, Export button, the de-duplicated AI label
- E2E (`make e2e`, fake destination): reviewer approves Barton Creek for rep1 → sync-now → `/crm` shows it synced → rep1 sees "In CRM ✓" → reviewer marks it do-not-contact → fake record shows Do not contact = true

## Acceptance criteria
- [ ] No opportunity that is not `approved` — and no suppressed business — ever reaches any adapter (parametrized test over csv, airtable, fake)
- [ ] An approval undone within 30 minutes never reaches the CRM; a kept approval is synced after the delay
- [ ] Each business appears **once** in the CRM, carrying all its approved services
- [ ] Updates never touch Assigned rep, Status, Follow-up date or Notes
- [ ] An existing CRM record (same Radar Business ID, domain or phone) is linked, not duplicated
- [ ] Re-syncing an unchanged business makes no API call
- [ ] 429/5xx are retried with backoff (max 3); auth/config errors hold immediately; every attempt is logged and visible on `/crm`
- [ ] Do-not-contact after sync sets the CRM flag; the CRM record is never deleted
- [ ] CSV opens in Excel with correct characters, and a cell starting with `=` is neutralised
- [ ] `make crm-check` reports missing Airtable fields clearly (tested with a recorded schema response)
- [ ] The Airtable token never appears in logs, errors or stored rows
- [ ] "AI-generated — verify before use" appears once per AI item; reused classifications count zero escalations
