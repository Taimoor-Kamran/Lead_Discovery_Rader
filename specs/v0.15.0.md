# v0.15.0 — Audit several businesses at once

Branch: `spec/v0.15.0-audit-concurrency`

- **Base:** `main` @ `c993eae` (v0.14.0 merged, schema 0015)
- **Author:** Taimoor
- **Status:** draft

---

## Goal

Auditing is the system's only real throughput limit. Each business takes up to
`AUDIT_SECONDS_PER_BUSINESS` (210 s), one at a time, so 147 businesses is about seven
hours and 100 is about five. That is why a daily run on a laptop keeps dying halfway, and
it is the honest answer to the client's question about doing more businesses per day:
Google's limits are not what stops us, the serial loop is.

The fetch layer was already built for parallel callers. What is serial is one loop in
`audit_web/worker.py:54–58`.

The rule this spec must not break: **auditing several businesses at once must not make a
single business's audit any less careful, or any less polite to the site being audited.**

---

## Scope

- A bounded thread pool over the per-run audit loop, size `AUDIT_CONCURRENCY` (default 4).
- A database session per worker thread, replacing the shared session plus savepoint.
- Progress, cancellation and the result summary made correct under concurrency.
- Nothing else.

## Out of scope

- Any change to what an audit checks or what it claims.
- Any change to the rate limiters, the daily caps or the per-host throttle. They are
  already Redis-backed and shared across processes; this spec relies on that and changes
  none of it.
- `run_single_audit`, which audits one business and stays as it is.
- Converting anything to asyncio. The audit path is synchronous `httpx.Client` with
  `time.sleep`, and threads fit that without a rewrite.
- Running several audit *runs* at once. One run, several businesses inside it.
- Raising any Places or PageSpeed cap.

### 1. Per-thread sessions

- [ ] `_audit_one` takes no session. It opens its own, does the work, commits, closes.
- [ ] The savepoint goes. Each thread's audit is its own transaction, so a failure rolls
      back only that business.
- [ ] `record_failure` still writes its row, in that thread's own session.
- [ ] **`RunTimedOut` must still escape.** It is a `BaseException` and must not be caught
      by the `except Exception` in `_audit_one`, nor swallowed by the pool. A run that
      times out must not record the businesses it was working on as failed audits. This
      was fixed in v0.11.0 and must not regress — add a test that proves it under
      concurrency.
- [ ] A business row read in the main thread is not passed into a worker thread as an ORM
      object. Pass the id; the thread loads its own.

### 2. The pool

- [ ] Replace the loop with a bounded pool of `AUDIT_CONCURRENCY` threads over the same
      list of businesses.
- [ ] `AUDIT_CONCURRENCY` default 4, in `.env.example` and `.env.prod.example`. A value of
      1 must behave exactly as today.
- [ ] The run's time limit still applies to the run as a whole.
- [ ] Results are collected as they finish; ordering is no longer the list's order and
      nothing may depend on it.

### 3. Progress, cancellation and the summary

- [ ] `checkpoint` is called **only from the main thread**, after each result arrives.
      Worker threads never touch the run row.
- [ ] The summary is tallied in the main thread from returned results, not mutated by
      worker threads.
- [ ] **Cancellation keeps its meaning.** Today a run stops between businesses, never
      halfway through one. Under concurrency: on cancel, stop dispatching new businesses,
      let in-flight audits finish, then stop. No audit is abandoned mid-write.
- [ ] Progress counts completed audits, so it still rises monotonically to
      `progress_total`.

- [ ] A test proves the per-run cap behaves the same way.
- [ ] The user agent and `BOT_CONTACT` are unchanged. We identify ourselves exactly as

## Acceptance criteria

1. With `AUDIT_CONCURRENCY=1` the whole existing test suite passes unchanged.
2. At 4, a run produces the same audits and the same summary as at 1, order aside.
3. Two businesses on the same host are never fetched closer together than the configured
   per-host interval, at any concurrency.
4. With 3 calls left on the daily cap and 8 threads claiming, exactly 3 succeed and the
   rest raise before sending.
5. `RunTimedOut` escapes the pool; no business is written as a failed audit because of it.
6. A cancelled run finishes its in-flight audits, starts no new ones, and leaves no
   partially written row.
7. Progress reaches `progress_total` exactly, counting completed audits.
8. A failure in one business leaves the others untouched and writes its own failure row.

## Test plan

Fixture-backed fetches only; no live network. Concurrency is tested with a deterministic
clock and a recording fetcher so the per-host gap can be asserted as an interval rather
than inferred from timing. Cap tests claim from several threads at once against a seeded
Redis counter. The production comparison is the real check on wall-clock gain.

## Implementation notes

**What is already right, and why this is small.** The daily and per-run caps claim their
slot atomically in Redis (`ratelimit.py:131`). The per-host throttle is in Redis and shared
by every process (`safe_fetch.py:223`). A slot limiter already exists
(`safe_fetch.py:275`). The HTTP layer is synchronous `httpx.Client` with an injectable
sleeper. The only serial part is the loop at `worker.py:54–58`.

**What is not right, and is the actual work.** `_audit_one` takes a shared session and uses
`session.begin_nested()`, with a comment saying the savepoint protects "the session the
rest of the run shares". SQLAlchemy sessions are not thread-safe. The savepoint pattern
must become a per-thread session and a per-thread transaction. That touches the error
handling v0.11.0 was written to get right, which is why `RunTimedOut` has its own
acceptance criterion.

**Why 4 and not more.** PageSpeed is capped at 1 request per second, so beyond about 4
concurrent audits the gain falls away while the risk of tripping a site's own rate limiting
rises. 4 should take a 147-business run from about seven hours to under two. If production
shows headroom, raising it later is a one-line change.

**What this does not change.** Nothing about what an audit checks, what it claims, or how
politely it behaves toward a business's website. A faster wrong answer would be worse than
a slow one.

---

## Blockers

- **PageSpeed's 200/day cap is unchanged.** Auditing faster reaches it sooner. A full
  147-business run still spends 147 PageSpeed calls whatever the concurrency.
- **The laptop's DNS has failed repeatedly during long runs.** More simultaneous lookups
  may surface it more often. On a Linux server this does not arise.
