# v0.15.0 — Audit several businesses at once

Branch: `spec/v0.15.0-audit-concurrency`

- **Base:** `main` @ `c993eae` (v0.14.0 merged, schema 0015)
- **Author:** Taimoor
- **Status:** draft

---

## Goal

Auditing is the system's only real throughput limit. Each business takes up to
`AUDIT_SECONDS_PER_BUSINESS` (210 s), one at a time, so 147 businesses is about seven
hours and 100 is about five. That is why a daily run on a laptop keeps dying halfway, and
it is the honest answer to the client's question about doing more businesses per day:
Google's limits are not what stops us, the serial loop is.

The fetch layer was already built for parallel callers. What is serial is one loop in
`audit_web/worker.py:54–58`.

The rule this spec must not break: **auditing several businesses at once must not make a
single business's audit any less careful, or any less polite to the site being audited.**

---

## Scope

- A bounded thread pool over the per-run audit loop, size `AUDIT_CONCURRENCY` (default 4).
- A database session per worker thread, replacing the shared session plus savepoint.
- Progress, cancellation and the result summary made correct under concurrency.
- Nothing else.

## Out of scope

- Any change to what an audit checks or what it claims.
- Any change to the rate limiters, the daily caps or the per-host throttle. They are
  already Redis-backed and shared across processes; this spec relies on that and changes
  none of it. *Amended 2026-10-03 (C1, Taimoor):* the per-host throttle's claim may be made
  atomic (`SET NX PX <interval>`, same key, same interval); nothing else about it changes.
- `run_single_audit`, which audits one business and stays as it is. *Amended 2026-10-03
  (C4, Taimoor):* its call follows `_audit_one`'s new signature; its behaviour does not
  change.
- Converting anything to asyncio. The audit path is synchronous `httpx.Client` with
  `time.sleep`, and threads fit that without a rewrite.
- Running several audit *runs* at once. One run, several businesses inside it.
- Raising any Places or PageSpeed cap.

- [ ] `checkpoint` is called **only from the main thread**, after each result arrives.

## Acceptance criteria

1. With `AUDIT_CONCURRENCY=1` the whole existing test suite passes unchanged.
2. At 4, a run produces the same audits and the same summary as at 1, order aside.
3. Two businesses on the same host are never fetched closer together than the configured
   per-host interval, at any concurrency.
4. With 3 calls left on the daily cap and 8 threads claiming, exactly 3 succeed and the
   rest raise before sending.
5. `RunTimedOut` escapes the pool; no business is written as a failed audit because of it.
6. A cancelled run finishes its in-flight audits, starts no new ones, and leaves no
   partially written row.
7. Progress reaches `progress_total` exactly, counting completed audits.
8. A failure in one business leaves the others untouched and writes its own failure row.

## Test plan

Fixture-backed fetches only; no live network. Concurrency is tested with a deterministic

than inferred from timing. Cap tests claim from several threads at once against a seeded
Redis counter. The production comparison is the real check on wall-clock gain.

## Implementation notes

**What is already right, and why this is small.** The daily and per-run caps claim their
slot atomically in Redis (`ratelimit.py:131`). The per-host throttle is in Redis and shared
by every process (`safe_fetch.py:223`). A slot limiter already exists
(`safe_fetch.py:275`). The HTTP layer is synchronous `httpx.Client` with an injectable
sleeper. The only serial part is the loop at `worker.py:54–58`.

**What is not right, and is the actual work.** `_audit_one` takes a shared session and uses
`session.begin_nested()`, with a comment saying the savepoint protects "the session the
rest of the run shares". SQLAlchemy sessions are not thread-safe. The savepoint pattern
must become a per-thread session and a per-thread transaction. That touches the error
handling v0.11.0 was written to get right, which is why `RunTimedOut` has its own
acceptance criterion.

**Why 4 and not more.** PageSpeed is capped at 1 request per second, so beyond about 4
concurrent audits the gain falls away while the risk of tripping a site's own rate limiting
rises. 4 should take a 147-business run from about seven hours to under two. If production
shows headroom, raising it later is a one-line change.

**What this does not change.** Nothing about what an audit checks, what it claims, or how
politely it behaves toward a business's website. A faster wrong answer would be worse than
a slow one.

### Task 0 sweep (2026-10-03)

Line numbers are on `ac0ba8e` (the branch base; the spec header says `c993eae`, one docs
commit earlier — no code differs).

- **Daily cap — atomic.** `DailyCallCap.reserve` (`core/ratelimit.py:130–147`) is
  `INCR` (:133), compare (:136), `DECR` and raise if over (:137–146). Increment-then-compare,
  so with 3 left and 8 claimers exactly 3 see a value ≤ cap; a refused claimer hands its
  increment back. `RunCallCap.reserve` (:184–211) is the same shape. `SourceLimiter.acquire`
  (:236–251) releases earlier claims if a later guard refuses. The `EXPIRE` on the first
  increment (:134–135) is a separate command; a crash between the two leaves a key without a
  TTL, not an over-spend.
- **Token bucket — safe from threads.** `TokenBucket._take` (:74–93) is `WATCH`/`MULTI`/`EXEC`
  with retry on `WatchError`; each call opens its own pipeline from redis-py's thread-safe
  connection pool. It reads the clock once before the retry loop, so a retried claim can write
  an earlier `updated` time; that lowers the refill it grants, never raises it.
- **Per-host throttle — Redis-backed, blocks the caller, NOT atomic (C1).**
  `HostThrottle.wait` (`core/safe_fetch.py:238–253`): key `audit:throttle:<host>`, `GET` (:246),
  compare, then `SET` (:250). Sleeping is the fetcher's `sleeper` (`time.sleep`), so only the
  calling thread blocks. Called only for backends that resolve DNS (:548–552), i.e. never for
  fixtures.
- **`safe_fetch.py:266–304` — `ConcurrencyGuard`.** A Redis counter `audit:concurrency`
  (:63), shared by every process, limit `AUDIT_MAX_CONCURRENCY` (`config.py:88`, default 4,
  `.env.example:104`). It counts **in-flight page GETs only**: acquired after DNS
  validation and the throttle wait (:554), released after the response is read (:577), for
  fixture fetches too. Robots, homepage and later pages are fetched one after another inside
  one audit, so one audit thread holds at most one slot. It is **soft**: after
  `CONCURRENCY_MAX_WAIT_SECONDS` (30 s, :67) it logs "went ahead anyway" and proceeds
  (:293–298).
  *Does it stack with `AUDIT_CONCURRENCY`?* At `AUDIT_CONCURRENCY ≤ AUDIT_MAX_CONCURRENCY`
  (4 and 4 by default) it never binds: 4 threads hold at most 4 slots, and compose runs one
  worker service, so no other audit job shares the counter. Above that it binds per fetch,
  for at most 30 s each, then gives way, so it cannot serialise a run; it only adds delay.
  *Which limit binds at 4:* none of the Redis limiters in the normal case. The per-host
  throttle binds only for businesses on the same host. The PageSpeed bucket (1 rps,
  `config.py:129`) does not bind, because each PSI call takes seconds to a minute (read
  timeout 60 s, `psi.py:48`), so 4 threads issue far under one call a second. What binds
  is the thread count against per-business latency, and the PSI daily cap (200,
  `config.py:130`) over the day.
- **`AuditTools` (`audit_web/service.py:77–106`).** `build` (:97–106) makes one
  `SafeFetcher` (one `NetworkFetchBackend` → one shared `httpx.Client`,
  `fetch_backends.py:117–120`), one PSI client and one RDAP client (each an `ApiHttpClient`
  with its own `httpx.Client`, `core/http.py:105`), a TCP connectivity probe and DNS tools.
  None of these holds per-business state: PSI, RDAP, the resolver and the probe keep
  configuration only; metering opens its own session per call
  (`discovery/service.py:235–253`); the per-audit state (`_Seen`, :130–136) is a local of
  `audit_business`. Two shared things exist:
  1. `SafeFetcher.requested` (`safe_fetch.py:345`, appended at :556) — every page URL the
     fetcher has asked for, across all businesses. Append-only, atomic under the GIL, and
     read by tests only, never by app code, so it cannot misattribute. It grows for the
     length of the run.
  2. **The shared `httpx.Client`'s connection pool (C2).** See below. This is the one
     place I found where one business's result can carry another's facts.
  `AuditTools.domain_tools()` initialises lazily (:92–95), but `build` always sets it, so
  that path is never raced.
- **`checkpoint`** (`workers/tasks.py:65–79`) sets `progress_done`, bumps `updated_at`,
  flushes, **commits the session**, `refresh`es the run and raises `JobCancelledError` if
  `cancel_requested` (:78). It is the only place cancellation is read. The audit loop calls it
  after each business (`worker.py:59`); the handler runs at `tasks.py:232`.
- **Sessions for a worker job.** `execute_job_run` → `_one_attempt` opens
  `session_scope()` (`core/db.py:161–171`: `get_session_factory()()`, commit on success,
  rollback on exception, close) and passes it to the handler. A per-thread session is the same
  call. One process-wide engine (`db.py:93–96`), default `QueuePool` (5 + 10 overflow); at 4
  threads the peak is about 9 connections (main, 4 audits, 4 metering sessions). Every
  connection has `idle_in_transaction_session_timeout` 600 s (`config.py:52`), longer than
  `AUDIT_SECONDS_PER_BUSINESS`.

### Contradictions between the spec and the code (2026-10-03)

- **C1 — the per-host gap does not hold under threads as written.** `HostThrottle.wait`
  reads the last time, then writes the new one. Two threads fetching the same host can both
  read "free" and both go. That cannot happen today, because one thread does one request at a
  time. Acceptance 3 and task 4's first box need it fixed, but Out of scope says the
  throttle is not changed. Smallest fix that keeps the key, the interval and the
  "blocks the caller" behaviour: claim the slot with one `SET key now NX PX <interval>`; a
  refused claimer sleeps for the key's `PTTL` and tries again. **Needs Taimoor's yes**,
  because it edits the throttle. The alternative (never run two businesses with the same
  website host at once) still misses redirects onto a shared host and robots fetches. Read-only
  query to see how common same-host businesses are:
  `docker exec -e PGOPTIONS='-c default_transaction_read_only=on' radar-prod-postgres-1 psql -U radar -d radar -c "SELECT lower(split_part(split_part(website, '://', 2), '/', 1)) AS host, count(*) FROM businesses WHERE website IS NOT NULL GROUP BY 1 HAVING count(*) > 1 ORDER BY 2 DESC;"`
  (adjust the container name to what `docker ps --filter name=radar-prod` shows).
- **C2 — the shared fetch client can reuse a TLS connection across hosts on one IP.
  Pre-existing; concurrency makes it more likely.** Requests are pinned: the URL's host
  becomes the validated IP, the hostname goes in `Host` and in the `sni_hostname` extension
  (`fetch_backends.py:163–183`). httpcore 1.0.9 picks a pooled connection by origin
  (scheme, host, port) alone (`httpcore/_sync/connection.py:167–168`,
  `connection_pool.py:308`); SNI is used only when a connection is opened
  (`connection.py:107`, `:151`). httpx keeps idle connections 5 s by default. So a request
  for `b.example` on the same shared-hosting IP as `a.example`, within 5 s, can go down
  `a.example`'s connection, whose certificate was checked for `a.example`. The page is
  usually still right (the server routes on `Host`), but **the TLS verdict for `b.example`
  is `a.example`'s**: an invalid certificate can go unrecorded (a missing `tls_invalid`,
  high severity). This happens serially today when two businesses on one IP are audited
  back to back. With 4 threads on shared hosts (Wix, Squarespace, GoDaddy) it happens much
  more often. Found by reading the code; **not reproduced**. Building `AuditTools` per
  thread does not fix it, because one thread still audits businesses one after another
  through one pool. A fix: no keep-alive on the page-fetch client
  (`httpx.Limits(max_keepalive_connections=0)` in `NetworkFetchBackend`), costing one TLS
  handshake per page request (robots, homepage and a few more per audit). No limit, cap or
  interval changes. **Needs Taimoor's yes**, as a fix to the fetch layer.
- **C2 — production evidence (Taimoor, 2026-10-03).** In a 40-host sample, four IP
  addresses each serve two different businesses: one Squarespace, two Cloudflare and one
  Fastly. So at least eight businesses are exposed to connection reuse **today**, in the
  serial code, and the full 147 will have more. The hostname query under C1 returned zero
  because it groups by hostname; this bug is keyed on IP. **This is a live false negative
  about real businesses, not a theoretical risk, and it is the reason this spec is worth
  doing even if concurrency were dropped entirely.** Whether any of the eight currently has
  a certificate problem the old code hid is what the C2 canary in group 6 shows: exposure
  is confirmed, a specific missed finding is not yet. The keep-alive fix moves to the top
  of task group 1, before the pool work.
- **C3 — `RunTimedOut` arrives on the main thread, not in a worker.** RQ 2.12.0 enforces the
  limit with `signal.alarm` (`rq/timeouts.py:70`); `RunDeathPenalty` raises `RunTimedOut` from
  the signal handler (`workers/timeouts.py`), and Python runs signal handlers only on the
  main thread. Under a pool the main thread receives it while waiting for results. Worker
  threads are not interrupted; they keep going until the work horse calls `os._exit`
  (`rq/worker/base.py:1633–1634`), which kills them mid-transaction. Postgres then rolls those
  back: no partial row and no "failed" row. Two consequences for the design:
  (a) the pool must be shut down with `wait=False, cancel_futures=True` when a
  `BaseException` passes, or a `with ThreadPoolExecutor()` block waits for in-flight audits
  past the time limit; (b) an audit that finishes inside RQ's grace minute still commits a
  complete row after the run is marked failed, which is a true audit and not a failure.
  The existing test (`test_audit_run.py:455–496`) raises `RunTimedOut` inside
  `audit_business`, which under a pool means inside a worker; that no longer matches
  production. The new test raises it on the main thread while it waits.
- **C1 — decision (Taimoor, 2026-10-03).** Approved and in scope. Production currently has
  no two businesses on the same hostname (the hostname query returned zero rows), so this
  is not biting today: it is fixed before concurrency makes it possible, not after.
  Acceptance 3 depends on it.
- **C4 — `run_single_audit` "stays as it is", but it calls `_audit_one(session, business)`**
  (`worker.py:94`), whose signature task 1 changes. Conservative reading: `run_single_audit`
  calls the new `_audit_one(business_id)`, so its one audit commits in its own session
  rather than in the run's. Same row, same summary, same progress.
- **C5 — no audit source has a per-run cap.** PageSpeed (`psi.py:299–307`) and RDAP
  (`core/rdap.py:265–275`) build their limiters without `run_call_cap`; only Places does
  (`google_places/client.py:115`). The per-run cap test in task 4 can only exercise
  `RunCallCap` directly from threads; nothing on the audit path depends on it.
- **C6 — two similar settings.** `AUDIT_MAX_CONCURRENCY` exists (fetch slots, soft);
  `AUDIT_CONCURRENCY` is new (businesses in flight). Proposed: keep both, document the
  difference, and log a warning at run start when `AUDIT_CONCURRENCY > AUDIT_MAX_CONCURRENCY`.
  Neither value is changed.
- **C4, C6 — decisions (Taimoor, 2026-10-03).** Both approved as proposed. C2's wording
  stands as corrected: the exposure is confirmed, a hidden bad certificate is not. A check
  that silently does not run is still a defect worth fixing.
- **C7 — "Why 4": PageSpeed's 1 rps is not what limits gains past 4** (see "Which limit
  binds"). The real limits are politeness to shared hosts and PageSpeed's own behaviour
  under parallel calls from one key, which we have not measured. 4 is still a sound start.
- **Benign, recorded.** (a) Two businesses with the same apex domain in flight: the
  `domain_intel` upsert (`domain_intel/service.py:220–225`, `ON CONFLICT DO UPDATE`) makes the
  second wait on the first's row lock until it commits; it does not fail. (b) Each audit's
  domain step already starts its own two-thread pool (`domain_intel/service.py:133`), so 4
  audits can run up to 8 lookup threads. (c) Existing tests: the cancel test
  (`test_audit_run.py:391–416`) flags cancellation from inside `audit_business` and passes
  under a pool only if no more than `AUDIT_CONCURRENCY` businesses are submitted at a time,
  which the cancellation design needs anyway. Seeds in that file are committed before the
  run (`audit_run`, :73–82), so per-thread sessions can see them.

- **The laptop's DNS has failed repeatedly during long runs.** More simultaneous lookups
  may surface it more often. On a Linux server this does not arise.
