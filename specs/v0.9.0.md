# v0.9.0 — Design pass: make it look like a studio built it

**Branch:** spec/v0.9.0-design
**Depends on:** v0.8.0 (merged, tag `v0.8.0`)
**Estimate:** 3–4 working days
**Context:** the client is **Flex The Brand Studio** (flextbs.com). Their own team uses this daily, and they sell design. A tool that looks like unstyled Tailwind undercuts that. This spec changes **presentation only** — no behaviour, no endpoints, no data changes.

## Goal
Give the app one deliberate visual identity and a reviewer-first layout: a design-token system, chosen
typography, a considered density and rhythm, proper empty/loading/error states, real focus and keyboard
support, and a review screen that reads as one clear argument ("here's the business, here's what's wrong with
their site, here's what to sell") instead of three columns of equal-weight boxes.

## Scope
- Token system (colour, type, space, radius, elevation, motion) as CSS variables + Tailwind theme extension
- Typography: two families with a real scale; no all-caps labels, no decorative eyebrows
- Component layer: buttons, inputs, selects, table, card, badge/chip, dialog, toast, tabs, disclosure, tooltip, skeleton, empty state, page header — one implementation each, used everywhere
- Re-layout of every existing screen against the new system (no new screens)
- States: loading (skeletons, not spinners on tables), empty (with the next action), error (what happened + how to fix), busy/disabled, success
- Accessibility floor: visible focus, labelled controls, keyboard operable dialogs/menus, contrast ≥ 4.5:1 for text, `prefers-reduced-motion` respected, correct landmarks and headings
- Responsive: usable 1280→1024, degrades cleanly to a tablet width; tables scroll rather than squash
- Print stylesheet for the lead detail page (reps print or PDF before calls)
- Documented design decisions in `docs/design.md`

## Out of scope
- Any API, data or workflow change; no renamed fields; no new features
- A component library dependency (shadcn/Radix etc.) — keep the current stack; build the small set by hand
- Dark mode (note it as a future option; do not build it)
- Rewriting copy wholesale — only the specific strings listed under "Writing"
- Logo/brand identity work for the client's own brand

## Human prerequisites
- Confirm with the client: may we use their brand colours and typefaces from flextbs.com? If yes, send the hexes/font names (or the brand guide). If no, we choose an internal palette that does not imitate their site
- If a licensed typeface is required, the client provides the licence/webfont files. Otherwise we use open fonts

## Design direction (the plan to follow; revise in `docs/design.md` if the client's brand dictates otherwise)
**Subject:** an internal evidence tool. Its job is to make a reviewer confident enough to approve or reject in
under two minutes. The personality should be *calm instrument*, not *marketing dashboard*: quiet surfaces,
strong hierarchy, evidence given typographic weight.

**Colour** — ink and paper, with one working accent and a strict semantic set:
| Token | Value | Use |
|---|---|---|
| `--ink` | `#101826` | primary text, header bar |
| `--ink-soft` | `#475467` | secondary text, labels |
| `--paper` | `#FBFAF8` | app background |
| `--surface` | `#FFFFFF` | cards, table rows |
| `--line` | `#E4E7EC` | borders, rules |
| `--accent` | `#0F766E` (deep teal) | primary actions, active nav, focus ring |
| `--warn` / `--risk` / `--ok` | amber / red / green, one shade each + a 10 % tint | severity, alerts, status only |
Severity and status are the **only** things allowed to use colour as meaning, and each also carries text.
No gradients. No coloured card backgrounds except severity tints.

**Type** — two families, clearly distinct:
- **Display/UI:** a humanist sans with real weights (e.g. Inter Tight, Public Sans, or the client's brand sans)
- **Evidence/data:** one monospace-adjacent or narrow face (e.g. IBM Plex Mono) used **only** for quoted
  evidence, URLs, scores and IDs — so a reviewer can tell at a glance what came from the website and what is our wording
- Scale: 12 / 13 / 15 / 17 / 21 / 27 px, line-height 1.5 body and 1.2 headings, measure ≤ 72 characters
- Sentence case everywhere. **No** tracked-out all-caps labels, no `LABEL —` eyebrows, no `·`-joined meta strings

**Layout**
- App shell: slim top bar (product name, primary nav, account), content max-width 1440 px, generous gutters
- Review detail becomes a **two-column argument**, not three equal panels:
```
┌──────────────────────────────────────────────┬──────────────────────┐
│ Business name              Austin, TX   [DNC]│  Opportunities       │
│ phone · website · industry                   │  ┌────────────────┐  │
├──────────────────────────────────────────────┤  │ Website redesign│ │
│ What the audit found                         │  │ score 78        │ │
│  ● No HTTPS            evidence…             │  │ [Approve][Reject]│ │
│  ● Not mobile-friendly evidence…             │  │ why · evidence  │ │
│  ● No online booking   evidence…             │  └────────────────┘  │
│ Speed  55/100 · 3.6 s                        │  ┌────────────────┐  │
│ AI summary (labelled, muted)                 │  │ SEO …          │  │
└──────────────────────────────────────────────┴──────────────────────┘
```
  Findings are a **list with severity markers**, not six stacked cards. The decision column is sticky.
- Queue and leads tables: denser rows, aligned numerals (tabular figures), the score as the rightmost column, one hover state, selection only on hover/selected
- 4 px spacing grid; radius 6 px for controls, 10 px for surfaces; one shadow level, used only for overlays

**Principles**
1. Evidence gets the distinct typeface; our wording stays plain.
2. One accent colour; severity is the only other colour that carries meaning.
3. Quiet by default — nothing animates unless it answers a click.
4. Every screen answers "what do I do next" in its empty state.

## Writing (only these strings)
- Buttons say what happens and keep the same word through the flow: **Approve** → toast **Approved**
- Empty states: Review queue → "Nothing to review. Run a search to find businesses." with a link to Searches; My leads → "No leads yet. A reviewer assigns leads to you."; CRM → "Nothing waiting. Approved leads appear here 30 minutes after approval."
- Errors state cause + fix: "Couldn't reach the API. Check that the api container is running (`make prod-ps`)."
- Replace remaining system vocabulary in the UI with user words: "opportunity" → **lead**? **No** — keep "opportunity" until approval and "lead" after, matching the blueprint's states; document this in `docs/design.md` so it stays consistent

## Implementation notes

- **Codes read as words, raw value in the tooltip.** The manual review found the business facts
  panel still printing the API's codes (`plumbing`, `own_site`, `operational`). `lib/labels.ts`
  gained `WEBSITE_KIND_LABELS` (Own website / Builder site / Social profile only / No website),
  `BUSINESS_STATUS_LABELS` (Open / Temporarily closed / Permanently closed / Unknown) and
  `industryLabel`, and every place those three fields appear now uses them: `BusinessFacts`,
  `QueueTable`, `LeadDetail` and `AiSummaryBox`. The raw code stays in the element's `title`, the
  pattern already used for finding codes and services. `INDUSTRY_LABELS` holds only `hvac`, the one
  slug the generic `humanize` reads wrongly — the taxonomy is data that grows without a code change,
  and `slug → Slug` is exactly the label the API's own industry dropdown returns, so a table listing
  every slug would be a second source of truth to keep in sync. The field-provenance table under the
  disclosure keeps showing values verbatim: it is *about* what was stored. `BusinessFacts.test.tsx`
  renders every website-kind × business-status pair and asserts no raw code reaches the text.
- **The API-unreachable message names the right stack.** It hard-coded `make prod-ps`, which is
  wrong advice for someone running `make up`. The obvious signal, `NODE_ENV`, is the wrong one:
  both compose stacks run the same image and that image is a production Next build, so `NODE_ENV`
  reads `production` after `make up` as well — the bundle currently on disk has `make prod-ps`
  inlined for exactly that reason. So the build now carries the stack it was built for:
  `NEXT_PUBLIC_ENVIRONMENT`, a build arg compose fills from the project's existing `ENVIRONMENT`
  (`local` in `docker-compose.yml`, `production` in `docker-compose.prod.yml`), inlined by Next
  like `NEXT_PUBLIC_API_BASE_URL` beside it. `production` and `staging` say `make prod-ps`;
  anything else, including an unset value, says `make ps`, because the development stack is the
  safer thing to name when we do not know. `API_UNREACHABLE` became `apiUnreachable()` for that
  reason; `loadFailed()` and `SignInPanel` are the callers. `lib/errors.test.ts` covers both
  stacks, the unset fallback, and that `NODE_ENV` does not override the answer.
  **The web image must be rebuilt (`make build`) for the string to change** — it is inlined, not
  read at runtime.
- The searches table and pipeline header keep showing `job.industry` verbatim. That field is not one
  of these enums — it is the free text sent to the source (`chosen.query`, e.g. `plumber`), and
  showing it as typed is provenance, not a raw code leaking into the UI.
