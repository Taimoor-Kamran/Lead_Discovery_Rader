# v0.9.0 — Design pass: make it look like a studio built it

**Branch:** spec/v0.9.0-design
**Depends on:** v0.8.0 (merged, tag `v0.8.0`)
**Estimate:** 3–4 working days
**Context:** the client is **Flex The Brand Studio** (flextbs.com). Their own team uses this daily, and they sell design. A tool that looks like unstyled Tailwind undercuts that. This spec changes **presentation only** — no behaviour, no endpoints, no data changes.

## Goal
Give the app one deliberate visual identity and a reviewer-first layout: a design-token system, chosen
typography, a considered density and rhythm, proper empty/loading/error states, real focus and keyboard
support, and a review screen that reads as one clear argument ("here's the business, here's what's wrong with
their site, here's what to sell") instead of three columns of equal-weight boxes.

## Scope
- Token system (colour, type, space, radius, elevation, motion) as CSS variables + Tailwind theme extension
- Typography: two families with a real scale; no all-caps labels, no decorative eyebrows
- Component layer: buttons, inputs, selects, table, card, badge/chip, dialog, toast, tabs, disclosure, tooltip, skeleton, empty state, page header — one implementation each, used everywhere
- Re-layout of every existing screen against the new system (no new screens)
- States: loading (skeletons, not spinners on tables), empty (with the next action), error (what happened + how to fix), busy/disabled, success
- Accessibility floor: visible focus, labelled controls, keyboard operable dialogs/menus, contrast ≥ 4.5:1 for text, `prefers-reduced-motion` respected, correct landmarks and headings
- Responsive: usable 1280→1024, degrades cleanly to a tablet width; tables scroll rather than squash
- Print stylesheet for the lead detail page (reps print or PDF before calls)
- Documented design decisions in `docs/design.md`

## Out of scope
- Any API, data or workflow change; no renamed fields; no new features
- A component library dependency (shadcn/Radix etc.) — keep the current stack; build the small set by hand
- Dark mode (note it as a future option; do not build it)
- Rewriting copy wholesale — only the specific strings listed under "Writing"
- Logo/brand identity work for the client's own brand

## Human prerequisites
- Confirm with the client: may we use their brand colours and typefaces from flextbs.com? If yes, send the hexes/font names (or the brand guide). If no, we choose an internal palette that does not imitate their site

## Design direction (the plan to follow; revise in `docs/design.md` if the client's brand dictates otherwise)
**Subject:** an internal evidence tool. Its job is to make a reviewer confident enough to approve or reject in
under two minutes. The personality should be *calm instrument*, not *marketing dashboard*: quiet surfaces,
strong hierarchy, evidence given typographic weight.

**Colour** — ink and paper, with one working accent and a strict semantic set:
| Token | Value | Use |
|---|---|---|
| `--ink` | `#101826` | primary text, header bar |
| `--ink-soft` | `#475467` | secondary text, labels |
| `--paper` | `#FBFAF8` | app background |
| `--surface` | `#FFFFFF` | cards, table rows |
| `--line` | `#E4E7EC` | borders, rules |
| `--accent` | `#0F766E` (deep teal) | primary actions, active nav, focus ring |
| `--warn` / `--risk` / `--ok` | amber / red / green, one shade each + a 10 % tint | severity, alerts, status only |
Severity and status are the **only** things allowed to use colour as meaning, and each also carries text.
No gradients. No coloured card backgrounds except severity tints.

**Type** — two families, clearly distinct:
- **Display/UI:** a humanist sans with real weights (e.g. Inter Tight, Public Sans, or the client's brand sans)
- **Evidence/data:** one monospace-adjacent or narrow face (e.g. IBM Plex Mono) used **only** for quoted
  evidence, URLs, scores and IDs — so a reviewer can tell at a glance what came from the website and what is our wording
- Scale: 12 / 13 / 15 / 17 / 21 / 27 px, line-height 1.5 body and 1.2 headings, measure ≤ 72 characters
- Sentence case everywhere. **No** tracked-out all-caps labels, no `LABEL —` eyebrows, no `·`-joined meta strings

**Layout**
- App shell: slim top bar (product name, primary nav, account), content max-width 1440 px, generous gutters
- Review detail becomes a **two-column argument**, not three equal panels:
```
┌──────────────────────────────────────────────┬──────────────────────┐
│ Business name              Austin, TX   [DNC]│  Opportunities       │
│ phone · website · industry                   │  ┌────────────────┐  │
├──────────────────────────────────────────────┤  │ Website redesign│ │
│ What the audit found                         │  │ score 78        │ │
│  ● No HTTPS            evidence…             │  │ [Approve][Reject]│ │
│  ● Not mobile-friendly evidence…             │  │ why · evidence  │ │
│  ● No online booking   evidence…             │  └────────────────┘  │
│ Speed  55/100 · 3.6 s                        │  ┌────────────────┐  │
│ AI summary (labelled, muted)                 │  │ SEO …          │  │
└──────────────────────────────────────────────┴──────────────────────┘
```
  Findings are a **list with severity markers**, not six stacked cards. The decision column is sticky.
- Queue and leads tables: denser rows, aligned numerals (tabular figures), the score as the rightmost column, one hover state, selection only on hover/selected
- 4 px spacing grid; radius 6 px for controls, 10 px for surfaces; one shadow level, used only for overlays

**Principles**
1. Evidence gets the distinct typeface; our wording stays plain.
2. One accent colour; severity is the only other colour that carries meaning.
3. Quiet by default — nothing animates unless it answers a click.
4. Every screen answers "what do I do next" in its empty state.

## Writing (only these strings)

## Implementation notes

- **Codes read as words, raw value in the tooltip.** The manual review found the business facts
  panel still printing the API's codes (`plumbing`, `own_site`, `operational`). `lib/labels.ts`
  gained `WEBSITE_KIND_LABELS` (Own website / Builder site / Social profile only / No website),
  `BUSINESS_STATUS_LABELS` (Open / Temporarily closed / Permanently closed / Unknown) and
  `industryLabel`, and every place those three fields appear now uses them: `BusinessFacts`,
  `QueueTable`, `LeadDetail` and `AiSummaryBox`. The raw code stays in the element's `title`, the
  pattern already used for finding codes and services. `INDUSTRY_LABELS` holds only `hvac`, the one
  slug the generic `humanize` reads wrongly — the taxonomy is data that grows without a code change,
  and `slug → Slug` is exactly the label the API's own industry dropdown returns, so a table listing
  every slug would be a second source of truth to keep in sync. The field-provenance table under the
  disclosure keeps showing values verbatim: it is *about* what was stored. `BusinessFacts.test.tsx`
  renders every website-kind × business-status pair and asserts no raw code reaches the text.
- **The API-unreachable message names the right stack.** It hard-coded `make prod-ps`, which is
  wrong advice for someone running `make up`. The obvious signal, `NODE_ENV`, is the wrong one:
  both compose stacks run the same image and that image is a production Next build, so `NODE_ENV`
  reads `production` after `make up` as well — the bundle currently on disk has `make prod-ps`
  inlined for exactly that reason. So the build now carries the stack it was built for:
  `NEXT_PUBLIC_ENVIRONMENT`, a build arg compose fills from the project's existing `ENVIRONMENT`
  (`local` in `docker-compose.yml`, `production` in `docker-compose.prod.yml`), inlined by Next
  like `NEXT_PUBLIC_API_BASE_URL` beside it. `production` and `staging` say `make prod-ps`;
  anything else, including an unset value, says `make ps`, because the development stack is the
  safer thing to name when we do not know. `API_UNREACHABLE` became `apiUnreachable()` for that
  reason; `loadFailed()` and `SignInPanel` are the callers. `lib/errors.test.ts` covers both
  stacks, the unset fallback, and that `NODE_ENV` does not override the answer.
  **The web image must be rebuilt for the string to change** — `make up` already builds, so a
  `make down && make up` picks it up; it is inlined at build time, not read at runtime.
- The searches table and pipeline header keep showing `job.industry` verbatim. That field is not one
  of these enums — it is the free text sent to the source (`chosen.query`, e.g. `plumber`), and
  showing it as typed is provenance, not a raw code leaking into the UI.

### The first production run: five bugs, one root cause (Part A)

Read out of `logs/worker.log` and `logs/worker.log.2026-09-20`. The whole file is one
story, so it is written as one.

**Root cause — the scheduler thread and job execution shared a socket.** The RQ worker
runs the scheduler in a daemon thread (v0.8.0 §3) *and* `rq.Worker` forks a work horse
for every job. Both halves used the single engine in `app/core/db.py`, so a connection
the scheduler had checked in was copied, file descriptor and all, into a child that then
checked it out and wrote on it. psycopg names its automatic prepared statements `_pg3_N`
per connection and keeps the counter client-side, so two processes on one socket disagree
about what has been prepared:

    psycopg.errors.DuplicatePreparedStatement: prepared statement "_pg3_0" already exists
    psycopg.errors.InvalidSqlStatementName:    prepared statement "_pg3_0" does not exist

That is every one of the 37 `scheduler tick failed` entries, the crash of job
`36b9ea86` in `checkpoint`, the crash of `910e22fd` in `transition`, and the
`DuplicatePreparedStatement` half of the classification failures. Three answers, all in
`app/core/db.py` and all cheap:

1. **The scheduler has its own engine**, with `NullPool` so it holds no connection
   between ticks and a fork finds nothing of its to inherit. `scheduler_session_scope()`
   is the only way the thread reaches the database. `docs/operations.md` says so, because
   the next background thread someone adds to the worker needs to know.
2. **A forked child drops what it inherited.** `os.register_at_fork(after_in_child=…)`
   disposes every pool with `close=False` — the sockets are the parent's and still in
   use, so the child must forget them, never close them. This covers RQ's fork without
   RQ having to be told about it, and covers any other fork too.
3. **Prepared statements are off** (`prepare_threshold=None`) on every psycopg engine.
   Belt as well as braces: with no `_pg3_N` names there is nothing to collide over. The
   plan cache is not worth this failure mode on a workload of this size. Only psycopg
   takes the option, so `connect_args_for()` checks the driver.

**Nothing may leave a run un-finished.** `execute_job_run` wrote every outcome through
the same session the handler had been using, and the `running` and `done` transitions sat
*outside* the try. Two different disasters followed from that.

`910e22fd` (`scheduled:crm-sync`, 2026-09-20T22:17Z) *succeeded*: `run_crm_sync` did its
work, and then `transition(run, done)` hit `DuplicatePreparedStatement` while writing its
audit row. The exception left the function, `session_scope` rolled back — taking the
`running` transition with it, since nothing had been committed — and the run sat in
`queued` with no job on the queue. The scheduler skips a job whose previous run has not
finished, so no CRM sync ran again for a day: 603 lines of "scheduled job skipped".

`36b9ea86` (discovery) had committed, so it stayed `running`; the retry path then tried
to write the failure on the aborted transaction, raised `InFailedSqlTransaction`, and
escaped. Half an hour later the watchdog failed it. No error was ever recorded on it.

So: the `running` transition is **committed before any work starts** (a stuck run should
be visibly stuck, and the watchdog's business); a handler failure is recorded in the
handler's own session **first**, so a handler that wrote something before failing — the
backup-verify alert, say — keeps it; and if that session cannot write, the failure is
carried out and recorded on a brand-new one. `_fail_run` is the last resort: whatever
broke, the run ends `failed` with the reason stored. Every exit from `execute_job_run` is
now terminal. `queued → failed` had to join the state machine for the runs that die
before they start — without it such a run can never be *finished*, and for a
`scheduled:*` kind that stops its job for ever.

**The watchdog now finishes stuck runs of every kind.** It always covered every kind, but
only in `running`; the gap was the other half of "stuck". `abandoned_runs` fails runs
left in `queued` past `WATCHDOG_STALE_MINUTES` that RQ no longer has a job for, with
`queue lost`. Redis is the arbiter and not the clock, so a run genuinely waiting its turn
behind a backlog is left alone, and if Redis cannot be read the sweep is skipped rather
than guessed at — failing runs on a guess is worse than failing them late. The regression
test also asserts the schedule starts moving again afterwards, which is the point.

**Why only 4 places were stored for a 20-result search.** Nothing to do with paging. The
run made exactly one `places:searchText` call, got 200 with a full page of 20, stored
four, and the fifth `checkpoint`'s `session.refresh(run)` hit the shared connection. The
16 results already in hand went with the generator, and because the exception escaped
`execute_job_run` the run was never failed and so never retried. With the failure
recorded properly the attempt retries, and `store_raw` is an upsert, so the retry ends
with all 60 stored — which is what the new test asserts, breaking the run on the fourth
record the way the real one broke (an aborted transaction, not a tidy exception).

**The classification `insertmany` errors.** Two different failures under one log message.
The `DuplicatePreparedStatement` ones are the root cause again. The
`UniqueViolation`s are their own bug:

    duplicate key value violates unique constraint "uq_opportunities_pending_business_service"
    DETAIL: Key (business_id, service)=(aaf0f250-…, booking_setup) already exists

`upsert_opportunities` read the open rows, decided what was missing, and inserted the lot
in one flush at the end. That index is *partial* (`WHERE review_status = 'pending'`), and
a row committed by anyone else between the read and the flush is a hard conflict — which
aborted the transaction and, through `_classify_one`'s savepoint, cost that business its
entire classification. The writer in production was the torn connection: a `COMMIT` from
the other process could make rows visible to the database that this session's snapshot
had not seen. Fixing the connection removes that writer, but the shape of the code was
wrong regardless, so both are fixed. Each new row now goes in inside a savepoint of its
own, fully populated, with a `session.flush()` first so a rollback to the savepoint can
only undo our own insert. A conflict **on that index** means somebody opened the row
first: roll back, take theirs, update it — which is what re-classification is supposed to
do anyway. Any other `IntegrityError` is a real fault and is re-raised, so a missing
`NOT NULL` still fails loudly. `pending_opportunities` also now prefers a `pending` row
over a `needs_enrichment` one for the same service, whatever their ages: `pending` is the
status the index covers, so it is the row an insert would collide with and therefore the
row to update.

**What is *not* changed.** The job framework's retry policy, backoff and cancellation
semantics are untouched; so is what any handler does. `make e2e` and every existing
suite pass unchanged. No migration: `queued → failed` is application state, and the
column already holds every status.

**Regression tests.** `tests/integration/test_worker_concurrency.py` runs a real
scheduler loop against real PostgreSQL while a real job runs, and reproduces RQ's fork
with an idle pooled connection; both fail against the code as it was. The crash paths are
in `test_job_framework.py` (a handler that poisons its transaction, a crash in the
run's own bookkeeping, and `running` surviving a later rollback), the watchdog in
`test_scheduler.py`, the truncated run in `test_discovery_run.py`, and the lost race in
`test_review_classification.py` — that last one reproducing the production
`UniqueViolation` exactly, by committing a rival row in the window between the read and
the insert.

**A note on the evidence.** The production database was not queried; everything above is
read from the two worker logs, the API log and the code. Where the logs cannot settle a
question — whether the torn connection or a second classification run committed the rival
opportunity row — the fix is written to be correct either way and the uncertainty is
written down here rather than smoothed over.
