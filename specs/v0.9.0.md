# v0.9.0 — Design pass: make it look like a studio built it

**Branch:** spec/v0.9.0-design
**Depends on:** v0.8.0 (merged, tag `v0.8.0`)
**Estimate:** 3–4 working days
**Context:** the client is **Flex The Brand Studio** (flextbs.com). Their own team uses this daily, and they sell design. A tool that looks like unstyled Tailwind undercuts that. This spec changes **presentation only** — no behaviour, no endpoints, no data changes.

## Goal
Give the app one deliberate visual identity and a reviewer-first layout: a design-token system, chosen
typography, a considered density and rhythm, proper empty/loading/error states, real focus and keyboard
support, and a review screen that reads as one clear argument ("here's the business, here's what's wrong with
their site, here's what to sell") instead of three columns of equal-weight boxes.

## Scope
- Token system (colour, type, space, radius, elevation, motion) as CSS variables + Tailwind theme extension
- Typography: two families with a real scale; no all-caps labels, no decorative eyebrows
- Component layer: buttons, inputs, selects, table, card, badge/chip, dialog, toast, tabs, disclosure, tooltip, skeleton, empty state, page header — one implementation each, used everywhere
- Re-layout of every existing screen against the new system (no new screens)
- States: loading (skeletons, not spinners on tables), empty (with the next action), error (what happened + how to fix), busy/disabled, success
- Accessibility floor: visible focus, labelled controls, keyboard operable dialogs/menus, contrast ≥ 4.5:1 for text, `prefers-reduced-motion` respected, correct landmarks and headings
- Responsive: usable 1280→1024, degrades cleanly to a tablet width; tables scroll rather than squash
- Print stylesheet for the lead detail page (reps print or PDF before calls)
- Documented design decisions in `docs/design.md`

## Out of scope
- Any API, data or workflow change; no renamed fields; no new features
- A component library dependency (shadcn/Radix etc.) — keep the current stack; build the small set by hand
- Dark mode (note it as a future option; do not build it)
- Rewriting copy wholesale — only the specific strings listed under "Writing"
- Logo/brand identity work for the client's own brand

## Human prerequisites
- Confirm with the client: may we use their brand colours and typefaces from flextbs.com? If yes, send the hexes/font names (or the brand guide). If no, we choose an internal palette that does not imitate their site
- If a licensed typeface is required, the client provides the licence/webfont files. Otherwise we use open fonts

## Design direction (the plan to follow; revise in `docs/design.md` if the client's brand dictates otherwise)
**Subject:** an internal evidence tool. Its job is to make a reviewer confident enough to approve or reject in
under two minutes. The personality should be *calm instrument*, not *marketing dashboard*: quiet surfaces,
strong hierarchy, evidence given typographic weight.

**Colour** — ink and paper, with one working accent and a strict semantic set:
| Token | Value | Use |
|---|---|---|
| `--ink` | `#101826` | primary text, header bar |
| `--ink-soft` | `#475467` | secondary text, labels |
| `--paper` | `#FBFAF8` | app background |
| `--surface` | `#FFFFFF` | cards, table rows |
| `--line` | `#E4E7EC` | borders, rules |
| `--accent` | `#0F766E` (deep teal) | primary actions, active nav, focus ring |
| `--warn` / `--risk` / `--ok` | amber / red / green, one shade each + a 10 % tint | severity, alerts, status only |
Severity and status are the **only** things allowed to use colour as meaning, and each also carries text.
No gradients. No coloured card backgrounds except severity tints.

**Type** — two families, clearly distinct:
- **Display/UI:** a humanist sans with real weights (e.g. Inter Tight, Public Sans, or the client's brand sans)
- **Evidence/data:** one monospace-adjacent or narrow face (e.g. IBM Plex Mono) used **only** for quoted
  evidence, URLs, scores and IDs — so a reviewer can tell at a glance what came from the website and what is our wording
- Scale: 12 / 13 / 15 / 17 / 21 / 27 px, line-height 1.5 body and 1.2 headings, measure ≤ 72 characters
- Sentence case everywhere. **No** tracked-out all-caps labels, no `LABEL —` eyebrows, no `·`-joined meta strings

**Layout**
- App shell: slim top bar (product name, primary nav, account), content max-width 1440 px, generous gutters
- Review detail becomes a **two-column argument**, not three equal panels:
```
┌──────────────────────────────────────────────┬──────────────────────┐
│ Business name              Austin, TX   [DNC]│  Opportunities       │
│ phone · website · industry                   │  ┌────────────────┐  │
├──────────────────────────────────────────────┤  │ Website redesign│ │
│ What the audit found                         │  │ score 78        │ │
│  ● No HTTPS            evidence…             │  │ [Approve][Reject]│ │
│  ● Not mobile-friendly evidence…             │  │ why · evidence  │ │
│  ● No online booking   evidence…             │  └────────────────┘  │
│ Speed  55/100 · 3.6 s                        │  ┌────────────────┐  │
│ AI summary (labelled, muted)                 │  │ SEO …          │  │
└──────────────────────────────────────────────┴──────────────────────┘
```
  Findings are a **list with severity markers**, not six stacked cards. The decision column is sticky.
- Queue and leads tables: denser rows, aligned numerals (tabular figures), the score as the rightmost column, one hover state, selection only on hover/selected
- 4 px spacing grid; radius 6 px for controls, 10 px for surfaces; one shadow level, used only for overlays

**Principles**
1. Evidence gets the distinct typeface; our wording stays plain.
2. One accent colour; severity is the only other colour that carries meaning.
3. Quiet by default — nothing animates unless it answers a click.
4. Every screen answers "what do I do next" in its empty state.

### The first production run: five bugs, one root cause (Part A)

Read out of `logs/worker.log` and `logs/worker.log.2026-09-20`. The whole file is one
story, so it is written as one.

**Root cause — the scheduler thread and job execution shared a socket.** The RQ worker
runs the scheduler in a daemon thread (v0.8.0 §3) *and* `rq.Worker` forks a work horse
for every job. Both halves used the single engine in `app/core/db.py`, so a connection
the scheduler had checked in was copied, file descriptor and all, into a child that then
checked it out and wrote on it. psycopg names its automatic prepared statements `_pg3_N`
per connection and keeps the counter client-side, so two processes on one socket disagree
about what has been prepared:

    psycopg.errors.DuplicatePreparedStatement: prepared statement "_pg3_0" already exists
    psycopg.errors.InvalidSqlStatementName:    prepared statement "_pg3_0" does not exist

That is every one of the 37 `scheduler tick failed` entries, the crash of job
`36b9ea86` in `checkpoint`, the crash of `910e22fd` in `transition`, and the
`DuplicatePreparedStatement` half of the classification failures. Three answers, all in
`app/core/db.py` and all cheap:

1. **The scheduler has its own engine**, with `NullPool` so it holds no connection
   between ticks and a fork finds nothing of its to inherit. `scheduler_session_scope()`
   is the only way the thread reaches the database. `docs/operations.md` says so, because
   the next background thread someone adds to the worker needs to know.
2. **A forked child drops what it inherited.** `os.register_at_fork(after_in_child=…)`
   disposes every pool with `close=False` — the sockets are the parent's and still in
   use, so the child must forget them, never close them. This covers RQ's fork without
   RQ having to be told about it, and covers any other fork too.
3. **Prepared statements are off** (`prepare_threshold=None`) on every psycopg engine.
   Belt as well as braces: with no `_pg3_N` names there is nothing to collide over. The
   plan cache is not worth this failure mode on a workload of this size. Only psycopg
   takes the option, so `connect_args_for()` checks the driver.

**Nothing may leave a run un-finished.** `execute_job_run` wrote every outcome through
the same session the handler had been using, and the `running` and `done` transitions sat
*outside* the try. Two different disasters followed from that.

`910e22fd` (`scheduled:crm-sync`, 2026-09-20T22:17Z) *succeeded*: `run_crm_sync` did its
work, and then `transition(run, done)` hit `DuplicatePreparedStatement` while writing its
audit row. The exception left the function, `session_scope` rolled back — taking the
`running` transition with it, since nothing had been committed — and the run sat in
`queued` with no job on the queue. The scheduler skips a job whose previous run has not
finished, so no CRM sync ran again for a day: 603 lines of "scheduled job skipped".

`36b9ea86` (discovery) had committed, so it stayed `running`; the retry path then tried
to write the failure on the aborted transaction, raised `InFailedSqlTransaction`, and
escaped. Half an hour later the watchdog failed it. No error was ever recorded on it.

So: the `running` transition is **committed before any work starts** (a stuck run should
be visibly stuck, and the watchdog's business); a handler failure is recorded in the
handler's own session **first**, so a handler that wrote something before failing — the
backup-verify alert, say — keeps it; and if that session cannot write, the failure is
carried out and recorded on a brand-new one. `_fail_run` is the last resort: whatever
broke, the run ends `failed` with the reason stored. Every exit from `execute_job_run` is
now terminal. `queued → failed` had to join the state machine for the runs that die
before they start — without it such a run can never be *finished*, and for a
`scheduled:*` kind that stops its job for ever.

**The watchdog now finishes stuck runs of every kind.** It always covered every kind, but
only in `running`; the gap was the other half of "stuck". `abandoned_runs` fails runs
left in `queued` past `WATCHDOG_STALE_MINUTES` that RQ no longer has a job for, with
`queue lost`. Redis is the arbiter and not the clock, so a run genuinely waiting its turn
behind a backlog is left alone, and if Redis cannot be read the sweep is skipped rather
than guessed at — failing runs on a guess is worse than failing them late. The regression
test also asserts the schedule starts moving again afterwards, which is the point.

**Why only 4 places were stored for a 20-result search.** Nothing to do with paging. The
run made exactly one `places:searchText` call, got 200 with a full page of 20, stored
four, and the fifth `checkpoint`'s `session.refresh(run)` hit the shared connection. The
16 results already in hand went with the generator, and because the exception escaped
`execute_job_run` the run was never failed and so never retried. With the failure
recorded properly the attempt retries, and `store_raw` is an upsert, so the retry ends
with all 60 stored — which is what the new test asserts, breaking the run on the fourth
record the way the real one broke (an aborted transaction, not a tidy exception).

**Re-audited once #5's cause moved (Part C).** #4 and #5 rested on the same
torn-connection premise, and #5's turned out to be the double dispatch, so #4 was read
again from the logs rather than left standing on the inference. It holds, on three pieces
of evidence and not on reasoning:

1. **One executor, not two.** `36b9ea86` has exactly one `queued → running` transition in
   `logs/worker.log` (19:53:32), and it was created by the API, not by a demo command:
   `logs/api.log:13187-13188` has the enqueue and then
   `POST /api/v1/search-jobs/8c06a95e…/run → 202` on the same request id. That endpoint
   only queues; it never executes. `load-demo-data`'s double dispatch is not in this
   story.
2. **The error is one only a shared socket can produce.** `DuplicatePreparedStatement:
   prepared statement "_pg3_1" already exists` means the server already knows a name this
   connection's own client-side counter has not issued. Two executors on two connections
   cannot collide that way — a prepared-statement namespace is per connection. Only a
   second process writing on *this* socket can.
3. **The other process is identifiable.** The scheduler tick 41 seconds later
   (19:54:14) failed on the same name, `_pg3_1`, from `enqueue_scheduled_run`. The
   scheduler thread and the forked work horse were on the one connection, which is the
   root cause exactly as written.

So #4 stays where it was. #1 and #3 were checked against the same evidence and did not
move either: both are the same `_pg3_N` collision, and #3's `scheduled:crm-sync` run
`910e22fd` likewise shows a single executor.

**Every symptom's cause, after the re-audit.** #1 (scheduler ticks), #2 (runs left
un-finished), #3 (the blocked CRM schedule) and #4 (the truncated discovery run) are the
torn connection. #5 (the duplicate opportunities) and #6 (`running → running`) are the
double dispatch. "Five symptoms, one cause" was true of the first pass and is not true
now; the two causes are independent and both fixes are needed.

**The classification `insertmany` errors.** Two different failures under one log message.
The `DuplicatePreparedStatement` ones are the root cause again. The
`UniqueViolation`s are their own bug:

    duplicate key value violates unique constraint "uq_opportunities_pending_business_service"
    DETAIL: Key (business_id, service)=(aaf0f250-…, booking_setup) already exists

`upsert_opportunities` read the open rows, decided what was missing, and inserted the lot
in one flush at the end. That index is *partial* (`WHERE review_status = 'pending'`), and
a row committed by anyone else between the read and the flush is a hard conflict — which
aborted the transaction and, through `_classify_one`'s savepoint, cost that business its
entire classification.

**Correction (see "The second executor" below): the other writer was not the torn
connection.** This note first said it was, on the reasoning that a `COMMIT` from the
other process could hide rows from this session's snapshot. That was a guess dressed as a
conclusion, and the log says otherwise: run `af9a4f40` finished with
`opportunities_created: 0, opportunities_updated: 54`, so the rows were already there
when the worker reached them. A second process was classifying the same businesses at the
same time, because the demo commands queued their run *and* executed it. The fix to
`upsert_opportunities` is right either way — a partial unique index is not a hint, and
re-classification has to be idempotent — but it is a second line of defence, not the
cure. The cure is one run, one executor. Each new row now goes in inside a savepoint of its
own, fully populated, with a `session.flush()` first so a rollback to the savepoint can
only undo our own insert. A conflict **on that index** means somebody opened the row
first: roll back, take theirs, update it — which is what re-classification is supposed to
do anyway. Any other `IntegrityError` is a real fault and is re-raised, so a missing
`NOT NULL` still fails loudly. `pending_opportunities` also now prefers a `pending` row
over a `needs_enrichment` one for the same service, whatever their ages: `pending` is the
status the index covers, so it is the row an insert would collide with and therefore the
row to update.

**What is *not* changed.** The job framework's retry policy, backoff and cancellation
semantics are untouched; so is what any handler does. `make e2e` and every existing
suite pass unchanged. No migration: `queued → failed` is application state, and the
column already holds every status.

**Regression tests.** `tests/integration/test_worker_concurrency.py` runs a real
scheduler loop against real PostgreSQL while a real job runs, and reproduces RQ's fork
with an idle pooled connection; both fail against the code as it was. The crash paths are
in `test_job_framework.py` (a handler that poisons its transaction, a crash in the
run's own bookkeeping, and `running` surviving a later rollback), the watchdog in
`test_scheduler.py`, the truncated run in `test_discovery_run.py`, and the lost race in
`test_review_classification.py` — that last one reproducing the production
`UniqueViolation` exactly, by committing a rival row in the window between the read and
the insert.

**A note on the evidence.** The production database was not queried; everything above is
read from the two worker logs, the API log and the code. The one question the first pass
could not settle — whether the torn connection or a second classification run committed
the rival opportunity row — has since been settled against the first pass's guess, by
`af9a4f40`'s summary and by the `done → done` entries; see "The second executor" below
and the re-audit above. The fix to `upsert_opportunities` was written to be correct
either way, which is why it still stands. The lesson kept: where the logs cannot decide,
say so and make the fix indifferent, rather than writing the likelier answer down as a
finding.

### The second executor: one run must have exactly one of them

Found by running `make e2e`, which failed at its first step every time. `reset-demo-data`
reported its classification run as `failed` with an empty `result_summary` — after the
handler had logged `classification run finished`, 29 businesses, 56 opportunities,
`ai_errors: 0`:

    InvalidStateTransitionError: A job run cannot go from 'running' to 'running'

`reset_demo_data` called `enqueue_classification_for_run`, which puts the run on RQ, and
then called `execute_job_run` on it in this process. In the real stack a worker is
listening, so **both** claimed the row: the CLI took it `queued → running` and ran the
handler; the worker picked the same RQ job up, found it already `running`, and raised.
`_fail_run` — correctly, by its own lights — then wrote `failed` on a brand-new session,
over work that had already been committed by somebody else.

`make load-demo-data` had the same defect three times over: it queues the resolution run
and executes it, and each `follow_up` queued the next run for the worker while
`run_pipeline` executed that one too.

**This is not a regression from commit 9695680; that commit exposed it.** Its
`session.commit()` after the `running` transition is what finally let the worker *see*
`running`. Before it, the worker read `queued`, transitioned happily, and ran the same
handler a second time, concurrently, in silence. The three
`A job run cannot go from 'done' to 'done'` entries in `logs/worker.log` are the same
collision arriving a moment later, and the first pass through these logs did not explain
them — it should have. They were the evidence that two executors were on one run all
along.

Two changes, because one is not enough:

1. **The demo commands dispatch to exactly one executor.** `enqueue_run` takes
   `dispatch=False` — create the run, do not queue it — and `follow_up`/`execute_job_run`
   take the same decision down the chain, so `make load-demo-data` walks resolution →
   audit → classification without ever handing one to the worker. *This* process is the
   executor, not the worker, although a worker is available: the command's job is to
   leave the database in a known state and report what it did to its caller (`make e2e`
   reads that before it starts), and waiting on another process would add a timeout, a
   second source of truth for "is it finished", and a hang whenever the worker is down.
   The handler needs nothing a worker has — the fake AI provider answers from checked-in
   files and nothing touches the network — and the test suite calls these functions
   directly, with no worker in existence. `run_inline` was the other candidate and was
   rejected: it would build a different row (no `search_job_id`, no parent link, no
   idempotency key) and would overwrite the summary the classification handler writes.
2. **An attempt that finds a run already `running` backs off.** `_one_attempt` guarded
   only `is_terminal`. RQ legitimately redelivers a job when a worker dies, so this case
   is reachable without any demo command involved. The second arrival now returns
   `running` and touches nothing. Deciding that a `running` run has been abandoned is the
   watchdog's job — it has `WATCHDOG_STALE_MINUTES` to judge by, and an attempt that has
   just walked in has nothing.

**`running → running` stays forbidden in the state machine.** It caught a real
double-execution; permitting it would only hide the next one. The guard is in the
attempt, where the situation is known, not in the rules.

Tests: `test_a_second_executor_of_a_running_run_leaves_it_alone` (the second call runs
mid-handler in a session of its own — all a separate worker process is, from the row's
point of view — and the run still ends `done` with its summary) and
`test_reset_demo_data_leaves_nothing_on_the_queue_for_a_second_executor` (the run reaches
`done` with a non-null summary *and* the queue is empty, so nothing can claim it twice).
Both fail against the code as it was, the first with the exact
`'running' to 'running'` error. `make check` cannot see the real thing — it needs a live
worker in another process — which is what `make e2e` is for.

### The inverse: the normal path must still dispatch (Part D)

`dispatch=False` now threads through `enqueue_run`, `follow_up` and `execute_job_run`, so
every call site carries a dispatch decision. The failure that arrangement invites is the
opposite of the one it fixed, and much worse to find: a missed call site or a default
flipped the wrong way makes a run that is *created and never executed*. Nothing raises,
nothing is logged as an error, and the only sign is a run sitting in `queued` until the
watchdog fails it half an hour later. `running → running` was loud; this is silent.

`test_the_normal_path_still_dispatches_every_link_to_a_worker` walks the real path with
no stand-in for RQ: the API creates the discovery run, the run id is asserted to be on
the queue, and `rq.SimpleWorker` — the real worker minus the fork — drains it in burst
mode, so each `follow_up` link must put the next run on the queue for the same worker to
pick up. The handlers are recorders, because what is under test is the dispatch, not the
work. It asserts the four kinds ran in chain order and that the queue is empty at the
end. Flipping `execute_job_run`'s `dispatch_follow_up` default to `False` stops it after
`discovery` (with `job run created for its caller to execute` in the log and no error);
flipping `enqueue_run`'s `dispatch` stops it at the API. Both were checked. Flipping
`follow_up`'s own default changes nothing, because `execute_job_run` always passes the
decision explicitly — its default is unreachable, which is the right way round: the
decision is made where it is known.

### The one non-terminal exit, and what stands under it (Part E)

`_one_attempt`'s back-off returns `run.status`, which for an already-`running` run is
`running` — **not terminal**. `execute_job_run` returns it, so RQ marks its job complete
for a run this process does not own. That is deliberate and is stated in the docstring as
the single exception to "every exit is terminal", but it is only safe because of what
stands under it:

- **The run is owned.** Normally by the executor that claimed it. If that executor has
  died, the run is left `running` with no RQ job — which is precisely the shape
  `stale_runs` exists to catch, and it is failed with `worker lost` after
  `WATCHDOG_STALE_MINUTES`. Asserted now rather than reasoned about, in
  `test_a_second_executor_hands_the_run_to_the_watchdog_not_to_rq`: the back-off returns
  `running`, touches nothing, counts no attempt and sleeps no backoff, and the watchdog
  then finishes it.
- **Callers compare against `done`, not against "not failed".** `reset_demo_data_command`
  already did (`return 0 if … is JobRunStatus.done else 1`), and so do the backup and
  backup-verify commands. `load_demo_data_command` did **not**: it printed all three of
  its run statuses and returned 0 regardless, checking only that the run *ids* existed.
  A `running` — or a `failed` — would have ended with "Now try GET
  /api/v1/opportunities" and a zero exit, over opportunities that were never classified.
  It now names what did not finish and returns 1. This is the only caller that was
  reading the status loosely; `run_inline`'s callers already had the strict check.

Leaving the back-off non-terminal was preferred to the alternatives. Returning `failed`
would write a verdict on somebody else's work — the original bug. Raising would put the
run back through `_fail_run`, which does the same. Blocking until the other executor
finishes would need a timeout and would hang whenever that executor is the dead one. The
watchdog already exists to adjudicate exactly this, and it is the only party with the
information (elapsed time) to do it.

### Production verification of fixes #1 and #3 (Part F)

The first five parts are argued from logs of the *broken* run and from tests. This is the
acceptance record for the two fixes that could only be proved by the fixed code running
in production: the scheduler's own engine (#1) and the watchdog's reach into `queued`
(#3). Both are confirmed. The fixed worker came up at **2026-09-21T22:07:59Z**
(`rq.worker`, `started with PID 1`); everything below is measured from there.

**#1 — the scheduler thread no longer shares a connection with job execution.**

- The last `scheduler tick failed` in `logs/worker.log` is **2026-09-21T21:24:02Z**, 43
  minutes *before* the restart, and it is also the last `DuplicatePreparedStatement`
  anywhere in the file. Zero of either in the 48 minutes the log covers after the
  restart (it ends 22:56:05Z).
- Absence alone would prove nothing, so note the rate it replaced: pre-fix these landed
  on essentially every tick — 21:14:01, 21:19:02, 21:24:02, five minutes apart, 49
  occurrences in the file. A gap of that length is not the scheduler being quiet.
- And the scheduler is demonstrably *live* across the gap, which is the other half of the
  claim: from the production database, `scheduled:crm-sync` has 48 runs `done` (newest
  22:53Z) and `scheduled:watchdog` 36 (newest 22:50Z). `crm-sync` is enqueued every
  minute in the log through to its last line.

**#3 — the watchdog finishes runs abandoned in `queued`.**

The test case is the original casualty, not a synthetic one. Job run
`910e22fd-741f-45f9-bf4a-92155576e2e5` — the `scheduled:crm-sync` run named in commit
9695680 as the cause of the day-long CRM sync outage — was created 2026-09-20T22:17:04Z
and sat `queued` for **23 h 51 m**, invisible to the old watchdog because it was never
`running`, and blocking every later CRM sync because the scheduler skips a job whose
previous run has not finished. The fixed worker freed it one second after it came up:

    22:07:59Z  app.scheduler  scheduled job skipped: its previous run has not finished
                              job=crm-sync run=910e22fd…            ← the 604th and last
    22:08:00Z  app.jobs.state job run transition  queued → failed   attempts=0
    22:08:00Z  app.scheduled  stale run failed by the watchdog
                              reason="queue lost: the run was still `queued` after the
                              stale-run limit, with no job on the queue"

`attempts=0` is the confirmation that this is the `queued` path and not the `running`
one: the run died before it ever started, which is exactly the case `queued → failed` had
to be added to the state machine for. `crm-sync` has run every minute since, so the
schedule restarted on its own rather than needing a hand — which is what the regression
test in `test_scheduler.py` asserts, now seen in production.

**Not verified this way.** #2, #4, #5 and #6 are not in this record. Each needs its
failure to recur to be observed, and the point of the fixes is that it does not; they
rest on the regression tests, which reproduce the production failures and fail against
the old code.

### The OpenAI 400: every real classification call was rejected (Part G)

Found in real-data testing after the six above, and **not part of the design pass** — see
"Where this belongs" at the end. 18 businesses, `ai_errors: 14`, `ai_calls: 0`,
`est_cost_usd: 0`. Nothing was billed because nothing reached the model.

**The cause.** `OpenAIClient.complete` sent `temperature=0`. This model family
(`gpt-5.6-luna` as `AI_TRIAGE_MODEL`) rejects it:

    400 Unsupported value: 'temperature' does not support 0 with this model. Only the
        default (1) value is supported.   param=temperature code=unsupported_value

Isolated against the live API one parameter at a time: a plain call is 200, the strict
`json_schema` `response_format` is 200, `temperature: 0` is the 400. `temperature` is now
omitted rather than pinned to `1` — the default is the only accepted value, so sending it
buys nothing and is one more thing to change when the next family arrives.

**A correction to the brief: there was no `max_tokens` to rename.** The probe also found
that `max_tokens` is rejected in favour of `max_completion_tokens`, but `grep` over the
whole repository finds neither name: the client never sent an output cap, and `LLMRequest`
has no field for one. So only `temperature` was ever causing the 400. **No output cap has
been added**, because adding one is a behaviour change, not a fix: too low a value
truncates a strict-schema answer mid-JSON and turns a working call into a parse failure,
and the right number is not knowable without measuring real completions. The test asserts
`max_tokens` is absent rather than asserting `max_completion_tokens` is present, so that
whenever a cap is wanted it can only arrive under the new name.

**Provenance of the failure (the second defect, and the reason the first was expensive).**
All 14 rows stored exactly `OpenAI answered 400: BadRequestError`. The response body —
the only thing that names the offending parameter — was thrown away, so diagnosing a
one-line fix needed a manual reproduction against the live API that the stored provenance
should have made unnecessary. `LLMError` now carries the provider's `message`, `param`
and `code`, truncated at `ERROR_BODY_MAX_CHARS` (600). `latency_ms` was also 0 on every
one of them: the elapsed time lived only on the success path, so a run that spent a
minute failing looked instant. `LLMError` carries it now and the row records it.

**What omitting `temperature` costs: classification output is no longer near-deterministic.**

- *It was never a guarantee.* `temperature=0` is greedy decoding, not reproducibility;
  the provider has never promised identical output for identical input, and the request
  carries no `seed`. The honest description of the change is that a strong nudge towards
  stability is gone, not that a guarantee was broken.
- *The reuse cache is unaffected mechanically, but its meaning changes.* `input_hash` is
  a sha256 over prompt version, model and the canonical input — nothing about sampling —
  so `find_reusable` keys and hits exactly as before. What changes is what a hit *means*:
  it used to approximate "what a fresh call would say", and now it pins the first answer
  that was given. For a human-review pipeline that is the better property — a reviewer and
  an auditor see one stable answer per input, and the row says `reused` with the id it
  came from — but "re-run it for a second opinion" no longer works through the cache,
  because the cache is what prevents the second call.
- *The guardrails become load-bearing rather than belt-and-braces.* They already strip
  every claim not supported by the evidence in the input, which is exactly the defence
  sampling calls for; nothing about them needed changing. Expect the
  `guardrail_trimmed` rate to move run to run where it used to be near-constant, so it is
  a rate to watch, not a constant to assert. The strict `json_schema` still fixes the
  *shape* of the answer server-side — variation is in content only.
- *The two-attempt retry in `_classify_one` starts earning its place.* Under greedy
  decoding a re-ask of an identical prompt returned the same unparseable text, so the
  second attempt was near-useless. With sampling a second attempt genuinely can parse
  where the first did not.
- *No test asserted determinism*, so none had to change: the suite drives the fake
  provider, which answers from checked-in files.

**Where this belongs: decided — it merges with v0.9.0.** This section argued for a spec
of its own, on the grounds that v0.9.0's Out of scope excludes "any API, data or workflow
change" and this changes what the AI pipeline does. That was a recommendation, and the
call went the other way: it ships here, with the CHANGELOG entries labelled `v0.9.0`.
The reasoning for the recommendation is left standing above rather than deleted, because
the cost it named is real and now has to be paid deliberately — this spec merges carrying
a behavioural change to the intelligence pipeline that its own Scope does not describe.
Goal and Scope are untouched either way, as they must be. The determinism consequences
above are the acceptance record this change would otherwise have had.
