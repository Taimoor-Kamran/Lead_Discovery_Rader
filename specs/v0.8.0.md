# v0.8.0 — Hardening → v1.0.0 (production mode on one machine)

**Branch:** spec/v0.8.0-hardening
**Depends on:** v0.7.0 (merged, tag `v0.7.0`)
**Estimate:** 4–5 working days
**Blueprint refs:** §4 Maturity tiers — "Production internal" (slide 21), §8 Security controls (slide 42), Failure handling (slide 44), Monitoring metrics (slide 45), §9 Testing + acceptance criteria (slides 49–50), §10 Risks (slide 52), Recommendation — validate with real data (slide 53)

## Goal
Make the MVP safe and dependable to run **for real on one machine** (no public server yet): a locked-down
production mode, daily backups with a tested restore, scheduled maintenance, an in-app health dashboard with
the blueprint's metrics, stronger auth, admin screens so nobody needs Swagger (users + search jobs), faster
tests, and the small leftovers from earlier reviews. Ends with a release checklist; when it is signed off, a human
tags **v1.0.0**. Moving to a VPS later is a separate small spec — this one keeps everything deploy-ready.

## Scope
- Production mode on localhost: `docker-compose.prod.yml` overlay, strict startup checks, ports bound to 127.0.0.1
- Backups: daily `pg_dump`, retention, `make backup` / `make restore` / `make backup-verify`
- Scheduler: purge-expired, backups, CRM `sync_due`, stale-job watchdog — one documented scheduler
- Monitoring: `/admin/health` page + API with the blueprint's metrics and in-app alerts; rotating log files
- Security: login rate limit + lockout, security headers, strict CORS, production config checks, forced password change, pinned-IP SSRF connections, dependency audit
- Admin UI: Users page; Search jobs page (create, cost estimate, run, follow the pipeline)
- Leftovers: timestamped CSV filename, Services on scheduled CRM rows, faster tests, deprecation clean-ups
- Docs: operations runbook, pilot (real-data validation) guide, release checklist

## Out of scope
- Public hosting, domain, TLS certificates, reverse proxy (future `v1.1` VPS spec)
- Email/SMS alerts or any outbound notification service (alerts are in-app + logs)
- Multi-tenant / SaaS, SSO
- New data sources, new CRM adapters

## Human prerequisites
- None to build or test
- For production mode: a strong `JWT_SECRET`, a real admin email and password in `.env.prod` (see Design); **never** reuse the local dev `.env`
- For the pilot run (optional before tagging v1.0.0, strongly recommended): the client's Google Places key + an OpenAI key, per the README

## Design

### 1. Production mode on one machine
- `docker-compose.prod.yml` overlay used by `make prod-up` / `make prod-down` / `make prod-logs`:
  - `ENVIRONMENT=production`, reads `.env.prod` (gitignored; `.env.prod.example` committed)
  - all published ports bound to **127.0.0.1** only (not reachable from the LAN)
  - `restart: unless-stopped`, no source mounts, healthchecks kept, resource limits set
  - separate Docker volumes (`*-prod`) so dev resets never touch production data
- **Startup refuses to run in production** (clear message, non-zero exit) if any of: JWT secret < 32 bytes; `DEBUG=true`; demo fixtures enabled; `CRM_DESTINATION=fake`; `AI_PROVIDER=fake`; admin email is `admin@example.com` or ends with `@example.com`; `DEMO_USERS_PASSWORD` set; CORS allows `*`. Each check has a test
- `make seed-demo-users`, `load-demo-data`, `reset-demo-data` refuse in production (already partly true — make it uniform + tested)
- Refresh cookie `Secure=true` in production (browsers treat `localhost` as a secure context — document this)

### 2. Backups
- `make backup` → `pg_dump -Fc` into `./backups/radar-YYYYMMDD-HHMMSS.dump` (directory gitignored), then keeps the newest `BACKUP_KEEP=14`
- Daily automatic backup at `BACKUP_AT=02:00` local time via the scheduler (below)
- `make restore FILE=…` → restores into the running stack **only** after a typed confirmation (`RESTORE <filename>`), stops api/worker first, runs migrations after
- `make backup-verify` → restores the newest dump into a throw-away database, checks `alembic current` = head and row counts for core tables, drops it. Runs weekly via the scheduler; a failure raises an alert
- Backups never include `.env*` files; README explains to copy `.env.prod` separately and store it safely

### 3. Scheduler
One scheduler (choose: RQ Scheduler, or a small loop inside the worker using `croniter`; document the choice) running:
| Job | When | Notes |
|---|---|---|
| CRM `sync_due` | every minute | existing function |
| `purge-expired` | daily 03:00 | Places content + audit page text + AI raw output |
| backup | daily `BACKUP_AT` | |
| backup-verify | weekly Sunday 04:00 | |
| stale-job watchdog | every 5 min | runs stuck in `running` > 30 min → `failed` with "worker lost", alert |
Each scheduled execution is a `job_run` (`kind` = `scheduled:<name>`) so it is visible and alertable. Only one scheduler instance may run (Redis lock).

### 4. Monitoring (blueprint slide 45)
`GET /admin/health` (admin, tech_admin) + page `/admin/health`:
| Metric | Window |
|---|---|
| Job success rate by kind | 24 h / 7 d |
| External API error rate by source (Places, PSI, OpenAI, Airtable) from `api_calls` | 24 h |
| Median + p95 processing time per job kind | 24 h |
| Queue length (RQ) | now |
| AI calls, reuse rate, cost today / budget | today |
| Data quality: invalid records rate, businesses missing city/phone/website | now |
| Duplicate rate: auto-merged / review / kept apart | 7 d |
| CRM: scheduled / held / synced today | now |
| Source freshness: last successful discovery per source | now |
| Audit outcomes: done / robots / unreachable / failed | 7 d |
| Last backup + last backup-verify result | now |
**Alerts** (in-app banner for admin/tech_admin + `WARNING` log line, stored in an `alerts` table with acknowledge): job success rate < 80 % (24 h), any source error rate > 20 % (24 h), CRM held > 0, AI budget > 80 %, no backup in 36 h, backup-verify failed, stale job detected, queue length > 500. Thresholds in config.
**Logs:** JSON logs also written to `./logs/*.log` with daily rotation, 14 days kept (gitignored).

### 5. Security
- **Login protection:** max 5 failed attempts per email+IP per 15 min → 429; 10 failures per account → locked 15 min; every failure/lockout audited. Generic error message stays the same
- **Forced password change:** users created or reset by an admin get `must_change_password=true`; after login they can only call `/auth/change-password` until they change it. Minimum 12 characters, not equal to email, not in a small built-in list of common passwords
- **Security headers:** API — `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` on authenticated responses. Web — the same plus a Content-Security-Policy (`default-src 'self'`; `connect-src` the API origin; no inline scripts except what Next.js requires via nonce/hash — document the final policy). `Strict-Transport-Security` only when served over https
- **CORS:** exact origins from config; credentials only for those
- **SSRF — pinned connections:** close the v0.4.0 note — `SafeFetcher` connects to the **already-validated IP** (custom transport/resolver) while keeping the hostname for SNI and the Host header, so DNS cannot change between check and connect. Test with a resolver that returns a public IP first and a private IP second
- **Dependency audit:** `make audit` → `pip-audit` (backend) + `pnpm audit --prod` (frontend); fails on high/critical. Not part of `make check` (needs network); runs in the GitHub Actions workflow on every push
- **Secrets hygiene test:** a test greps the repo (excluding `.env*` and fixtures) for key-shaped strings (`sk-`, `AIza`, `pat…`) and fails if any appear
- Upgrade ESLint off the deprecated 9.36 line and remove the Starlette/httpx `TestClient` deprecation warning if the fix is a dependency bump; otherwise note it

### 6. Admin UI
- **`/admin/users`** (admin): list users (email, role, active, last login, locked?), create user (email, role, temporary password → `must_change_password`), change role, deactivate/reactivate, unlock, reset password (sets a new temporary password). All audited. The placeholder `admin@example.com`, if present, shows a warning with a one-click deactivate
- **`/searches`** (admin, sales_rep, tech_admin read-only):
  - Create a search job: industry (dropdown from the taxonomy), city + state **or** lat/lng/radius, max results (≤ `PLACES_MAX_RESULTS_PER_JOB`), source (`google_places`)
  - **Cost estimate before running:** Places calls ≈ ⌈max_results / 20⌉, today's remaining daily cap, expected PageSpeed calls, expected AI calls with the current budget remaining. Run is disabled when the daily cap would be exceeded
  - Run → a pipeline view per run: Discovery → Resolution → Audit → Classification with status, counts from each `result_summary`, errors, and a link to the review queue filtered to that city
  - List of past searches with their last run status and "Run again" (warning if run within the last 7 days: "re-running costs API calls and usually finds the same businesses")
- **`/profile`**: change own password

### 7. Leftovers from reviews
- CSV export filename `radar-leads-YYYYMMDD-HHMM.csv` via `Content-Disposition`
- `/crm` Scheduled rows show Services (from the approved opportunities) before the first sync
- **Faster tests:** `pytest-xdist` with one database per worker; target `make check` < 6 minutes on the dev machine; keep the Stop hook limit at 30 min
- `make e2e` keeps self-resetting; add a check at the start that `CRM_DESTINATION=fake` in dev, otherwise print how to run it

- `docs/pilot.md` — the real-data validation from the blueprint: one industry + one city, 60 results; reviewer reviews ≥ 20; record approval rate, false-positive findings, duplicates missed, time per review, API + AI cost; reps contact approved leads by hand for 14 days and record replies. Includes a results table to fill in and the go/no-go questions
