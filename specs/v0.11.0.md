# v0.11.0 — A deeper audit: accessibility, page quality, and a fifth service

Status: draft
Branch: `spec/v0.11.0-deeper-audit`
Previous: v0.10.0 (provenance, recency, rules-only)

## Goal

Today the audit answers four technical questions and the lead page shows four
findings. A prospect reading it learns that their meta description is missing. They
learn nothing about whether their site is usable, whether anyone can contact them
without picking up the phone, or how their Google presence compares.

This spec widens what the audit observes — using data already fetched or already
available free — so that a lead carries enough substance to open a sales
conversation. Everything added stays deterministic and evidence-backed: a measured
number, or a count of something in the HTML. Nothing subjective, no screenshots, no
opinions about design.

## Scope

### 1. Accessibility and best-practices scores

PageSpeed Insights already returns the full Lighthouse category set. The audit
requests only `performance`.

- Request `accessibility` and `best-practices` alongside `performance` and store both
  scores on `website_audits`.
- Two findings, worded per the catalogue rule:
  - *"PageSpeed scored accessibility at 58 out of 100."* below a configurable
    threshold (default 90)
  - *"PageSpeed scored best practices at 67 out of 100."* below the same threshold
- Both map to the `website_design` service. Both are `null` when PSI is unavailable —
  no key, quota exhausted, or the API failed — and a `null` never produces a finding.
- Show them in the Speed block on the lead page, which becomes **Speed and quality**.

### 2. Page-quality counts from the HTML already fetched

The audit downloads the homepage and currently extracts sixteen boolean-ish checks.
These are countable facts in the same document, and they are the closest honest thing
to a usability signal:

- **Images without alt text** — *"Audit found 37 of 41 images with no alt text on the
  homepage."* Evidence: the first three offending `<img>` tags, truncated.
- **Form inputs without labels** — *"Audit found 4 form fields with no associated
  label on the homepage."*
- **Thin content** — visible-text word count below `AUDIT_THIN_CONTENT_WORDS`
  (default 200). *"Audit found 84 words of visible text on the homepage."*
- **Heading structure** — an `h1` with no `h2` beneath it, or headings that skip a
  level. *"Audit found no section headings below the main heading."*

All four are counts with quotable evidence. None is a judgement.

### 3. A richer prompt, within what the model can already see

The model receives up to 8,000 characters of homepage text and is asked only to
classify services. The same text supports several observations it is never asked for:

- no clear call to action
- no pricing or "request a quote" anywhere
- no opening hours
- no service area stated
- no testimonials or reviews on the page

Add these to the prompt as optional, quote-backed observations subject to the existing
guardrails — a claim without a verbatim quote from the input is dropped, as now.

**Bump the prompt version to `classify-2`.** The reuse cache keys on prompt version +
model + input hash, so every business reclassifies at full price on the first run
after this ships. At roughly $0.0019 per business that is acceptable, but it should be
a deliberate choice, not a surprise on the bill.

### 4. Live chat detection and a fifth service

There is no service for chat, assistant or AI-agent work, so the system can never
produce that lead however obvious the need.

- Detect live-chat and messaging widgets on the homepage by script signature, the same
  mechanism as the existing booking detection: Intercom, Drift, Tawk.to, Crisp,
  HubSpot chat, Zendesk, Tidio, LiveChat, Facebook Customer Chat.
- Finding `no_live_chat`: *"Audit found no live chat or messaging widget on the
  homepage."*
- New service `ai_chat_setup` in `catalogue.py`, labelled **Chat assistant**.
  Confidence follows the existing severity model; this is a medium finding.
- `lib/labels.ts` gains the service and the finding. The v0.10.0 label-guard test
  should fail if either is missed.

### 5. Widen the booking signatures

On the very first real run, the AI flagged this unknown against Copperhead Electrical:

> *"Whether the 'BOOK A SERVICE' element provides functional online booking."*

The page has a booking call to action the audit did not recognise, so `no_online_booking`
may be a false positive there. Widen the signature list to include common booking link
text and hrefs — "book a service", "book online", "schedule service", "request
service", "book now", "schedule an appointment" — as well as the widget scripts.

Add a test for the false-positive case specifically: a page with booking link text but
no known widget must **not** produce `no_online_booking`.

### 6. A builder subdomain is a redesign signal

`topelectricianaustin.wixstudio.com` was classified `website_kind = builder` and
produced no `website_design` opportunity. For a web-design agency a business trading
on a builder's subdomain, with no domain of its own, is among the strongest redesign
leads available.

- Finding `builder_subdomain`: *"Audit found the homepage served from a
  website-builder subdomain."* Evidence: the host.
- Maps to `website_design`, medium severity.
- Does **not** fire when the business has its own domain built on a builder platform —
  a WordPress or Wix site on a custom domain is a different, weaker signal.

### 7. Google rating and review count

`rating` and `userRatingCount` are in the Places response but not in the field mask.

- Add both to the mask, store them, show them on the lead page and in the review queue.
- Finding `few_reviews` when `userRatingCount` is below `PLACES_FEW_REVIEWS`
  (default 20): *"Listing shows 11 reviews."* Maps to `seo_gbp`, low severity.
- **Billing note:** both fields are Enterprise-tier, and the mask already requests
  `websiteUri` and `nationalPhoneNumber`, which are also Enterprise. The request is
  therefore already billed at Enterprise and adding these two does not change the
  tier. Verify against the live console before shipping.
- **Do not add `reviews` or `editorialSummary`.** Those escalate the request to
  Enterprise + Atmosphere, a higher rate, and review text carries attribution and
  caching obligations this spec is not taking on.

## Out of scope

- **Screenshots and vision models.** No rendering, no JavaScript, no image sent to any
  model. Every claim in this system quotes verbatim evidence, and a judgement about a
  picture cannot. This is deliberate and is not to be revisited inside this spec.
- Any opinion about design quality, taste, or whether a site "looks dated".
- Any page other than the homepage. No crawling.
- Any new data source.
- The prospect-facing PDF report and its "why this matters" library — its own spec.
- Rebalancing the scoring weights, including the permanently-zero `intent` component.
- The Google Maps caching and attribution question, which needs legal input first.
- Any change to the review, CRM, suppression or outreach paths.

## Implementation notes

_(append only)_

**Why nothing here is a judgement.** Every addition is a measured number or a count of
something present in a document we fetched. That constraint is what lets a finding
quote its evidence, which is what lets the lead page show a prospect exactly what was
read on their own site. A usability *score* from Lighthouse is Google's measurement,
not ours — quotable and checkable by the prospect. A usability *opinion* from a model
would be neither.

**On the prompt version bump.** `classify-2` invalidates every cached classification.
That is correct behaviour — the cache keys on prompt version precisely so that a
changed prompt is not served stale answers — but it means the first run after this
ships pays full price for every business already in the database.

**Copperhead Electrical — what the real page shows (2026-09-23).** Both routes were used.
Route (b) first, because starting the production database container was refused by this
session's permissions: the homepage
`https://www.copperheadelectricalservices.com/` was fetched once through `SafeFetcher`
(robots.txt allowed it; HTTP 200; sha256 `1ccd58c9…90cf9c`), the same fetch an audit makes.
What it contains:

- `BOOK A SERVICE` is an Elementor button, `<a class="elementor-button …"
  href="…/contact-us">`, and the nav's `Appointment` link goes to the same contact page.
  No booking widget or booking-tool URL is on the homepage.
- The v0.10.0 code **already** recognised that button: `booking_text_match` has matched
  "book a service" in `<a>` text since v0.4.0, so the check reads
  `"link text: BOOK A SERVICE"` and `no_online_booking` is **not** produced — under the old
  code and the new.
- Route (a), later in the session, once the production stack turned out to be running
  already: a read-only query (`default_transaction_read_only=on`) of the stored audit
  confirms it. Copperhead's audit of 2026-09-23 10:05 UTC (`audit-2`, status `done`) stored
  `checks.booking = "link text: BOOK A SERVICE"` and the findings `missing_title`,
  `missing_meta_description`, `no_h1`, `no_structured_data` — **no `no_online_booking`**.
  What the client saw was the AI's unknown, not a rules finding. The same query shows
  Top Electrician Austin stored as `website_kind = own_site`.
- The AI's unknown ("whether the 'BOOK A SERVICE' element provides functional online
  booking") was therefore well founded: the call to action leads to a contact form, not a
  booking tool. **Open for a human:** should a booking call to action that leads to a
  contact page count as online booking? This spec widens the signatures, so it is kept as
  counting; narrowing it is a product decision, not taken here.
- The demo site `copperlineelectric.invalid` reproduces the page's *structure* — the
  Elementor button markup, the contact-page target, the WordPress CSS block, the heading
  order — with an invented business and text, because `app/demo/sites/README.md` forbids
  copying a real website's content into a fixture.
- The same page carries `--wp--preset--shadow--crisp`, a WordPress CSS token on every
  block-theme site. A chat signature on the bare word "crisp" would have reported a chat
  widget there; every chat signature is a script host instead, and a test pins this case.

**`wixstudio.com` was not a builder domain.** `topelectricianaustin.wixstudio.com` was
classified `own_site` with the identity `wixstudio.com` — not `builder`, as scope item 6
says. `wixstudio.com` and eight other per-customer builder domains are added to
`BUILDER_DOMAINS`. The `builder_subdomain` finding reads the host the homepage was *served
from* (`builder_host`), not the stored `website_kind`, so a re-audit of an existing record
is enough; a builder subdomain that redirects to the business's own domain does not fire.
Businesses already stored keep their old `website_kind`/`domain` until they are next
normalised — no data migration rewrites identities (the most conservative option).

**Booking, widened.** A call to action is read from `<a>`, `<button>`, submit/button
`<input>` and `role="button"` elements, by text or, for an icon button, by `aria-label`,
`title` or `value`. A link whose path has a booking segment (`/book-online`,
`/schedule-service`, `/appointments`, …) counts whatever its label; segments are matched
whole, so `/books` and `/bookkeeping` do not.

**Page quality — choices where the spec is silent.**
- Images: only an `<img>` with **no `alt` attribute** is counted. `alt=""` is the correct
  markup for a decorative image, and images hidden from assistive technology
  (`aria-hidden="true"`, `role="presentation"`/`"none"`) are neither shown nor counted —
  the same rule Lighthouse applies. The real Copperhead page has 75 images, all with `alt`.
- Form fields: a placeholder is not a label. Hidden, submit, button, reset and image
  inputs are not fields. `<label for>`, a wrapping `<label>`, `aria-label`,
  `aria-labelledby` and `title` all count as labels. Finding code `unlabelled_form_fields`.
- Thin content: not reported when `js_shell_suspected` is, since that word count describes
  our fetch rather than the page. Its evidence is the count, **never a quote**: on the real
  page the first visible words included a named person's email address.
- Headings: the spec's one wording ("no section headings below the main heading") only
  describes the first of its two conditions, so a skipped level is a second code,
  `heading_level_skipped` — "Audit found the homepage headings skip a level, from h2 to h5."
  A page with no `h1` is left to `no_h1`.
- All five page-quality findings are `low` and map to `website_design`.

**Live chat fires on most homepages.** `no_live_chat` is medium per the spec, so every
audited site without a widget gains an `ai_chat_setup` opportunity at 0.6 — in the demo,
23 of the 24 homepages read. Worth watching once real leads are reviewed.

**The label guard now covers finding codes.** `test_label_coverage.py` checked services,
statuses and sources but not the finding catalogue, so it could not have failed on a
missing finding label as scope item 4 assumes. `FINDING_LABELS` is now checked against
`CATALOGUE`.

**Finding for v0.12.0 (recorded, not implemented — a scope change).** A booking call to
action that links to a contact page (`/contact-us`), as on Copperhead's "BOOK A SERVICE",
should **not** count as online booking. A contact form in place of booking is exactly the
prospect who needs booking set up, so counting it as booking-present hides a real
`booking_setup` lead. v0.11.0 leaves the behaviour as it is: text-matched calls to action
count whatever they link to. A v0.12.0 spec should decide how a link target is judged
(contact paths such as `/contact`, `/contact-us`, `#contact`, `mailto:`; or "only a known
booking tool or booking-path link counts") and how the evidence says so.

**Decision made during the build: the PageSpeed score findings are graded (2026-09-23, at
the product owner's direction; supersedes "both score findings are `low`" above).** The
spec gave these findings no severity. A flat `low` understated a site scoring 58; a flat
`medium` would have treated 88 the same as 58. So each is graded by the score it reports:
below `AUDIT_QUALITY_SCORE_MEDIUM_BELOW` (70) it is `medium`, from 70 up to
`AUDIT_QUALITY_SCORE_THRESHOLD` (90) it is `low`, and at 90 or above nothing is reported.
Both thresholds are configurable. The catalogue keeps `low` as the mildest grade and
`build()` takes the graded severity; the rules already read each stored finding's own
severity. What `medium` changes, before the decision was taken — a finding's severity sets
its confidence (low 0.4, medium 0.6), confidences for one service combine as
`1 − Π(1 − c)` capped at 0.95, and the score is `0.25·facts + 0.45·confidence +
0.10·intent + 0.20·contactability`:

| Other `website_design` findings on the site | low | medium | score change |
|---|---|---|---|
| none — the score finding stands alone | 0.40 | 0.60 | +9 points |
| both score findings, nothing else | 0.64 | 0.84 | +9 |
| one other low finding (live Copperhead: 64 → 69) | 0.64 | 0.76 | +5 |
| one high finding (e.g. no HTTPS) | 0.88 | 0.92 | +2 |
| already at the 0.95 cap (e.g. Pecan Street) | 0.95 | 0.95 | 0 |

Nothing is hidden or revealed by the change (the weak-signal cut is 0.4, inclusive). Under
the graded rule the live Copperhead audit (accessibility 88) stays `low`; the demo's Pecan
Street (58 and 67) becomes `medium`, with no change to its capped confidence.

**Places pagination loop, and the cost estimate (found in the walk-through, 2026-09-24).**
This bug predates v0.11.0 but the manual walk-through cannot complete without the fix, so
it merges with this spec at the product owner's direction.

**Symptom.** A search for "electrician in Austin, TX" with no `max_results` (so 60) reached
"52/52 finished" and then failed on the Google Places daily cap, whatever the cap: 30, 100
and 400. `api_calls` holds 500 `google_places` rows in the 48 hours to 2026-09-24 18:09
UTC — every one `places:searchText`, status 200, attempt 1. Four failed runs made 27, 70,
100 and 300 of them; the three earlier runs of 20 results made one each.

**What it was not.** The counter did not over-count: the Redis daily counters (100 on
09-23, 400 on 09-24) equal the `api_calls` rows for each UTC day exactly, a refused call is
handed back (`decr`), and the key rolls over at UTC midnight. A quota refusal is not
retried (`QuotaExceededError` is not retryable; each run shows one attempt). No call was a
Place Details call — this build makes none; Text Search returns every field.

**What it was — observed, not deduced.** Discovery asked each page for only what it still
wanted, `min(20, limit − yielded)`. Two live walks of the same query on 2026-09-24
(`scripts/places_smoke.py`, new):

| Walk | pageSize sent | places per page | calls | places | how it ended |
|---|---|---|---|---|---|
| always 20 | 20 each | 20, 16, 12, 10, 2 | 5 | 60 | no token |
| as discovery did | 20, 20, 20, 13, 9, 8 | 19, 16, 12, 4, 1, **0** | 6 | 52 | empty page **with a token** |

After 52 places the adapter asked for 8 more; Places answered 200 with no places and a
fresh token (recorded verbatim as
`tests/fixtures/google_places/text_search_empty_page_with_token_recorded.json` — the
token and nothing else). `yielded` stayed at 52, below 60, so discovery sent the same
request again, and again, until the daily cap refused one. That each later page is also
empty is inferred from production (`fetched` frozen at 52 across ~290 calls), not from a
second recorded page.

**Fix.** Every page asks for 20 and the last is trimmed locally — Places bills per
request, so asking for fewer saved nothing and cost results. The walk stops on a page
that brings no **new** place id (an empty page, or a page of repeats — both stall the walk
the same way), and a place seen twice in one walk is yielded once. The comment that said
"at most 20 results a page and 3 pages in total" — which both the builder and the product
owner relied on, and which the first walk disproved — now says what the walks showed. Two
related guards, correct whatever Places does:

- **A slot is spent only on a request that is sent.** `SourceLimiter.acquire` reserved
  the daily slot before waiting on the token bucket and never returned it when the wait
  gave up. It now hands back every slot it claimed when a later guard refuses.
- **A per-run safety limit**: `PLACES_RUN_CALL_CAP_MULTIPLIER` (default 4) ×
  ceil(results / 20). That base is the fewest pages the results could possibly take — a
  floor, not an estimate, and nothing calls it one. It scales with the search, so it holds
  for sizes nobody has tried (200 results → 40). Counted in Redis per job run, so a worker
  retry spends from the same limit. It is checked before the daily cap, so a looping run
  stops without drawing more of the day's budget. Reaching it fails the run at once, not
  retried, with an error that names the count and says plainly it is a safety limit, not a
  quota. It would have stopped each runaway run at 12 calls instead of 300.

**The cost estimate was wrong — because its page arithmetic was wrong.** It showed
"≈ 3" Google Places calls for 60 results, from ceil(60 / 20): full pages of 20. Pages come
back short, so the same search really costs 5 calls. It did not ignore Place Details;
there are none. No exact figure can be promised: page sizes vary between identical
requests — page 1 held 20 places on the first walk and 19 on the second, minutes apart. The
estimate now shows the enforced per-run limit as **"at most N"** (`places_max_calls`, 12
for 60 results), a number the worker guarantees. For scale, *observed, not computed*: two
live walks of one query on 2026-09-24 took 5 and 6 calls for 60 results.

**The run is blocked on that maximum.** The estimate's "not enough calls left today"
blocker now compares the maximum, not a typical figure, with what is left. A run allowed
to start on fewer calls than it may need can be stopped by the daily cap part way through
discovery, which fails the whole run (carried to v0.12.0). The cost: late in a day a run
may be refused though it would probably have fitted.

**Smoke spend.** 12 live calls on 2026-09-24 (1, then 5, then 6), run with
`scripts/places_smoke.py` in the production API container, where the key is. The script,
like `psi_smoke.py`, goes through neither the metering hook nor the daily cap, so those 12
calls are in neither `api_calls` nor the Redis counter. Recorded for v0.12.0.

**The audit run killed at 7/54 (walk-through, 2026-09-24 19:48-20:20 UTC).** Not a hang,
and not the stale-run limit. RQ held every run to its default 180 s because nothing set a
`job_timeout`; at 180 s it raised `JobTimeoutException` — an `Exception` — inside a PageSpeed
request, the audit loop's per-business handler caught it and stored that business
(Harlow Beauty and Hair Salon) as a failed audit, and the loop carried on until RQ killed
the work horse 64 s later, mid-fetch of the eighth business (Smooshine). Nothing was left
to finish the row, so it sat `running` until the watchdog failed it at 30 minutes. The
same swallowed timeout had already cost one business in run `be6a2868` (Hoffman Electric
Company), which reported done. Audits run one at a time at about 35 s each, so 54 take
about 30 minutes — past both the 180 s limit and a watchdog that measured from the start.

The "44% PageSpeed error rate" was attempts, not leads: 4 of 9 attempts hit the shared
20 s read timeout and every retry answered 200 within seconds, so all five businesses that
reached PageSpeed got scores. One further attempt, cut off by the 180 s alarm, was never
metered.

While reading the logs: the PageSpeed key was in them. PSI took it as `&key=` in the URL
and httpx logs every request URL at INFO (5 lines, `logs/worker.log`, git-ignored). The
Google Places key — a different key, sent in a header — appears in none of the log files
or container logs. Fixes, in the order the product owner set: the key moves to the
`X-Goog-Api-Key` header with httpx held at WARNING and the scrubber hardened; the run time
limit is set explicitly and raised as `RunTimedOut`, a `BaseException`; the watchdog reads
`job_runs.updated_at`, a heartbeat every checkpoint moves; PSI waits 60 s.

- **PSI keeps one retry — a deviation from "60 s instead of 20 plus a retry", accepted by
  the product owner (2026-09-25).** With a 60 s read timeout a timeout should be rare, and
  a single attempt would leave a lead without scores after any transient 5xx. Worst case
  per business is about 2 x 65 s, which `AUDIT_SECONDS_PER_BUSINESS` (150) covers.
- **The header is confirmed by two live calls** (`scripts/psi_smoke.py`, example.com,
  2026-09-25). The real key in `X-Goog-Api-Key`: 200 with all three categories — which
  alone proves only a well-formed request, since PSI also answers keyless on a small shared
  quota. A deliberately invalid key in the same header: **400, "API key not valid. Please
  pass a valid API key."** So Google reads and checks the header; a wrong header name would
  have been ignored and answered from the shared quota, the problem the key exists to solve.
- **Audit concurrency is deferred to v0.12.0** by the product owner. Fixes 2-4 let a
  54-business run finish, slowly — about 30 minutes one business at a time — and a slow
  run that completes is preferred to a fast one that adds a new bug.

**The scale proof: audit run `4a5f7154` (2026-09-25 00:37-01:02 UTC, fixed build,
migration `0010`).** 47 of 47 businesses in 25 min 9 s — about eight times the old 180 s
limit — with 0 failed (43 audited, 3 unreachable, 1 skipped). 43 PageSpeed calls, every one
200 on its first attempt, mean 22 s. No PageSpeed key in the new worker logs. The product
owner accepted this as the at-scale proof of the timeout fixes; no forced re-audit.

- **The 60 s PageSpeed read timeout has about 1 s of margin.** The slowest successful call
  in that run took 58,968 ms. Whoever tunes `PSI_TIMEOUT` next: a call that runs over now
  costs a retry — up to another 60 s and a unit of quota — so there is almost no room to
  lower it, and a slower day may already push some calls past it.
- **A host that sleeps mid-run loses the run — a laptop artefact, not a product bug.** The
  classification run that followed (`8bfc8945`) failed at 34/47: the machine slept from
  01:07 to 03:08 (every container log silent, no scheduler rows for 02:00 or 04:00-12:00).
  On waking, RQ compared wall-clock time with the run's limit and killed the work horse
  within 13 s, before `RunTimedOut` — raised by an alarm that, by inference, does not count
  time asleep — could record anything; the watchdog failed the run at 03:56.
