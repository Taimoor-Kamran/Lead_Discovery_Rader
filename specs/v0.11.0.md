# v0.11.0 — A deeper audit: accessibility, page quality, and a fifth service

Status: draft
Branch: `spec/v0.11.0-deeper-audit`
Previous: v0.10.0 (provenance, recency, rules-only)

## Goal

Today the audit answers four technical questions and the lead page shows four
findings. A prospect reading it learns that their meta description is missing. They
learn nothing about whether their site is usable, whether anyone can contact them
without picking up the phone, or how their Google presence compares.

This spec widens what the audit observes — using data already fetched or already
available free — so that a lead carries enough substance to open a sales
conversation. Everything added stays deterministic and evidence-backed: a measured
number, or a count of something in the HTML. Nothing subjective, no screenshots, no
opinions about design.

## Scope

### 1. Accessibility and best-practices scores

PageSpeed Insights already returns the full Lighthouse category set. The audit
requests only `performance`.

- Request `accessibility` and `best-practices` alongside `performance` and store both
  scores on `website_audits`.
- Two findings, worded per the catalogue rule:
  - *"PageSpeed scored accessibility at 58 out of 100."* below a configurable
    threshold (default 90)
  - *"PageSpeed scored best practices at 67 out of 100."* below the same threshold
- Both map to the `website_design` service. Both are `null` when PSI is unavailable —
  no key, quota exhausted, or the API failed — and a `null` never produces a finding.
- Show them in the Speed block on the lead page, which becomes **Speed and quality**.

### 2. Page-quality counts from the HTML already fetched

The audit downloads the homepage and currently extracts sixteen boolean-ish checks.
These are countable facts in the same document, and they are the closest honest thing
to a usability signal:

- **Images without alt text** — *"Audit found 37 of 41 images with no alt text on the
  homepage."* Evidence: the first three offending `<img>` tags, truncated.
- **Form inputs without labels** — *"Audit found 4 form fields with no associated
  label on the homepage."*
- **Thin content** — visible-text word count below `AUDIT_THIN_CONTENT_WORDS`
  (default 200). *"Audit found 84 words of visible text on the homepage."*
- **Heading structure** — an `h1` with no `h2` beneath it, or headings that skip a
  level. *"Audit found no section headings below the main heading."*

All four are counts with quotable evidence. None is a judgement.

### 3. A richer prompt, within what the model can already see

The model receives up to 8,000 characters of homepage text and is asked only to
classify services. The same text supports several observations it is never asked for:

- no clear call to action
- no pricing or "request a quote" anywhere
- no opening hours
- no service area stated
- no testimonials or reviews on the page

Add these to the prompt as optional, quote-backed observations subject to the existing
guardrails — a claim without a verbatim quote from the input is dropped, as now.

**Bump the prompt version to `classify-2`.** The reuse cache keys on prompt version +
model + input hash, so every business reclassifies at full price on the first run
after this ships. At roughly $0.0019 per business that is acceptable, but it should be
a deliberate choice, not a surprise on the bill.

### 4. Live chat detection and a fifth service

There is no service for chat, assistant or AI-agent work, so the system can never
produce that lead however obvious the need.

- Detect live-chat and messaging widgets on the homepage by script signature, the same
  mechanism as the existing booking detection: Intercom, Drift, Tawk.to, Crisp,
  HubSpot chat, Zendesk, Tidio, LiveChat, Facebook Customer Chat.
- Finding `no_live_chat`: *"Audit found no live chat or messaging widget on the
  homepage."*
- New service `ai_chat_setup` in `catalogue.py`, labelled **Chat assistant**.
  Confidence follows the existing severity model; this is a medium finding.
- `lib/labels.ts` gains the service and the finding. The v0.10.0 label-guard test
  should fail if either is missed.

### 5. Widen the booking signatures

On the very first real run, the AI flagged this unknown against Copperhead Electrical:

> *"Whether the 'BOOK A SERVICE' element provides functional online booking."*

The page has a booking call to action the audit did not recognise, so `no_online_booking`
may be a false positive there. Widen the signature list to include common booking link
text and hrefs — "book a service", "book online", "schedule service", "request
service", "book now", "schedule an appointment" — as well as the widget scripts.

Add a test for the false-positive case specifically: a page with booking link text but
no known widget must **not** produce `no_online_booking`.

### 6. A builder subdomain is a redesign signal

`topelectricianaustin.wixstudio.com` was classified `website_kind = builder` and
produced no `website_design` opportunity. For a web-design agency a business trading
on a builder's subdomain, with no domain of its own, is among the strongest redesign
leads available.

- Finding `builder_subdomain`: *"Audit found the homepage served from a
  website-builder subdomain."* Evidence: the host.
- Maps to `website_design`, medium severity.
- Does **not** fire when the business has its own domain built on a builder platform —
  a WordPress or Wix site on a custom domain is a different, weaker signal.

### 7. Google rating and review count

`rating` and `userRatingCount` are in the Places response but not in the field mask.

- Add both to the mask, store them, show them on the lead page and in the review queue.
- Finding `few_reviews` when `userRatingCount` is below `PLACES_FEW_REVIEWS`
  (default 20): *"Listing shows 11 reviews."* Maps to `seo_gbp`, low severity.
- **Billing note:** both fields are Enterprise-tier, and the mask already requests
  `websiteUri` and `nationalPhoneNumber`, which are also Enterprise. The request is
  therefore already billed at Enterprise and adding these two does not change the
  tier. Verify against the live console before shipping.
- **Do not add `reviews` or `editorialSummary`.** Those escalate the request to
  Enterprise + Atmosphere, a higher rate, and review text carries attribution and
  caching obligations this spec is not taking on.

## Out of scope

- **Screenshots and vision models.** No rendering, no JavaScript, no image sent to any
  model. Every claim in this system quotes verbatim evidence, and a judgement about a
  picture cannot. This is deliberate and is not to be revisited inside this spec.
- Any opinion about design quality, taste, or whether a site "looks dated".
- Any page other than the homepage. No crawling.
- Any new data source.
- The prospect-facing PDF report and its "why this matters" library — its own spec.
- Rebalancing the scoring weights, including the permanently-zero `intent` component.
- The Google Maps caching and attribution question, which needs legal input first.
- Any change to the review, CRM, suppression or outreach paths.

## Implementation notes

_(append only)_

**Why nothing here is a judgement.** Every addition is a measured number or a count of
something present in a document we fetched. That constraint is what lets a finding
quote its evidence, which is what lets the lead page show a prospect exactly what was
read on their own site. A usability *score* from Lighthouse is Google's measurement,
not ours — quotable and checkable by the prospect. A usability *opinion* from a model
would be neither.

**On the prompt version bump.** `classify-2` invalidates every cached classification.
That is correct behaviour — the cache keys on prompt version precisely so that a
changed prompt is not served stale answers — but it means the first run after this
ships pays full price for every business already in the database.

## Blockers

- [~] `PAGESPEED_API_KEY` is not yet available. Scope item 1 can be built and tested
  against recorded fixtures, but cannot be verified against the live API until the key
  arrives. Everything else in this spec is independent of it.
- [~] **Prompt `classify-2` (scope item 3) is deferred at the product owner's direction**
  (2026-09-23) until AI is re-enabled. The MVP runs `AI_PROVIDER=disabled`, so a richer
  prompt changes no output anyone sees, and it cannot be tested beyond the Fake provider's
  canned answers. `PROMPT_VERSION` stays `classify-1`. Whoever switches AI back on pays one
  full reclassification either way — adding the `ai_chat_setup` service already changes
  the reuse key, because the service list is part of the hashed input — and that is the
  moment to decide the prompt, with live output to judge it against. The acceptance box
  for `AI_PROVIDER=disabled` stays in scope and is tested.
- [~] **Places billing tier for `rating` and `userRatingCount`** awaits the product
  owner's own check against the live Google Cloud console. It is not ticked on reasoning
  alone; the code change is built and tested against recorded fixtures.
