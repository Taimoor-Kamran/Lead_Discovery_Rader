## Goal

The client's queue brief says every row shows the same three findings and scores bunch
together, so a rep cannot tell the best lead from the sixth. He tagged F1, F2 and F3
"Do first".

Half of that is already fixed in the data. v0.12.0 gave the audit differentiated findings,
v0.12.1 made booking honest, v0.13.0 added domain findings for businesses whose homepage
never answers. **The screen still does not show any of it.**

This covers F2, F3, F8 and F9 — the parts nothing is blocking.

Rules carried forward: show what we know and nothing about what we don't; a reviewer must be
able to see why from what is on the screen.

## Scope

- Two sorts: score (today's default) and review count.
- The F2 decision columns that exist in the data today.
- F3: findings column reordered, top 2 plus "+N more".
- F8: render `method` and `confidence`, already stored and never shown.
- F9: badges for no-website, service-area and permanently-closed.
- `score_components` shown as "why this score" on the detail page.

## Out of scope

- **F1 rank by value** — blocked on price bands. This spec changes how the score is shown
  and sorted, not how it is computed.
- **F4 worklist** — blocked on the lead-owner decision.
- **F7 scorecard** — blocked on branding. Draft outreach is declined on principle.
- **F6 inline duplicates** — deferred.
- Sorting by PageSpeed, finding count or audit date. Each needs its own keyset cursor; add
  later if a rep asks.
- F8's thumbs-down calibration store.
- Any change to scoring, the audit, or opportunity generation.

## Acceptance criteria

1. Both sorts page through the full set exactly once, no row repeated or missing.
2. A business with no PageSpeed score sorts last and renders "—", not 0.
3. The hidden-weak count is identical under both sorts and both directions.
4. `method` and `confidence` are visible; a test asserting this fails against current code.
5. Two businesses with equal scores but different finding counts are distinguishable from
   the row alone.
6. A service-area business and a no-website business are visibly different from each other
   and from a normal row.
7. The findings column shows at most two codes plus a count, and the two shown are not
   identical on every row of a mixed set.
8. No column, badge or tooltip shows a value the system has not measured.

## Test plan

Backend tests use a seeded set with deliberate ties, nulls and duplicate scores so cursor
correctness is exercised rather than assumed. Frontend tests use fixed row fixtures. No test
depends on production data. The manual pass is the real check on ordering: a sort can be
plausible and wrong at the same time.

## Implementation notes

**The cursor is the hard part.** Today's cursor encodes `(top_score, business.id)`. The new
sort needs its own shape with `business.id` kept as the tie-breaker so ordering is total.
Getting this wrong produces duplicate or skipped rows across pages, which looks fine until a
reviewer misses a lead.

**Rarity, not a blocklist.** A hardcoded list of boring codes would rot the moment a new
check lands. Rarity over the current result set adapts on its own and is explainable.

**F8 is nearly free.** `method` and `confidence` are in the data and simply are not rendered.
Cheapest item in the client's brief, and it answers his "can I trust this" question directly.

**What this does not fix.** Scores still cluster, because scoring is unchanged. Sorting by
review count gives a second axis in the meantime. F1 is the real fix and it needs price bands.

### Task 0 sweep (2026-10-02)

- **Queue query** — `backend/app/modules/review/service.py`: `review_queue` :676; grouped
  subquery :713–724 (`business_id`, `top_score` = max score of strong opps, `weak_hidden`);
  outer select :726–729; keyset predicate :748–752; sort :753

- **Cursor today** — urlsafe base64 of `"{top_score}|{business_id}"`, no padding. It carries

### Groups 1, 2, 4 (F8 part), 5 — what was built (2026-10-02)

- **Cursor.** urlsafe base64 of `sort|dir|value|business_id`; an empty value is a null
  review count. Order is `(key IS NULL), key {dir}, business.id {dir}`. The keyset
  predicate is a row-value comparison OR `key IS NULL`, and when the last row's key is null
  it is `key IS NULL AND id {cmp} last_id` (`review/service.py`, `_after`). A cursor from
  another sort or direction, or from before v0.14.0, is a 422.
- **Finding count is null, not 0,** when the audit read nothing and filed nothing (status
  other than `done`/`skipped` with no findings); with no audit at all the UI says "Not
  audited yet". PageSpeed is null whenever `psi.performance_score` is absent.
- **Has-website** uses `website_kind`, so a social profile is "Social profile only", not a
  website, and the no-website badge means `website_kind = none`.
- **Industry filter** offers the taxonomy list from `GET /search-jobs/industries`, the same
  list the search form uses.
- **Closed badge.** The queue does not hide closed businesses; the test runs the real
  pipeline (`opportunities.classify`) and shows a permanently closed business is never
  left with an open opportunity, so no queue row carries the badge. Between a business
  flipping to closed in Places and its next classification, its open rows would still
  list, and would show the badge, honestly.
- **Confidence** was already in tooltips and a disclosure; the new meter puts it on the card
  face with the weak line. The F8 tests were run against the pre-change components and fail
  there (3 failures), then pass.

### Groups 3 and 4 — what was built (2026-10-02)

- **Where rarity is computed (open question, conservative reading).** On the server,
  over the whole filtered set — every business the current filters return, before the
  cursor and the limit — counting businesses whose latest audit has the code
  (`audit_web/service.py`, `finding_code_counts`). Not per page in the browser: that would
  reorder a row's findings as the reviewer paged, and would differ between the two sorts.
  Order is severity, then that count ascending, then the code, so it is total. Each finding
  carries its count and the chip tooltip shows it ("on 3 businesses in this list"), so the
  order can be checked from the screen.
- **`top_findings` in the queue is now two, not three,** and follows the new order. The
  CRM payload's `top_findings` (severity only, sellable only) is untouched.
- **`inference` vs "confidence" (open question, conservative reading).** The spec lists
  "facts, confidence, intent, contactability"; the stored key is `inference`, and
  `scoring.score` sets it to the opportunity's confidence clamped to 0–1. So they are the
  same number. The card labels it "Confidence", with the tooltip naming the stored
  `inference` component; the key and the API are unchanged.
- **Weights are shown only where they provably produced the score:** same
  `scoring_version` as the current one, all four components stored, and the weighted sum
  within 0.0015 of the stored total (both are kept to three places). Otherwise the card
  says the weights are not shown. The weights come from settings via
  `ReviewDetail.scoring_weights`, never from the frontend. Reason: `SCORING_WEIGHT_*` are
  env vars and can change after a row was scored, and scoring stores no weights.
- **A missing component is `null`, not `0.0`.** `summarize()` used to turn a missing key
  into 0.0. Classification always writes all four, so this changes nothing for rows made
  by the pipeline; it stops an incomplete row from showing a measured-looking zero.
- **Context.** A finding is context when its stored `service` is null. In the queue, an
  older audit without the key falls back to the finding catalogue, and a code the
  catalogue does not know is not called context. The detail page's `FindingList` has no
  catalogue, so there an older finding without the key gets no marker either way.
- **Point numbering.** Taimoor's answer called PageSpeed sorting "point 7"; in these notes
  PageSpeed was point 5 and point 7 was where rarity is computed. The PageSpeed answer is
  applied to the PageSpeed question whatever its number.
