## Goal

The client's queue brief says every row shows the same three findings and scores bunch
together, so a rep cannot tell the best lead from the sixth. He tagged F1, F2 and F3
"Do first".

Half of that is already fixed in the data. v0.12.0 gave the audit differentiated findings,
v0.12.1 made booking honest, v0.13.0 added domain findings for businesses whose homepage
never answers. **The screen still does not show any of it.**

This covers F2, F3, F8 and F9 — the parts nothing is blocking.

Rules carried forward: show what we know and nothing about what we don't; a reviewer must be
able to see why from what is on the screen.

## Scope

- Two sorts: score (today's default) and review count.
- The F2 decision columns that exist in the data today.
- F3: findings column reordered, top 2 plus "+N more".
- F8: render `method` and `confidence`, already stored and never shown.
- F9: badges for no-website, service-area and permanently-closed.
- `score_components` shown as "why this score" on the detail page.

## Out of scope

- **F1 rank by value** — blocked on price bands. This spec changes how the score is shown
  and sorted, not how it is computed.
- **F4 worklist** — blocked on the lead-owner decision.
- **F7 scorecard** — blocked on branding. Draft outreach is declined on principle.
- **F6 inline duplicates** — deferred.
- Sorting by PageSpeed, finding count or audit date. Each needs its own keyset cursor; add
  later if a rep asks.
- F8's thumbs-down calibration store.
- Any change to scoring, the audit, or opportunity generation.

## Acceptance criteria

1. Both sorts page through the full set exactly once, no row repeated or missing.
2. A business with no PageSpeed score sorts last and renders "—", not 0.
3. The hidden-weak count is identical under both sorts and both directions.
4. `method` and `confidence` are visible; a test asserting this fails against current code.
5. Two businesses with equal scores but different finding counts are distinguishable from
   the row alone.
6. A service-area business and a no-website business are visibly different from each other
   and from a normal row.
7. The findings column shows at most two codes plus a count, and the two shown are not
   identical on every row of a mixed set.
8. No column, badge or tooltip shows a value the system has not measured.

## Test plan

Backend tests use a seeded set with deliberate ties, nulls and duplicate scores so cursor
correctness is exercised rather than assumed. Frontend tests use fixed row fixtures. No test
depends on production data. The manual pass is the real check on ordering: a sort can be
plausible and wrong at the same time.

## Implementation notes

**The cursor is the hard part.** Today's cursor encodes `(top_score, business.id)`. The new
sort needs its own shape with `business.id` kept as the tie-breaker so ordering is total.
Getting this wrong produces duplicate or skipped rows across pages, which looks fine until a
reviewer misses a lead.

**Rarity, not a blocklist.** A hardcoded list of boring codes would rot the moment a new
check lands. Rarity over the current result set adapts on its own and is explainable.

**F8 is nearly free.** `method` and `confidence` are in the data and simply are not rendered.
Cheapest item in the client's brief, and it answers his "can I trust this" question directly.

**What this does not fix.** Scores still cluster, because scoring is unchanged. Sorting by
review count gives a second axis in the meantime. F1 is the real fix and it needs price bands.

### Task 0 sweep (2026-10-02)

- **Queue query** — `backend/app/modules/review/service.py`: `review_queue` :676; grouped
  subquery :713–724 (`business_id`, `top_score` = max score of strong opps, `weak_hidden`);
  outer select :726–729; keyset predicate :748–752; sort :753
  (`top_score DESC, business.id DESC`, `limit+1`); next cursor :757–760; cursor codec
  `_encode_queue_cursor` / `_decode_queue_cursor` :884 / :890. Router `review/router.py:44`.
- **Cursor today** — urlsafe base64 of `"{top_score}|{business_id}"`, no padding. It carries
  no sort key and no direction, and the predicate is a row-value `<`, which only works
  for DESC on a non-null key. A second sort needs: a version/kind tag and direction in
  the cursor (a cursor replayed under a different sort or direction → 422); for `reviews`,
  explicit nulls handling because `(NULL, id) < (x, id)` is NULL in Postgres. Plan: order
  by `(user_rating_count IS NULL), user_rating_count {dir}, business.id {dir}` and encode
  `null` in the cursor, with the predicate expanded into OR branches. `business.id` stays
  the tie-breaker in both sorts so ordering is total.
- **Table.tsx** — `frontend/src/components/ui/Table.tsx:55` `Th` takes
  `sort?: "ascending" | "descending" | "none"` and `onSort?: () => void`, renders a button
  with `aria-sort` and an arrow. Presentational only; sorting is the caller's job, which
  suits server-side sorting.
- **QueueTable.tsx** — headers :71–80 (select, Business, Industry, Source, Opportunities,
  Audit, Top findings, Score); cells :96–203; review-count chip :117–129; findings chips
  :190–200. `columns` count :65. **FindingList.tsx** — `Finding` type :5–11 (no `method`),
  severity sort :22–24, item render :27–53.
- **score_components** — `opportunities.score_components` JSONB NOT NULL default `{}`
  (`opportunities/models.py:86`), written by `opportunities/service.py:822`. Keys are
  `facts`, `inference`, `intent`, `contactability` (`opportunities/scoring.py:50`), weights
  0.25 / 0.45 / 0.10 / 0.20 from `SCORING_WEIGHT_*` (`core/config.py:221–224`).
  `summarize()` (`opportunities/service.py:1295–1313`) turns a missing key into `0.0`.
  Whether every production row is populated cannot be confirmed without production
  access — query handed to Taimoor.
- **Address / business_status on the queue row** — neither. `QueueItem`
  (`review/schemas.py:153`) has city, state, industry, website, rating, user_rating_count.
  `Business` has `address_line1`, `business_status`, `website_kind` (`businesses/models.py`).
  `state` and `industry` are already accepted by `GET /review-queue`; the UI exposes only city.
- **PageSpeed** — only in `website_audits.psi` JSONB (`performance_score`,
