# Codebase audit — what actually exists (2026-09-25)

Read from the code only: no spec, changelog or commit message was used as evidence.
Paths are relative to `backend/app/` unless they start with `frontend/`. Line numbers are
as of branch `spec/v0.11.1-safety-pass` at commit `5a9cf34`.

**How the audit is shaped (context for everything below).**
- **There is no check registry.** The checks are the keys of one dict assembled by hand:
  - `modules/audit_web/checks.py::fetch_checks` (lines 111–199) covers what the fetch itself tells us.
  - `checks.py::analyse_html` (205–239) covers the parsed HTML.
  - A check is only data. Findings are made separately, by hand-written `if`s in
    `modules/audit_web/findings.py::for_page`, `_content_findings`, `_page_quality_findings`
    and `_quality_score_findings`, from the `CATALOGUE` at `findings.py:86–250`.
- **Exactly one page is fetched per business.** `modules/audit_web/service.py::audit_business`
  calls `tools.fetcher.robots(url)` (line 112) and then `tools.fetcher.fetch(url)` (line 150),
  and nothing else.
- **`FetchOutcome` holds no response headers** (`core/safe_fetch.py:83–96`: `url`, `final_url`,
  `status_code`, `redirect_chain`, `content_type`, `body`, `text`, `truncated`, `tls_valid`,
  `error`, `error_kind`). No check can therefore read a header.

Legend: **Built** means a check exists *and* produces a finding. **Partly** means data is
collected but not acted on, or only a subset is covered. **Absent** means no code.

Notes:
1. **Page title (partly).** `_meta_checks` (`checks.py:262–267`) records the `<title>` text and
   `title_length`. The only finding is `missing_title`, raised when there is no title at all
   (`findings.py:410–411`). Nothing detects a default title ("Home", "My WordPress Site") or a
   thin one: `title_length` is stored and never read.
2. **Meta description (built, presence only).** `checks.py:268–277` records the content and
   `meta_description_length`. Finding `missing_meta_description` is raised when it is absent
   or empty (`findings.py:412–413`). The length is never evaluated.
3. **H1 count (partly).** `_content_checks` (`checks.py:288–298`) records only
   `h1_present` (a bool). Finding `no_h1` (`findings.py:414–415`). Multiple H1s are never
   counted as such. `_heading_structure` (591–627) does list every heading level, so the
   count could be derived, but no rule does.
4. **Social link validity (partly).** `_social_links` (`checks.py:412–431`) substring-matches
   hrefs against `SOCIAL_PLATFORMS` (`fingerprints.py:181–189`) and records which platforms are
   linked. The links are never followed or validated (docstring: "recorded, never followed").
   No finding comes from this check; `ads_social` confidence is a separate constant in
   `opportunities/catalogue.py:28`.
5. **Viewport zoom blocking (partly).** The `viewport_meta` content is stored verbatim
   (`checks.py:257–261`). Finding `no_mobile_viewport` is raised only when the tag is absent
   (`findings.py:408–409`). `user-scalable=no` and `maximum-scale` are never parsed.
6. **Click-to-call (partly).** `tel_link` presence is recorded (`checks.py:307–311`). The only
   finding, `no_contact_on_homepage`, fires when tel, mailto **and** a contact form are all
   absent (`findings.py:419–420`). A site with a form but no `tel:` link gets nothing.
7. **Contact form action inspection (absent).** `_contact_form` (`checks.py:717–727`) finds a
   form by its fields' type/name/id/placeholder/autocomplete. The form's `action` appears
   only inside the evidence string (`_form_evidence`, 730–736) and is never inspected.
8. **Online booking (built).** `_booking` (`checks.py:329–353`) looks, in order, for:
   - a widget signature (`BOOKING_SIGNATURES`, `fingerprints.py:45–59`, 15 vendors);
   - a call to action whose label offers booking;
   - a link to a booking path.

   Finding `no_online_booking` is raised only for industries in `AUDIT_BOOKING_INDUSTRIES`
   (`findings.py:422–424`).
9. **LocalBusiness / JSON-LD (partly).** `_structured_data` (`checks.py:434–453`) parses every
   `application/ld+json` block, flattens `@graph` (`_json_ld_nodes`, 456–469), and returns the
   first LocalBusiness-type `@type` plus the raw block as evidence. Finding
   `no_structured_data` (`findings.py:416–417`). No field (name, address, phone, hours) is
   extracted or compared with the listing.
10. **HTTPS and redirect chain (built).** `fetch_checks` records `redirect_chain`, `final_url`,
    `tls_valid`, `https` and `http_redirects_to_https` (`checks.py:133–198`). Findings:
    `no_https` (`findings.py:371–372`) and `tls_invalid` (`findings.py:341–352`, from the
    unreachable path). `http_redirects_to_https` produces no finding of its own.
11. **CMS/generator version (partly).** `_tech_stack` (`checks.py:472–493`) stores the raw
    `<meta name="generator">` value as `tech_stack.generator`, which includes a version string
    when the site prints one, and maps it to a platform label (`generator_label`,
    `fingerprints.py:327`). The version is never parsed or compared, and `tech_stack` produces
    no finding at all.
12. **Builder/theme detection (partly).** `TECH_SIGNATURES` (`fingerprints.py:140–158`)
    detects the platform: WordPress, Wix, Squarespace, Webflow, GoDaddy, Weebly, Duda, Joomla,
    Drupal and others. The one finding is `builder_subdomain` (`findings.py:374–382`, via

13. **PageSpeed mobile (built).** `NetworkPageSpeedClient` (`psi.py:159–203`) is one GET per

14. **Core Web Vitals (partly).** `parse_psi` (`psi.py:95–115`) keeps lab LCP, CLS and TBT

## Finding model

A finding is the dataclass `modules/audit_web/findings.py::Finding` (lines 62–83). It is
stored as a JSON dict in `WebsiteAudit.findings`, a JSONB list (`modules/audit_web/models.py:83`),
and has no table of its own. `as_dict` emits exactly: `code`, `severity`,
`service_category`, `message`, `evidence_text`, `evidence_url`.

| Field asked about | Real field? | What exists |
|---|---|---|
| `check_id` | **No** | `code` is the *finding* code (e.g. `no_h1`). The check that triggered it (`h1_present`) is passed to `_from_check` (`findings.py:554–563`) only to copy its evidence, and is not stored |
| `status` | **No** | No per-finding status. Status lives on the audit (`AuditStatus`, `models.py:36–43`) and on opportunities (`ReviewStatus`) |
| `severity` | **Yes** | `Severity` enum info/low/medium/high (`findings.py:26–30`). It comes from the catalogue, except the two PSI quality scores, whose severity is graded by score (`findings.py:469–473`) |
| `method` | **No** | Nothing records how a finding was established (HTML parse / PSI / listing). It can only be inferred from the code or the message's opening words |
| `evidence` | **Yes**, as `evidence_text` | Clipped to 300 chars (`checks.py:46`, `clip`) |
| `evidence_url` | **Yes** | Null only for `no_website` (`findings.py:309`) |
| `service_mapping` | **Partly** | See below |
| `dollar_band` | **No** | No price/value/band field anywhere in `audit_web`, `opportunities` or `review`. The only `_usd` fields are AI spend (`est_cost_usd`) |

`service_mapping` in detail:
- **On the finding:** `service_category`, a coarse `ServiceCategory` enum
  (`findings.py:33–43`: web_design, seo, booking, performance, ecommerce, security,
  web_presence, chat).
- **Finding → sellable service:** a separate table, `SERVICES` in
  `modules/opportunities/catalogue.py:46ff`, maps finding codes to services such as
  `website_design` and `seo_gbp`.
- The two disagree in places: for example `slow_mobile` has category `performance` but maps
  to `website_design`.

## The three direct questions

**1. Does the copyright-year check fire on a future year like "© 2035"? No.**
- `_copyright_year` (`checks.py:509`) keeps a year only if
  `EARLIEST_COPYRIGHT_YEAR <= year <= now.year`, so 2035 is discarded.
- If it is the only year on the page, the check returns `False` ("No copyright year on the
  homepage"), exactly like a page with no notice, and no finding is raised.
- The only finding, `stale_copyright` (`findings.py:435–440`), fires only on an *outdated*
  year (≤ now − 3).

Verified by calling the function (now = 2026-09-25):

| Page text | Check value |
|---|---|
| `© 2035 Acme LLC` | `False` |
| `© 2024 Acme` | `2024` |
| `© 2018-2035 Acme` | `2018` |

That last row is a side effect worth knowing. The range pattern's later year (2035) is
rejected, the single-year pattern then matches the first year (2018), and the page is
reported as `stale_copyright` "2018". So a future-dated *range* produces a stale finding.

**2. Does the HTML fetcher strip `<script>` tags before parsing? No.**
- The fetcher (`core/safe_fetch.py`, `core/fetch_backends.py`) returns the body untouched;
  neither file removes any tag.
- `analyse_html` parses the full document, scripts included:
  `soup = BeautifulSoup(outcome.text, "lxml")` at **`checks.py:217`**.
- It also keeps the raw lowercased HTML, `lowered = outcome.text.lower()` at `checks.py:218`.
  The booking, chat, e-commerce and tech signature matches run against that string, and
  they depend on script `src`s and inline scripts being present.
- Scripts are removed only from a **copy**, and only for the visible-text extraction:
  `visible_text` (`checks.py:667–673`) re-parses (`clone = BeautifulSoup(str(soup), "lxml")`,
  line 669) and decomposes `script`, `style`, `noscript`, `template` and `svg` at
  **`checks.py:670–671`**.
- The visible text feeds `copyright_year`, `word_count`, `js_shell_suspected` and the stored
  `page_text`. Everything else sees the scripts.

### Does the audit extract and evaluate JSON-LD / LocalBusiness?

**It detects LocalBusiness JSON-LD, but it does not extract anything from it.** The only
question it answers is whether some JSON-LD node has a LocalBusiness-family `@type`. Name,
address, phone, hours and `sameAs` are never read or compared with the listing.

The code, `checks.py::_structured_data` (434–453):

```python
def _structured_data(soup: BeautifulSoup, url: str) -> CheckResult:
    """Whether the page carries LocalBusiness JSON-LD, and the block that says so."""
    for script in find_tags(soup, "script", attrs={"type": "application/ld+json"}):
        raw = script.string or script.get_text()
        if not raw:
            continue
        try:
            parsed = json.loads(raw)
        except (ValueError, TypeError):
            continue
        for node in _json_ld_nodes(parsed):
            if is_local_business_type(node.get("@type")):
                return CheckResult(
                    str(node.get("@type")),
                    evidence_text=" ".join(raw.split()),
                    evidence_url=url,
                )
    return CheckResult(
        False, evidence_text="No LocalBusiness JSON-LD block on the homepage", evidence_url=url
    )
```

- `_json_ld_nodes` (`checks.py:456–469`) flattens `@graph` and top-level arrays.
- `@type` is matched against a fixed list of 41 types, `LOCAL_BUSINESS_TYPES`
  (`fingerprints.py:195–238`).
- A full URL such as `https://schema.org/Plumber` is reduced to its last segment first
  (`fingerprints.py::is_local_business_type`, 336–341).

**For a site with none**, the check value is `False`, and `findings.py::_content_findings`
(416–417) turns that into a finding:

```python
    if not value_of(checks, "structured_data"):
        findings.append(_from_check(checks, "structured_data", "no_structured_data"))
```

The finding comes from the catalogue entry at `findings.py:150–155`:

```python
        FindingSpec(
            "no_structured_data",
            Severity.low,
            ServiceCategory.seo,
            "Audit found no LocalBusiness structured data on the homepage.",
        ),
```

So a site with none gets:
- **Code** `no_structured_data`, severity **low**, category `seo`.
- **Message:** "Audit found no LocalBusiness structured data on the homepage."
- **Evidence:** "No LocalBusiness JSON-LD block on the homepage", with the page URL.
- **Service:** it counts towards `seo_gbp` (`opportunities/catalogue.py:80`).
- It fires only on a page that was fetched and parsed (`findings.py:384–385`).

**Four quite different pages all get that same "none" answer**, confirmed by calling the
function:

| Page carries | Result |
|---|---|
| No JSON-LD at all | `False` → `no_structured_data` |
| Only an `Organization` or `WebSite` node | `False` → `no_structured_data` |
| A LocalBusiness block with invalid JSON (e.g. a trailing comma) | `False` → `no_structured_data`; the parse error is silently skipped (`checks.py:440–443`), not reported as broken markup |
| LocalBusiness as Microdata (`itemtype=…/LocalBusiness`) | `False` → `no_structured_data`; only `application/ld+json` scripts are read (`checks.py:436`) |

The positive case works, including a node nested in `@graph`:
`{"@graph":[{"@type":"WebSite"},{"@type":"https://schema.org/Plumber"}]}` returns
`"https://schema.org/Plumber"`. That value is the raw `@type` string, not a normalised type
name.
