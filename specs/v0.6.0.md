# v0.6.0 — Human review queue (UI + decisions)

**Branch:** spec/v0.6.0-review-queue
**Depends on:** v0.5.0 (merged, tag `v0.5.0`)
**Estimate:** 4–5 working days
**Blueprint refs:** §2 Personas (slide 7), User journey steps 11–12 (slide 8), Lead states 3→4→5 (slide 9), §7 Human review is a required gate (slide 41), §10 Risks (review bottleneck → prioritised queue, batch UX)

## Goal
The first real screens. A **reviewer** opens a prioritised queue of businesses with pending opportunities,
sees the facts, audit evidence and AI output side by side, and records a decision per opportunity:
**approve, reject, needs enrichment, duplicate, not a fit, do not contact**. Approved opportunities become
**qualified leads** that a **sales rep** can see in "My leads". Duplicate pairs from v0.3.0 get a screen too.
Every decision is recorded, auditable and reversible for a short window. Nothing is exported to a CRM yet (v0.7.0).

## Scope
- Backend: review decisions (single + limited batch), decision history, undo window, optimistic concurrency, business-level **do-not-contact** suppression, re-classification cool-down, review-queue endpoint grouped by business, "my leads" endpoint, demo users
- Frontend: auth flow with refresh, role-aware navigation, **Review queue**, **Business review detail**, **Duplicates**, **My leads**; typed API client generated from OpenAPI
- Safety in the UI: text-only rendering of site/AI content, safe external links, AI content clearly labelled
- Tests: backend API tests, frontend component tests, one end-to-end smoke (`make e2e`, run by a human)

## Out of scope
- CRM export, sync, CRM field mapping (v0.7.0)
- Outreach of any kind (no email/SMS buttons, no templates)
- Editing business facts by hand (reviewers decide, they do not rewrite data)
- Running new searches from the UI (search jobs stay API-only for the MVP; a simple form is v0.8.0 at the earliest)
- Mobile-first design (desktop first; must remain usable at 1024 px wide)
- Notifications / email to reps

## Human prerequisites
- None to build. For the manual test: decide which real people will be reviewers and sales reps (names/emails) — create them later with the admin API or `make seed-demo-users` locally

## Design

### Roles (blueprint slide 7)
| Role | Review queue | Decide | Duplicates | My leads | Undo |
|---|---|---|---|---|---|
| `admin` | ✅ | ✅ | ✅ | all leads | any decision |
| `reviewer` | ✅ | ✅ | ✅ | all leads (read) | own decisions |
| `sales_rep` | ❌ | ❌ | ❌ | leads **assigned to them** | ❌ |
| `crm_manager` | read-only | ❌ | ❌ | all leads (read) | ❌ |
| `tech_admin` | read-only | ❌ | ❌ | ❌ | ❌ |
Enforced in the API; the UI hides what a role cannot do but never relies on hiding.

### Decisions (blueprint slide 41)
| Decision | Resulting `review_status` | Required input | Effect |
|---|---|---|---|
| Approve | `approved` | optional note, optional `assigned_to` (a `sales_rep`) | becomes a **qualified lead** |
| Reject | `rejected` | `reason_code` ∈ `evidence_wrong`, `business_closed`, `wrong_industry`, `ai_mistake`, `other` (+ note if `other`) | removed from queue |
| Needs enrichment | `needs_enrichment` | note | stays visible under a filter; not a lead |
| Duplicate | `duplicate` | `duplicate_of` (another opportunity id for the same service) | removed from queue |
| Not a fit | `not_a_fit` | `reason_code` ∈ `too_small`, `too_large`, `outside_area`, `already_client`, `other` (+ note if `other`) | removed from queue |
| Do not contact | `do_not_contact` on **every** opportunity of the business | note (required), confirmation in UI | business added to `suppressions`; no new pending opportunities ever |

### Backend changes

**Module:** `backend/app/modules/review/` (package exists, empty): `models.py`, `service.py`, `router.py`, `schemas.py`.
Suppression lives in `backend/app/modules/compliance/` (package exists): `models.py`, `service.py`.

**Migration `0006_review`**
- `review_decisions` — full history
  `id uuid pk`, `opportunity_id fk`, `decision enum`, `from_status`, `to_status`, `reason_code text null`, `note text null`,
  `duplicate_of uuid null`, `assigned_to fk users null`, `decided_by fk users`, `decided_at`, `undone_at null`, `undone_by fk null`
- `opportunities`: add `decided_at null`, `decided_by fk null`, `lock_version int default 0`
- `suppressions`
  `id uuid pk`, `business_id fk null`, `domain text null`, `phone_e164 text null`, `reason text`, `source enum[review, admin]`,
  `created_by fk users`, `created_at`, `lifted_at null`, `lifted_by null`
  Index on `domain`, `phone_e164`, `business_id` (active rows only)

**Service rules**
- Only `pending` or `needs_enrichment` opportunities can be decided. Requests carry `lock_version`; a mismatch → **409 Conflict** ("someone else already decided this") — test with two reviewers
- Every decision writes `review_decisions` + an `audit_logs` row
- **Undo:** within `REVIEW_UNDO_WINDOW_MINUTES=30`, the deciding reviewer (or any admin) can undo → previous status restored, history row marked `undone_at`. Undoing a do-not-contact lifts the suppression row
- **Batch:** `POST /opportunities/review-batch` accepts ≤ 50 ids, **only** for `reject`, `not_a_fit`, `duplicate` is not allowed in batch (needs `duplicate_of`). Approvals and do-not-contact are always one at a time — a human signs off each lead
- **Suppression is checked everywhere it matters:** classification (v0.5.0) must not create pending opportunities for a suppressed business, domain or phone; the review queue excludes suppressed businesses; an approved-then-suppressed lead is hidden from My leads. Add these checks to the existing classification service
- **Re-classification cool-down:** if an opportunity for the same business+service was rejected / not_a_fit / duplicate within `REVIEW_COOLDOWN_DAYS=90`, classification must not re-create it as pending (it may update evidence on the decided row only if nothing was approved). Approved rows are never overwritten by classification
- `assigned_to` must be an active user with role `sales_rep` (422 otherwise)

**Endpoints (under `/api/v1`)**
- `GET /review-queue` — businesses with ≥ 1 pending opportunity, not suppressed, sorted by highest pending score. Params: `service`, `city`, `state`, `industry`, `min_score`, `include_weak` (default **false** → hides opportunities with confidence < `REVIEW_WEAK_CONFIDENCE=0.4`; a business whose only pending items are weak is hidden too), `status` (`pending` default | `needs_enrichment`), `q`, cursor pagination. Each item: business id, display name, **city + state**, industry, website, latest audit status + top 3 finding codes, pending opportunities (id, service, confidence, score, source, `lock_version`), count of weak items hidden
- `GET /review-queue/{business_id}` — everything a reviewer needs in one call: business facts with field provenance, latest audit (findings with evidence), PSI, AI summary (flagged `ai_generated: true`), all opportunities (any status) with evidence, score components, AI provenance, decision history
- `POST /opportunities/{id}/review` — body: `decision`, `lock_version`, and the required fields per decision. Returns the updated opportunity
- `POST /opportunities/review-batch` — `{ids, decision, reason_code, note}` for reject/not_a_fit; returns per-id result (ok / conflict / not_allowed)
- `POST /review-decisions/{id}/undo`
- `GET /leads` — approved, not suppressed opportunities. `sales_rep` sees only `assigned_to = me`; others see all. Filters `service`, `assigned_to`, `city`. Item: business name, city, service, score, reason, approved by/at, public business phone + website (business-level only)
- `GET /users?role=sales_rep` for the assignment picker (admin, reviewer)
- `GET /suppressions`, `POST /suppressions` (admin: add by domain/phone/business), `POST /suppressions/{id}/lift` (admin)

**Dev helper:** `make seed-demo-users` (development only) creates `reviewer@example.com` (reviewer), `rep1@example.com`, `rep2@example.com` (sales_rep), `crm@example.com` (crm_manager) with passwords from `DEMO_USERS_PASSWORD` in `.env`. Refuses to run outside local/development.

### Frontend (Next.js App Router, TypeScript, Tailwind)

**API client:** generate TypeScript types from the backend's `openapi.json` with `openapi-typescript` (dev dependency) into `frontend/src/lib/api-types.ts`; `make api-types` regenerates it; `make check` fails if the committed file is out of date. All requests go through one `api.ts` wrapper that attaches the in-memory access token, retries **once** after `POST /auth/refresh` on 401, and redirects to login if refresh fails. `credentials: "include"` for the refresh cookie.

**Decision UX**
- Approve: optional note + optional rep picker. Reject / Not a fit: reason dropdown (+ note when "other"). Duplicate: pick another opportunity of the same service from a search box. Needs enrichment: note
- After a decision: toast with **Undo** (calls the undo endpoint) and move to the next business automatically
- 409 conflict → message "Another reviewer already decided this" and refresh the detail
- Keyboard shortcuts on the detail page: `j`/`k` next/previous business, `a` approve focused opportunity, `r` reject (opens reason), `?` shows shortcuts. Shortcuts never fire while typing in an input

**Safety rules in the UI (tested)**
- Page text, evidence and AI output are rendered as **plain text** only — never `dangerouslySetInnerHTML`
- External links (website, evidence URLs) only for `http:`/`https:` URLs, with `target="_blank" rel="noopener noreferrer"`; anything else is shown as text
- AI-generated fields always carry the "AI-generated — verify" label
- No phone number or email is shown other than the business-level public fields already stored

**Look:** clean internal-tool style using the blueprint palette (navy `#0f1f3a` headers, teal `#2dd4bf` accents), readable tables, visible focus rings, labels on all inputs. Desktop first, usable down to 1024 px.

## Acceptance criteria
- [ ] A reviewer can approve, reject (with reason), mark needs-enrichment, duplicate (with target), not-a-fit (with reason) and do-not-contact from the UI, and each writes a history row + audit log
- [ ] Nothing can be approved in batch; batch only accepts reject / not_a_fit, max 50
- [ ] Two reviewers deciding the same opportunity: the second gets 409 and the UI says so
- [ ] Undo restores the previous status within 30 minutes and is refused after; do-not-contact undo lifts the suppression
- [ ] After do-not-contact, the business disappears from the queue and leads, and re-running classification creates **no** pending opportunity for it (test)
- [ ] A rejected opportunity is not re-created as pending by re-classification within 90 days; an approved one is never overwritten (tests)
- [ ] The queue hides confidence < 0.4 by default, shows a hidden-weak count, and the toggle reveals them
- [ ] Every queue row and lead row shows city and state next to the business name
- [ ] A sales rep sees only leads assigned to them and gets 403 on review endpoints
- [ ] AI summary and AI-only opportunities are visibly labelled "AI-generated — verify before use"
- [ ] Evidence containing `<script>` renders as text; a `javascript:` URL is never rendered as a link (tests)
- [ ] The generated API types match the backend (`make check` fails on drift)
- [ ] `make e2e` passes against the demo stack (run by a human before merge)
- [ ] `alembic upgrade head` / `downgrade -1` succeed; no test makes a live network call; `make check` passes
