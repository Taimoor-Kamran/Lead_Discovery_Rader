# v0.12.0 — Finish the sentence

Status: draft
Branch: `spec/v0.12.0-finish-the-sentence`
Previous: v0.11.1 (safety pass), merged and tagged.
Input: `specs/audit-2026-09-25.md` — a line-cited audit of what the checks actually do.

## Goal

The client's verdict on two verified leads was "accurate but shallow". The audit shows why,
and it is not what either of us assumed. The audit does not lack checks. Ten of its checks
collect rich data and then emit a binary.

- `title_length` is stored. `missing_title` fires only when there is no title at all, so
  Ultimate Plumber's `Home | Business` passes clean (checks.py:262–267, findings.py:410).
- The viewport tag's full content string is stored. Only a missing tag is flagged, so
  `user-scalable=no` is never seen (checks.py:257–261, findings.py:408).
- Nine social platforms and their first href are stored. Nothing reads them
  (checks.py:412–431).
- The `<meta name="generator">` string, version and all, is stored. **No rule anywhere reads
  `tech_stack`** (checks.py:472–493).
- `builder_subdomain` fires only on a builder *subdomain*. Ultimate Plumber is Wix on its own
  domain and emits nothing (findings.py:374–382).
- LCP, CLS and TBT are collected and appear only inside another finding's evidence string
  (psi.py:110–113, findings.py:566–580).

Two of these are not shallow. They are wrong, in a document a rep reads out loud to a
prospect. A site carrying LocalBusiness as microdata is told it has none. A site whose JSON-LD
has a trailing comma is told the same, and the parse error is swallowed. `© 2018-2035` is
reported as a stale 2018.

This spec makes the checks finish their sentences. Almost every item works on data the audit
already has in hand, so the depth is close to free — and nothing here makes an outbound
request to anything other than the prospect's own homepage.

Budget: about five and a half days.

## Scope

### Part one — findings that are currently wrong

#### 1. Structured data must stop collapsing four states into one

`_structured_data` (checks.py:434–453) answers exactly one question: does some JSON-LD node
carry a LocalBusiness-family `@type`. Four materially different pages all return `False` and
receive the same low-severity `no_structured_data`:

| The page carries | Today | Should be |
|---|---|---|
| No structured data at all | `no_structured_data` | unchanged |
| Only `Organization` or `WebSite` | `no_structured_data` | a distinct finding — schema exists but not the local one |
| LocalBusiness JSON-LD that fails to parse | `no_structured_data` | a distinct finding — **broken markup**, higher severity |
| LocalBusiness as **microdata** (`itemtype`) | `no_structured_data` | **no finding** — the business has it |

The microdata case is a false statement about the prospect. The invalid-JSON case is silently
swallowed by `except (ValueError, TypeError): continue`, and it is the most sellable of the
four — "your structured data is there but broken" beats "you have none".

- Read microdata (`itemtype` / `itemscope`) as well as JSON-LD.
- Report a parse failure as its own finding, with the offending block as evidence. Do not
  swallow it.
- Distinguish "schema present, but no LocalBusiness" from "no schema".
- **Extract the fields** once a LocalBusiness node is found: `name`, `address`, `telephone`,
  `sameAs`, `openingHours`. Store them. Item 8 consumes them.
- Normalise the stored `@type` — today it keeps the raw string, so
  `https://schema.org/Plumber` and `Plumber` are different values.

#### 2. The copyright check discards the years that matter

`_copyright_year` (checks.py:509) keeps only years up to the current one. Two consequences,
both confirmed by running the function:

- **`© 2035` produces nothing.** The future year is discarded, the page then reads as having
  no copyright notice at all, and no finding fires. This is the exact string the client used
  as their headline example of what we miss.
- **`© 2018-2035` is reported as a stale 2018.** The range's later year is rejected, and the
  single-year pattern then picks up the earlier one.

- A year in the future is a finding in its own right — a template placeholder, not a stale
  site. It is more sellable than a stale year because it is visibly absurd.
- Parse ranges. `© 2018-2026` on a site in 2026 is current, not stale.
- Keep `stale_copyright` as it is for genuinely old years.

#### 3. Service mapping exists twice and the two disagree

A finding carries `service_category`, and `opportunities/catalogue.py` holds a separate
finding-to-service table. The audit found cases where they disagree. Every opportunity the
client sees is filed under one of these, and F1 in their queue brief ranks by service value —
so this has to be one source of truth before anything is built on top of it.

- Pick one as authoritative, derive the other from it, and delete the duplicate.
- Add a test that fails if any finding code maps to two different services.
- Report which findings were mis-filed and how many opportunities in the production database
  change service as a result.

#### 3a. A network outage on our side is not the prospect's site being down

*(Added by the human before the build started, on 2026-09-26.)*

A homepage that failed to load because the machine running the audit slept (Windows Modern
Standby drops the network; found during v0.11.2, walkthrough note 13) is recorded today as
the site being `unreachable` — a high-severity finding a rep would read out to the prospect.
It is a false statement about them, which is exactly what Part one is for.

- Distinguish "we could not reach the network" from "the site did not respond".
- Re-verify before recording `unreachable`: a site is only called unreachable after a
  second attempt also fails while our own connectivity is confirmed.
- An audit that failed because our own network was down is recorded as ours (`failed`),
  produces no finding, and is retried on the short failed-audit schedule.

#### 3b. A bot-challenge page is not the business's homepage

*(Added by the human after the production canary, on 2026-09-28.)*

In the canary on Plumbing in Austin, four businesses (AAA Auger, Mr. Rooter, Fox Service,
Rooter-Man) answered HTTP 403 with a Cloudflare bot-check page ("Just a moment...",
"Attention Required! | Cloudflare"), and the audit read that page as the homepage. Every
finding those four carry — the new ones and the ones from before this spec — describes
Cloudflare's page, not the business's site.

- A bot-challenge page is its own audit outcome: not `done`, not `unreachable`.
- It produces **no findings at all**, and nothing downstream turns it into an opportunity.
- It has a distinct status a reviewer can see, and its own retry schedule.

### Part two — data collected but never judged

Each of these is a rule over a value the audit already stores. No new fetching.

#### 4. Evaluate the page title

`title` and `title_length` are both stored and neither is evaluated.

- Default and template titles: `Home | Business`, `Home`, `Untitled`, `Site`, and the common
  builder defaults. Treat "title contains no word from the business name" as the general case
  rather than maintaining a blocklist alone.
- Too short (under ~20 characters) and too long (over ~60, truncated in results).
- Evidence is the literal title string. The screenshot writes itself.

#### 5. Parse the viewport content

The full content string is stored. Flag `user-scalable=no` and `maximum-scale` below 1.5 —
ATX's zoom restriction, and an accessibility issue as well as a mobile one.

#### 6. A builder on the business's own domain

`builder_subdomain` covers `something.wixsite.com`. It misses the far more common case: a
Wix, Squarespace, GoDaddy or Duda site on the business's own domain, which is what Ultimate
Plumber is. The platform label is already detected (fingerprints.py:140–158).

- Emit a finding for the detected builder regardless of domain, at a lower severity than the
  subdomain case. It maps to `website_design`.
- Nothing in the codebase currently reads `tech_stack`. Wire it into the rules.

#### 7. More than one H1

`h1_present` is a bool, but every heading level is already in `heading_structure.levels`.
Multiple H1s is a real SEO finding and the data is sitting there.

#### 8. Placeholder contact details, and a name/phone diff

The audit detects *that* a mailto exists but not *what* it points at, and never compares
what the site says against the Places record.

- Store the mailto address, not just its presence. Flag placeholder domains:
  `mysite.com`, `example.com`, `yourdomain`, `email.com`, `domain.com`. Ultimate Plumber's
  `info@mysite.com` means every emailed enquiry is lost — the single most sellable finding in
  either verification report.
- Flag placeholder footer text: `Business Name`, `Your Company`, `Company Name`, `Lorem ipsum`.
- Compare the site's `tel:` link against the Places `nationalPhoneNumber`, and the
  LocalBusiness `address` from item 1 against the Places address. A mismatch is a NAP finding
  — this is ATX's Suite #11 vs Ste 303.
- Compare the site's canonical URL against the Places `websiteUri`. Flag a stale `http://`
  or a non-www/www mismatch in the listing.

Normalise both sides before comparing, and reuse the existing normalisation rather than
writing a second one. A false NAP finding is worse than no NAP finding: say in the notes how
you avoided one.

#### 9. Click-to-call on its own

`no_contact_on_homepage` fires only when `tel:`, `mailto:` and a contact form are *all*
missing (findings.py:419). A site with a form and no phone link — normal on a builder
template, and a real loss for a home-services business — gets nothing. Emit a finding for a
missing `tel:` link independently.

### Part three — structural

#### 10. `method` on every finding

The finding model has `code`, `severity`, `service_category`, `message`, `evidence_text`,
`evidence_url`. Add `method`: `deterministic` | `api` | `ai`. Every check already knows which
it is. The client's brief asks for it, the queue needs it to show an AI finding differently
from a measured one, and it is the precondition for their F8 trust work.

#### 11. Re-audit when the check logic changes, not when the audit ages

Everything above changes what a check concludes about a page. Existing audits are now wrong,
and `needs_audit` treats any successful audit inside `AUDIT_MAX_AGE_DAYS` as fresh — so
without this, the client sees none of the new findings for thirty days.

- Add an `audit_logic_version` constant, stored on each audit.
- A business whose latest audit carries an older logic version is due immediately, regardless
  of age.
- Bump it in this spec, and document bumping it as part of shipping any check change.

This pays for itself on every spec after this one.

## Out of scope

- **Crawling beyond the homepage** (M1). It multiplies audit time by roughly ten and forces
  audit concurrency and tiering with it. Its own spec.
- **Response headers and the security family** (M6). The fetch result keeps no response
  headers, which is what makes mixed content, HSTS and security headers impossible. Retaining
  them is small; the checks on top of them are not. Next spec.
- **Social link validation.** The hrefs are stored and Ultimate Plumber's broken Facebook link
  is real, but checking it means an outbound request to a social platform. The project's
  constraint bars social scraping; the client's own brief allows "validating that the link
  resolves, nothing deeper". A `HEAD` that reads no content probably clears both. It needs a
  written decision and respx fixtures, not a quiet inclusion here.
- **Per-metric Core Web Vitals findings.** LCP, CLS and TBT deserve their own thresholds
  rather than living in another finding's evidence text, and INP is absent. Next spec.
- **Generator version parsing** ("outdated WordPress"). Cheap, but it needs a version
  database to be worth anything.
- **DNS, WHOIS/RDAP, SPF/DMARC** (M8). A whole axis, and a good one. Its own spec.
- **`dollar_band` and value ranking** (F1). Blocked on the client's price list.
- The two dead checks, `ecommerce` (checks.py:398–409) and `favicon` (checks.py:278–284),
  which collect data no rule reads. Decide in this spec whether to emit or delete them; do not
  build on them.

## Implementation notes

_(append only)_

**Why this order.** Part one is three findings that state something false about a prospect.
Depth on top of a wrong answer makes the wrong answer louder. Part two is where the value is
and it is nearly free — the data is already collected on every audit today and thrown away.
Part three is the plumbing that makes the next spec possible and stops this one from being
invisible for thirty days.

**On false positives.** Items 8 and 1 both compare the site against the Places record. Every
comparison is a chance to accuse a prospect of something untrue, in front of a rep who will
repeat it. Normalise hard, prefer `unknown` to a guess, and where a comparison is uncertain
say so in the evidence rather than raising a finding.

**Nothing here fetches anything new.** Every item works on the prospect's own homepage, which
is already fetched once per audit, or on the Places record already in hand. No new API calls,
no new cost, no new rate limit. That is deliberate — it keeps the spec's risk in the logic,
where tests can catch it.

**Build log (2026-09-26, Claude).** Everything below was decided during the build; the
human's own notes above are unchanged.

*Starting the branch.* `scripts/spec-start.sh` hung on `git pull --ff-only origin main`
(the fetch never returned). It was stopped and its remaining local steps were done by hand:
branch `spec/v0.12.0-finish-the-sentence` from `main` at `cb17ed0`, active spec set, the
stop counter cleared. Nothing was pushed.

*Item 3a was added by the human before the build* (their message of 2026-09-26: "One
addition to Part one … distinguish 'we couldn't reach the network' from 'the site didn't
respond', and re-verify before recording unreachable"). It is written into Scope with its
own tasks and acceptance criteria, marked as the human's.

**3a — how an outage is told from a dead site.**
- Only a request that got *no answer* is doubted: error kinds `connect`, `timeout`,
  `network`, and an HTTP 5xx on the homepage. A certificate that does not verify, or a URL
  the SSRF guard refuses, is an answer, and is recorded as before without a re-check.
- Our own connectivity is asked with a TCP connection to `AUDIT_CONNECTIVITY_CHECK_URL`,
  default `https://www.googleapis.com/` — the PageSpeed host every audit already calls, so
  no new host appears (the outbound-host guard passes unchanged) and no HTTP request is
  sent (no quota, nothing read). DNS is part of the probe, which matters: the usual symptom
  of a slept laptop is the resolver failing.
- The order is: request fails → probe → if we are offline, stop: the audit is `failed`
  ("a fact about us", retried after `AUDIT_FAILED_RETRY_HOURS`) with the probe's answer in
  `checks.network_available` and **no finding**. If we are online, wait
  `AUDIT_UNREACHABLE_RECHECK_SECONDS` (10) and ask the site once more; a second failure is
  probed again, because the network can drop between the two attempts. Only a second
  failure with our network confirmed is `unreachable`, and its evidence now says
  "tried twice, 10 s apart, while our own connectivity check succeeded".
- The same applies to the robots.txt request, which is the one an outage usually hits first.
  A robots *timeout* with our network up still falls to the existing robots policy.
- A host answered by the fixture backend (demo data, tests) is neither probed nor re-checked:
  its failure is scripted, and probing would make an offline `make load-demo-data` record
  the demo's unreachable site as `failed`.
- Cost: a dead site now takes two probes (≤ 5 s each), 10 s and a second request (≤ 20 s)
  longer — at most about 60 s, and no PageSpeed call follows an unreachable site, so it
  stays inside `AUDIT_SECONDS_PER_BUSINESS` (150). The one path that can exceed it is a
  site whose robots.txt times out once and then answers, followed by a slow homepage and a
  slow PageSpeed answer; the run budget is per run, so such a business borrows from the
  others.

**Item 1 — structured data.** Microdata is read by `itemscope`/`itemtype`/`itemprop`,
including a nested `PostalAddress`; RDFa (`typeof`/`property`) is read the same way, since
it is the third syntax Google accepts and leaving it out would keep one false "none". A
block is called broken only after the wrappers CMSes add are forgiven — a byte-order mark,
an HTML comment, `CDATA` markers, a raw newline inside a string (`strict=False`) — because
search engines forgive them too. When a block is broken, neither `no_structured_data` nor
`no_local_business_schema` is also reported: the business has tried, and "none" would be
the false statement item 1 exists to remove. `LOCAL_BUSINESS_TYPES` was widened from 41
types to schema.org's whole LocalBusiness subtree: once "schema, but not LocalBusiness"
became a finding, a real subtype missing from the list (`HardwareStore`, `AutoDealer`,
`Notary`…) would have been a false finding.

**Item 2 — copyright.** A future year is believed only when it sits directly after the mark
(`© 2035`, `Copyright © 2018-2035`) and at most 30 years ahead. The older, looser pattern
allows 40 characters between the mark and the year, and in "© Acme Plumbing, 2100 Lamar
Blvd" that is a street number (fixture `copyright_street_number.html`). Severity: `medium`,
one above `stale_copyright`, because the spec calls it the more visibly broken of the two.

**Item 3 — which mapping is authoritative, and what was mis-filed.** The finding catalogue
(`audit_web/findings.py`) is now the one mapping: each entry names its `Service`, and
`opportunities/catalogue.py` derives `ServiceSpec.finding_codes` from it. The *values* were
taken from the old `SERVICES` table, not from `service_category`, because `SERVICES` is
what every opportunity was filed through; `service_category` was written on every finding
and read by nothing (no rule, no AI input, no CRM payload, no frontend code). The finding's
field is now `service`, holding the opportunity service key.
- Mis-filed under the old `service_category` (5 of 26 codes): `no_website` and
  `social_profile_only` (`web_presence`), `no_https` and `tls_invalid` (`security`), and
  `slow_mobile` (`performance`) — each sold as `website_design`. `ServiceCategory.ecommerce`
  had no finding at all. The other 21 agreed.
- **Opportunities in production that change service: 0, by construction.** Opportunities
  were only ever filed through `SERVICES`, and no pre-v0.12.0 code changed service —
  pinned by `tests/unit/test_service_mapping.py::test_no_pre_v012_finding_changed_service`.
  This could not be counted against the production database from this session (reads of
  production data are refused here), and it does not need to be: nothing that decides an
  opportunity's service read the field that disagreed. Old audit rows keep their
  `service_category` key in the stored JSON until they are re-audited; nothing reads it.

**Item 4 — title.** `default_title` fires when every segment of the title is a template
word ("Home | Business", "Welcome", "My WordPress Site") **or** the title shares no word with
the business name. The name match is deliberately lenient, since a "no" becomes a finding:
words are normalised as entity resolution normalises names, generic words ("services",
"company") are ignored, a shared start of five letters counts ("Electric"/"Electrical",
"Plumber"/"Plumbing"), and a name run together counts ("UltimatePlumber.com"). A name with
no identifying word leaves only the template list. `short_title` is not also reported when
the title is already a template one. The title is the finding's evidence, not its message
(see *messages* below).

**Item 5 — viewport.** Threshold 1.5 as the spec says (Lighthouse's own audit uses 5; 1.5 is
the more conservative line, so fewer findings). A non-numeric `maximum-scale` is not read as
a number. The wording says the tag *asks* phones not to zoom, which is exactly what it does —
some browsers ignore it.

**Item 6 — builder.** `site_builder` (low, `website_design`) needs strong evidence: a
generator tag naming the builder, or one of the builder's own asset hosts
(`static.wixstatic.com`, `static1.squarespace.com`, `img1.wsimg.com/isteam`,
`irp.cdn-website.com`, `editmysite.com`…). The looser `TECH_SIGNATURES` match `wix.com`
anywhere, so a WordPress post linking to Wix would otherwise be "built with Wix" (fixture
`builder_link_only.html`). Covered: Wix, Squarespace, GoDaddy Website Builder, Duda, Weebly.
Webflow is left out: it is a professional tool, and "built with Webflow" does not say what
"built with Wix" says. Not reported alongside `builder_subdomain`.

**Item 7.** `h1_count` counts h1s with text, as `h1_present` always has.

**Item 8 — how the name/phone/address comparisons avoid false positives** (the human asked
for this reasoning). A false NAP finding is worse than none, so each comparison is a check
of its own (`checks.listing_comparison`) that answers `match`, `mismatch` or `not_compared`
*with the reason*, and only `mismatch` becomes a finding. The reasons are visible to a
reviewer in the audit's checks.
1. *One normaliser on both sides.* Phones go through `normalization.phones.to_e164` with
   the listing's country; streets through `normalization.addresses.street_key`; websites
   through `normalization.web` — the code that already decides whether two records are one
   business. No second normaliser was written.
2. *Only two known values can conflict.* No listing phone, no `tel:` link, a `tel:` that
   does not parse (`tel:CALL-NOW`), no LocalBusiness address, no street number on either
   side, a PO box, or a listing website on a different domain → `not_compared`.
3. *Any agreement is agreement.* Of up to three `tel:` numbers, one matching the listing is
   a match — a second, call-tracking number beside the listed one is not a disagreement.
4. *Addresses are compared by numbers, not spellings.* Street number, unit and ZIP are
   compared exactly; street **names** never are ("US-290" and "Hwy 290" are one road, and no
   normaliser we have can prove it). Unit designators are unified ("Suite #11", "Ste 11",
   "#11"). A unit on one side only is not a conflict. "Fl"/"Floor" is not read as a unit
   designator, because "Miami, FL 33101" would read as unit 33101; a one-line address takes
   its ZIP from after the first comma, because the first five digits of
   "12345 Research Blvd" are the street number.
5. *A site describing several locations is not compared* — its second node is a branch,
   not a disagreement.
6. *The finding says the two differ, never which is wrong.* A tracking number is a real
   difference and worth knowing; the wording claims nothing more.
7. *Matched pairs in the tests*: every comparison is tested against an agreeing and a
   disagreeing listing, so a comparison that fires on agreement fails the build.
- Placeholder email domains: `example.*`, `mysite.*`, `yourdomain.*`, `yoursite.*`,
  `domain.com`, `company.com`, `website.com` and similar. `email.com` is a real free-mail
  provider, so there an address is a placeholder only when its local part is one a
  template prints (`info@`, `your@`, `name@` …); `jane.doe@email.com` is a person.
- Placeholder footer text is looked for only in the footer (a `<footer>`, a
  `role="contentinfo"` element, an element whose id/class says footer, minus any form
  controls and labels in it) and on the copyright line, because "Company Name" is an
  ordinary field label in a quote form. "Lorem ipsum" counts anywhere. A phrase that is part
  of the business's own name ("Your Company Store") is not reported.
- The tel: numbers (at most three) and one mailto address are stored as check values. Both
  are the business's own published contact points, which the blueprint allows, and the
  mailto was already stored verbatim in the old check's evidence.
- Travis Heights in the demo data gained `nap_phone_mismatch`: its listing says
  (512) 555-0203 and its page dials 555-0202. The fixture really does disagree; the finding
  is kept as a demo NAP case.

**Messages carry no page text or contact detail.** Found by the existing AI-privacy test:
finding messages go into the AI input as they are, and only evidence is scrubbed. So the
title, phone numbers and the placeholder address are the evidence of their findings, and the
placeholder-email message names only the domain (`mysite.com`). A new test fails any
wording template that takes a field outside a fixed safe list.

**Item 9.** `no_click_to_call` is reported whenever there is no `tel:` link *and* the page
offers some other contact route. When there is none at all, `no_contact_on_homepage` already
says "no phone link", and reporting both would double-count one gap in the confidence
combination.

**Item 10 — method.** A property of the catalogue entry. `api`: `slow_mobile`,
`low_accessibility_score`, `low_best_practices_score` (PageSpeed measured them) and
`few_reviews` (the listing reported the count). Everything else is `deterministic`,
including the listing comparisons — the listing's value came from an API, but the finding
is our own comparison. No audit finding is `ai`; the value exists for the queue work. The
frontend does not display `method` yet; the spec asks for it on the model.

**Item 11 — logic version.** `AUDIT_LOGIC_VERSION = 4` in `audit_web/models.py`, stored in
the new integer column `website_audits.audit_logic_version` (migration `0011`; existing
rows backfilled from `rules_version`'s `audit-N`, anything else 0 and therefore due).
`rules_version` is kept and is now derived (`audit-4`), so nothing that displays it changes.
An integer because "older" must be a comparison: `"audit-10" < "audit-9"` as text.
`needs_audit` checks it before age or status, so a `failed`, `unreachable` or `skipped`
audit by older logic is due too. "Due on the next run" means the next audit run that
considers the business. *(Corrected after the build.)* There are two ways to get one:
  - **Re-run a saved search.** This spends Places API calls: the run starts with discovery,
    which queries Places again, and only then audits the businesses that search finds.
  - **`POST /api/v1/jobs/{job_run_id}/audit`** with the id of an existing *resolution* run
    (`tech_admin` or `admin`). It audits the businesses that resolution run linked, skipping
    permanently closed ones and anything `needs_audit` calls fresh, and makes no Places call.
    It still fetches each homepage, calls PageSpeed, and — because a finished audit run
    queues classification — calls the AI wherever the new findings changed its input. Send
    an `Idempotency-Key` header, or each call starts a new run.
  Nothing re-audits every business in the database at once: covering the whole set means
  one call per search's latest resolution run. **Neither audit endpoint (this one, or
  `POST /api/v1/businesses/{id}/audit` for one business) has any UI today; both are
  API-only.** That gap deserves its own spec later; it is not part of this one. Bumping is documented in CLAUDE.md's definition of done, in the
constant's comment, and in `docs/operations.md` → *Upgrading*.

**The two dead checks — deleted, not emitted** (the human asked for this judgement).
- `favicon` read only `<link rel="icon">`. Browsers request `/favicon.ico` whether or not the
  tag exists, and most sites answer it, so "no favicon" would be false for many sites, and
  the only way to check is a second request, which this spec rules out. It cannot be made
  true, so it cannot be emitted; and data no rule reads is what this spec removes.
- `ecommerce` detected a shop platform or a cart link. A shop is not a gap in any service
  the agency sells: no `ServiceSpec` would take it, and "has no shop" is not a finding for a
  plumber. Shopify still shows in `tech_stack.platforms` via `TECH_SIGNATURES`, so the
  context a reviewer sees is unchanged. `ECOMMERCE_SIGNATURES` and `CART_LINK_PATTERNS` went
  with it. Old audits keep both values in their stored JSON.

**Demo data.** `messyformat-demo.com` linked `office@example.invalid`, a stand-in for a real
address that the new rule rightly reads as a placeholder (`example.*`); the fixture now uses
`office@messyformat-demo.invalid`. New demo findings, each checked against its page:
