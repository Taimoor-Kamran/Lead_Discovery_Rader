# v0.10.0 — Provenance on the page, recency filtering, rules-only MVP

Status: draft
Branch: `spec/v0.10.0-provenance`
Previous: v0.9.0 (design pass + seven production bugs), merged.

## Goal

A reviewer looking at a lead can answer, in one sentence and without opening a
developer table, the question a prospect will actually ask: **"where did you get my
details?"** They can also narrow the queue to what was found recently, and the MVP
runs and sells without the AI layer switched on.

Nothing about what the system fetches changes. This spec is about surfacing what is
already stored, adding one filter, and making rules-only a first-class mode rather
than a fallback.

## Scope

### 1. Source attribution, said in plain words

Provenance has been mandatory since v0.3.0 — every stored fact already carries
`source`, `source_url`, `source_record_id` and `discovered_at`. It is currently
visible only as an 18-row "field provenance" disclosure aimed at a developer. This
spec turns it into a sentence a salesperson can read aloud.

- A **"Where this came from"** block on the review detail page and the lead detail
  page, showing:
  - the **source name** in human words (*Google Places*), not the code
    (`google_places`), with the raw code in the element's tooltip, consistent with
    the v0.9.0 labels rule;
  - a **link to the source record** (`source_url`) where one exists, opening in a
    new tab with `rel="noopener noreferrer"`, `http(s)` only;
  - **when it was found** (`discovered_at`), and when it was last seen again, in the
    same date format the rest of the app uses;
  - where a business was built from **more than one discovered record**, one line per
    source rather than only the survivorship winner.
- A **source column** on the review queue and the leads list, showing the source name
  compactly. Sortable is not required.
- **`lib/labels.ts` gains source labels** for every row in the `sources` table:
  `google_places`, `pagespeed_insights`, `openai`, `airtable`, `demo_fixture`. A
  guard test fails if a registered source has no label, so adding a source later
  cannot silently ship a raw code to the screen.
- **Social profiles linked from the business's own homepage**, which the v0.4.0 audit
  already collects, shown under a heading that says exactly what they are — e.g.
  *"Linked from their website"* — with each platform named and linked. This is
  presented as *what their site links to*, never as a source the system read.

### 2. Recency filter

- A **"Found within"** filter on the review queue and the leads list:
  **24 hours · 3 days · 7 days · 30 days · Any time**, defaulting to Any time.
  (24 hours and "1 day" are the same window; only one is offered.)
- Backed by a `discovered_within_days` (or equivalent) query parameter on
  `GET /review-queue` and `GET /leads`, filtering on the business's earliest
  `discovered_at`, with the semantics written down in the endpoint's docstring —
  "first found within N days", not "last seen".
- The filter composes with the existing `service`, `city`, `state`, `industry`,
  `min_score`, `q` and `status` filters, and survives pagination.

### 3. Rules-only mode as a supported configuration

The deterministic rules have run under every provider since v0.5.0, including
`disabled`. What is missing is that the UI still reserves space for an AI that is
not there.

- `AI_PROVIDER=disabled` is **accepted in production** by `app/core/startup.py`
  (it currently refuses `fake`; `disabled` must be explicitly allowed and covered by
  a test, so nobody later "tidies" it into the refusal list).
- With AI disabled the UI shows **no empty AI furniture**: no AI summary box, no AI
  rationale line, no AI provenance disclosure, and the opportunity source badge reads
  **Rules** rather than *Rules + AI*.
- `/admin/health` and the search **cost estimate** show AI as off rather than
  estimating zero calls against a budget that is not in use.
- No AI code is deleted. This is a switch, not a removal.

### 4. Carried over from v0.9.0

- **`buying_intent` renders as a raw code** (`none_detected`) on the review detail
  page, breaking v0.9.0's own "codes are read, not shown" rule. Add it to
  `lib/labels.ts` — *None detected* — with the code in the tooltip. Note this becomes
  invisible with AI disabled, and must still be fixed for when it is on.
- **Unknowns** on the AI summary block is a semicolon-joined run-on; render as a list.
- The **v0.9.0 manual test plan steps 2–6** were not walked before that spec was
  merged. They are inherited here and must be completed against this release.

## Out of scope

- **Any new data source.** No Meta/Facebook, LinkedIn, X, TikTok, Reddit or other
  social-media reading, in any form, including "just the public page". No scraping of
  Google Ads Transparency or any ad library. The blueprint's permitted-sources rule
  stands: official APIs, plus the business's own homepage within robots.txt.
- Any change to what is fetched, stored, or retained.
- Any change to the audit checks, the findings catalogue, the rules, the scoring
  weights or the review decision model.
- Removing or rewriting the AI module.
- A PDF export. The existing print stylesheet stays as it is.

## Implementation notes

_(append only — do not edit the sections above)_

**On "source" as the client asks about it.** The question this spec answers is a
sales question: a prospect asks where their details came from and the reviewer needs
a defensible answer on screen. Today there is exactly one answer — the Google Places
listing — and that is the whole truth. The value of building the display properly now
is that the `sources` table, the adapter registry and the provenance columns already
support more than one source, so a second permitted source shows up correctly without
another UI pass.

**Why social profiles are presented the way they are.** A prospect who sees
"Facebook" on their lead record will reasonably ask whether their Facebook page was
read. The answer must be no, and the wording on the page has to make that obvious
before anyone asks. These are links the business published on their own homepage,
recorded by the audit that already runs there.

**Where the source's human name comes from.** The task asks the API for `name` *and* `code`
per entry, while v0.9.0's labels rule puts the wording in `lib/labels.ts`. Both are shipped and
the screen prefers its own: `code` is `sources.name` (`google_places`), `name` is the
operator-facing `display_name` already stored on the source row (*Google Places API (New)*),
and the page renders `sourceNameLabel(code)` — *Google Places* — with `code` in the tooltip.
The API's `name` is what a consumer that is not this web app would read. The guard test lives
in the backend (`tests/unit/test_label_coverage.py`) because the backend is the only place that
knows which sources are registered.

**Linked profiles are read out of the audit's stored evidence, not re-fetched.** The
`social_links` check stores the platform keys as its value and `"key: href; key: href"` as its
evidence, clipped to 300 characters. Changing that shape would be a change to what is stored,
which is out of scope, so the block parses what is there: the keys are authoritative, and an
href is only offered when it parsed out of evidence that was not cut mid-URL. A platform whose
link cannot be recovered is named with `url = null` — a truncated href would be a working link
to somewhere we never saw.

**"First found" is the earliest record, and a business with no record is in no window.**
`discovered_within_days` filters on `min(discovered_records.first_discovered_at)` per business,
so a record the source handed over again this morning does not make a business discovered last
year look new. The join drops a business with no discovered record at all: "first found within
N days" cannot be true of something that was never found. Both are tested.

**The source badge keeps stating the recorded source, even with AI off.** The spec asks for
the badge to read *Rules* rather than *Rules + AI* when the provider is disabled. A rules-only
run records `source = rules`, so it does read *Rules* — that part needed no code. What this
build deliberately does **not** do is rewrite the badge on an opportunity stored as `rules+ai`
back when the model was on: that claim did come from rules + AI, and saying otherwise would be
inventing provenance, which the blueprint forbids outright. So with AI disabled the model's own
output is hidden everywhere (summary box, rationale line, details disclosure) while the badge
still says where the claim came from. Both cases are tested in
`frontend/src/test/ai-switch.test.tsx`.

**A missing `ai_enabled` means enabled.** The front end hides AI only on an explicit `false`.
A response that does not carry the flag must not hide what the model actually said.

**`.env.example` keeps `AI_PROVIDER` blank; `.env.prod.example` sets `disabled`.** The task
says to document `disabled` as the MVP default. `.env.example` is the *development* template
that `make env` copies and that the demo and `make e2e` run against, and those want the offline
`fake` provider so the AI parts of the screens have something to show — setting `disabled`
there would have turned `make e2e` red. So the default is set where it is actually the default
(the production template) and documented in both, with the reason written in `.env.example`.

**The label guard is a rule, in two halves.** Coverage is asserted in the backend (every
registered source, social platform and API enum has an entry in `lib/labels.ts`); the rule
itself is asserted against rendered pages in `frontend/src/test/labels.test.tsx` — every
snake_case value in the payload must stay out of the page's prose, and no single text node may
hold two values of the same multi-valued field, which catches `join("; ")`, `join(" · ")` and
any other separator alike. Both guards have tests proving they fail on the defect they exist
for.

**`buying_intent` was not the only code still reaching the screen.** The classification status
(`guardrail_trimmed`, `skipped_budget`, …) rendered raw in the AI details disclosure too. It is
labelled here rather than left for a later spec, since it is the same v0.9.0 rule and the new
guard fails on it.

**The outbound-host guard.** "No new outbound host appears anywhere in the codebase" is tested
by freezing the set of hosts the source names (`backend/tests/unit/test_outbound_hosts.py`),
with one line per host saying what it is, plus a standing assertion that no social-media host is
ever requested. Reserved TLDs, `localhost` and the demo fixtures' checked-in HTML are excluded:
they are fixture content and documentation names, not requests.

**One change on this branch is not from this spec.** `backend/tests/integration/test_backup.py`
(v0.8.0) seeded its "older" dumps from the wall clock but wrote the new dump at a hardcoded
`2026-09-21 02:00`. Retention sorts by the timestamp in the filename, so from 2026-09-23
onwards the file seeded "2 days ago" sorted above the new one and the test failed on a
machine where nothing had changed. It is fixed here — every stamp now derives from the same
`now` — because the definition of done requires `make check` to pass, and it is recorded in
`CHANGELOG.md` under v0.10.0 rather than left to look like part of this spec's work. I
checked the rest of the suite for the same shape: `test_crm_sync.py:681` already guards with
`max(T0, datetime.now(UTC))`, and every other mix of a fixed date and the real clock measures
staleness entirely against the real clock, so none of them can drift.

**The manual test plan was walked on 2026-09-23 by the repository owner**, who reported every
step passing. Steps 1–7 are done: the demo stack rebuild, the source line read aloud on a lead
from a real search, rules-only mode with `AI_PROVIDER=disabled`, every screen at 1280 px and
then 1024 px, a full review of one business on the keyboard alone, reduced motion with nothing
animating, and the lead page printing to one sheet. The recency filter was checked by hand too,
which is not one of the numbered steps. Step 8, client sign-off on the before/after
screenshots, is the one item still outstanding — it needs the client.

That pass answers the two things this branch had flagged for particular attention, and both
came back clean: the lead page still prints to a single A4 sheet with the "Where this came
from" block on it, and the source line does read correctly on live Google Places data, where
`source_url` is present and the record links (the demo fixture stores no URL, so only a real
search exercises that link).

It also settles the five steps inherited from v0.9.0. They were carried into this spec because
nobody had walked them before v0.9.0 merged; they have now been walked against this release, so
they are no longer outstanding and no longer inherited by anything after this.
