# v0.3.0 — Normalization + entity resolution

**Branch:** spec/v0.3.0-normalize-dedupe
**Depends on:** v0.2.0 (merged, tag `v0.2.0`)
**Estimate:** 3–5 working days
**Blueprint refs:** §2 Lead state model (slide 9, states 1→2), §5 businesses table (slides 25–27), §6 Normalization (slide 31), Entity resolution (slide 32), §3 Provenance (slide 16)

## Goal
Raw `discovered_records` become clean, deduplicated `businesses`. Every discovery run is followed
automatically by a resolution run that normalizes each record into one shape, matches it against
existing businesses, and either links it (high confidence), sends the pair to a human (mid confidence),
or creates a new business (low confidence). Every business field keeps a record of which source said what.

Also fixes two gaps found while testing v0.2.0: Swagger has no **Authorize** button, and there is no
way to reset a forgotten password.

## Scope
- Normalizers: name, phone (E.164), address, website/domain, industry taxonomy, business status, dates
- `businesses` table + field-level provenance (`business_field_values`)
- `match_candidates` table for mid-confidence pairs + reviewer decision endpoint
- Entity resolution: blocking → weighted scoring → auto-merge / review / keep apart
- `run_resolution` worker task, enqueued automatically when a discovery run finishes `done`
- Retention: Places-derived business fields follow the same expiry as their raw records
- Demo dataset + loader so all of this can be tested **without a Google API key**
- Read endpoints for businesses
- Fix: Swagger Authorize button (declare the bearer scheme)
- Fix: `reset-password` CLI command

## Out of scope
- Website fetching / audit (v0.4.0) — the `website` field is stored as given, not visited
- A second real source (the resolver must be source-agnostic, but only Places + demo exist)
- Multi-location modelling (`business_locations`): in the MVP one business = one physical location
- Un-merge of an already merged business (log it in Implementation notes as a future item)
- Any UI for the review queue (v0.6.0) — use API / Swagger
- Owner or personal contacts of any kind

## Human prerequisites
- None required to build and test (demo data covers it)
- Optional: once the client's Google key arrives, add it to `.env` with `PLACES_DAILY_CALL_CAP=30` and re-run the v0.2.0 live check (`make places-smoke`)
- Confirm with the client whether Places-derived business data (name, phone, address) must also be purged after `PLACES_CONTENT_TTL_DAYS`. This spec assumes **yes** (the conservative reading); flag it back if the client's legal review says otherwise

### Normalization rules (blueprint slide 31) — explicit nulls, never guess
| Field | Rule | Example |
|---|---|---|
| `display_name` | Trim, collapse whitespace, keep original casing | `ABC Plumbing, LLC.` → `ABC Plumbing, LLC.` |
| `normalized_name` | Lowercase, `&`→`and`, strip punctuation, strip legal suffixes (`llc, inc, incorporated, co, company, corp, corporation, ltd, pllc, lp, llp`), collapse spaces | → `abc plumbing` |
| `name_key` | Double-metaphone of `normalized_name` (jellyfish) for blocking | |
| `phone_e164` | `phonenumbers.parse(raw, region=country or "US")`; must be `is_valid_number`; else null | `(512) 555-0142` → `+15125550142` |
| Address | Prefer Places `addressComponents` (street_number, route, subpremise, locality, administrative_area_level_1, postal_code, country). Fall back to parsing `formattedAddress` only for city/state/postal; leave the rest null | |
| `street_key` | Lowercase `street_number + route`, expand abbreviations (`st→street, ave→avenue, rd→road, blvd→boulevard, dr→drive, ste→suite, n→north…`), strip punctuation | `123 Main St.` → `123 main street` |
| `state` | 2-letter USPS code (map full names) | `Texas` → `TX` |
| `postal_code` | 5-digit for US (drop +4) | `78701-1234` → `78701` |
| `website` | Keep the URL as given (scheme + host + path) | |
| `domain` | Lowercase host, drop `www.` and port. Use `tldextract` **offline** (`suffix_list_urls=()`, bundled snapshot — it must never hit the network) | `https://www.ABC.com/` → `abc.com` |
| `website_kind` | `own_site` · `builder_subdomain` (host on `wixsite.com, square.site, godaddysites.com, business.site, weebly.com, webflow.io, carrd.co` → domain = **full host**) · `social_profile` (facebook, instagram, linktr.ee, yelp, nextdoor, x/twitter, tiktok, linkedin → **domain = null**) · `none` | |
| `industry` | Map Places `primaryType`/`types` through `taxonomy.py` (e.g. `plumber→plumbing`, `electrician→electrical`, `roofing_contractor→roofing`, `general_contractor→general_contracting`, `dentist→dental`, `lawyer→legal`, `restaurant→restaurant`, …). Unmapped → `other`, raw types kept | |
| `business_status` | `OPERATIONAL→operational`, `CLOSED_TEMPORARILY→closed_temporarily`, `CLOSED_PERMANENTLY→closed_permanently`, else `unknown` | |
| Dates | ISO 8601 UTC everywhere | |

`NormalizedBusiness` is a Pydantic model validated on every record; a validation failure marks the
record `resolution_status = invalid` with the error, it is never silently dropped.

### Entity resolution (blueprint slide 32)
**0. Same source record** → if a `discovered_record` with the same `(source_id, source_record_id)` is already linked, reuse that business (no scoring).

**1. Blocking** — candidate businesses = union of:
- same `domain` (when not null and `website_kind != social_profile`)
- same `phone_e164`
- same `postal_code` + same `name_key`
- same or neighbouring `geohash7` (~150 m) + `rapidfuzz.token_set_ratio(normalized_name) ≥ 80`
Cap at 25 candidates per record.

**2. Signals** (each 0–1) and default weights (config, not hard-coded):
| Signal | Weight | How |
|---|---|---|
| `domain_match` | 0.30 | exact domain |
| `phone_match` | 0.30 | exact E.164 |
| `name_similarity` | 0.20 | `token_set_ratio / 100` on `normalized_name` |
| `address_match` | 0.15 | 1.0 same `street_key`+`postal_code`; 0.5 same postal only |
| `geo_proximity` | 0.05 | 1.0 ≤ 50 m, linear to 0 at 500 m |
Score = weighted sum, rounded to 3 decimals. Store every signal in `signals` jsonb.

**3. Hard rules** (applied after scoring, override the score):
- **Never merge on name alone:** auto-merge requires at least one strong key — `domain_match`, `phone_match`, or (`address_match = 1.0` **and** `name_similarity ≥ 0.9`). Otherwise cap the decision at `review`
- **Conflicting strong keys:** both sides have different non-null domains **and** different non-null phones → `keep_apart` regardless of score
- **Closed vs open** with the same name is still eligible — status does not block matching

**4. Decision thresholds** (config `RESOLUTION_AUTO_MERGE=0.85`, `RESOLUTION_REVIEW=0.60`):
- best score ≥ 0.85 and passes hard rules → **auto-merge**: link record, write field values
- 0.60 – 0.85, or ≥ 0.85 but capped by a hard rule → **review**: create `match_candidates` rows (top 3), record `needs_review`, **and do not create a business yet**
- < 0.60 → **new business**

**5. Survivorship** — the value shown on `businesses` for each field = the most recent non-purged `business_field_values` entry, with source priority `google_places > demo_fixture` (configurable list). Recomputed whenever values change.

### Retention (extends v0.2.0 `purge-expired`)
- `business_field_values.expires_at` = the raw record's `content_expires_at` for Places-derived values
- `purge-expired` also nulls expired field values (keeps the row, sets `purged_at`), then recomputes survivorship
- A business whose `display_name` has no remaining value keeps `display_name = "[expired] <place_id>"` and `businesses.places_content_expires_at` shows why; re-discovery refreshes it
- Place IDs are kept (already true)

### Pipeline
- When `run_discovery` finishes `done`, it enqueues `run_resolution(parent_run_id)` as a new `job_run` (`kind=resolution`, same `search_job_id`)
- `run_resolution` processes records sighted in that run whose `resolution_status = pending` **or** whose `payload_hash` changed since `resolved_at`; idempotent (running twice changes nothing)
- Progress, cancel, retry follow the v0.1.0 job framework; `result_summary`: `{processed, linked_existing, created, needs_review, invalid}`
- Record lookups within one run must lock the candidate business (`SELECT … FOR UPDATE`) or use one worker per run, so two records of the same new business in one run don't create two businesses — test this

### Endpoints (under `/api/v1`)
- `GET /businesses` — filters `industry, city, state, has_website, website_kind, business_status, q` (name search), cursor pagination; any authenticated role
- `GET /businesses/{id}` — detail + `field_values` (value, source, observed_at, expires/purged) + linked records
- `GET /match-candidates?status=pending` — `reviewer`, `admin`; shows both sides + score + signals
- `POST /match-candidates/{id}/decision` `{decision: "merge" | "keep_apart"}` — `reviewer`, `admin`
  - `merge` → link the record to that business, write field values, mark other pending candidates for that record `kept_apart`
  - `keep_apart` on the **last** pending candidate → create a new business from the record
  - Writes an audit log entry either way
- `POST /jobs/{id}/resolve` — manually enqueue resolution for a discovery run (`admin`, `tech_admin`), idempotent via `Idempotency-Key`

## Implementation notes

Decisions taken where the spec left room, and the conservative option chosen each time.

**`name_key` uses metaphone, not double metaphone.** `jellyfish` dropped
`double_metaphone` in 1.0 and the version we depend on does not ship it. `jellyfish.metaphone`
is the same family of algorithm and is what `names.name_key()` uses. Two spellings of one
name still share a key; nothing else does.

**Two extra paths to `review`, neither of which can ever auto-merge.** With the spec's own
weights, a pair with no shared domain and no shared phone tops out at
`0.20 + 0.15 + 0.05 = 0.40` — below the 0.60 review threshold. Taken literally, that
would send every near-duplicate straight to a second business, and the demo cases the spec
asks for (`near-duplicates → review`, `chain locations → review`) would be unreachable. A
candidate is therefore also reviewable when:

- it shares a domain or a phone (two locations of one chain look exactly like this, and
  score 0.50); or
- it shares a postal code and its name similarity is at least 0.80 (`ABC Plumbing LLC`
  next door to `ABC Plumbing & HVAC`).

Both only ever *add* a human decision. The auto-merge rule is untouched: a strong key and
a score at or above `RESOLUTION_AUTO_MERGE` are still required, so neither case can merge
by itself.

**Survivorship orders by source priority first, then recency.** "The most recent
non-purged entry, with source priority" is ambiguous about which wins. Priority is treated
as the stronger rule and recency as the tiebreak within a source, because a configurable
`>` ordering is only meaningful if it can actually override something. A source that is
not on `RESOLUTION_SOURCE_PRIORITY` sorts last, in name order. A `null` never beats a
known value, whatever its priority.

**`domain` falls back to the whole host when the suffix is unknown.** `tldextract` runs
against its bundled snapshot with no network and no cache directory. For a suffix that
snapshot does not know — a brand-new TLD, an intranet name, or a reserved one such as
`.invalid` — it can name no registered domain. Rather than dropping the domain entirely,
the whole host becomes the identity. That is exactly what the rules table says `domain`
is ("lowercase host, drop `www.` and port"), and it can only under-merge: two different
hosts stay two different businesses.

**`website` keeps the URL as given, minus the query string and the fragment.** The rules
table says "keep the URL as given (scheme + host + path)", so casing and the path are
preserved verbatim and only the parts it does not list are dropped. A string with no
parseable host (`tel:...`, free text) stores no website at all rather than a guess.

**`job_runs.params`, a new column.** The spec describes `run_resolution(parent_run_id)`,
but a `job_run` had nowhere to carry which run it was asked to resolve. `params jsonb`
holds `{"parent_run_id": ...}`, is set when the run is enqueued and is never written by a
handler. `job_runs.kind` needed no migration: it is a plain string column.

**"Whose `payload_hash` changed since `resolved_at`" is read as `updated_at > resolved_at`.**
The hash at the time of resolution is not stored, and `updated_at` moves whenever a record
is re-stored — a superset of "the payload changed". Reprocessing is harmless anyway: rule 0
reuses the business a record already has, so a second pass rewrites the same values. A
record sitting at `needs_review` is deliberately skipped, so re-running resolution never
clears a queue a reviewer is working through.

**Concurrency within a run.** One worker processes one run's records sequentially in one
session, so the second record of a new business already sees the first through its own
blocking query. Linking additionally re-reads the chosen business `SELECT … FOR UPDATE`,
so two runs cannot write the same business at once.

**`businesses.domain` is not unique.** Two locations of one chain legitimately share a
domain; the blueprint's unique index would reject the pair instead of putting it in front
of a human. Relaxed on purpose, as the spec instructs.

**`APP_ENV` is accepted as an alias for the existing `ENVIRONMENT` setting**, and
"development" means `local` or `development` — `local` is what `.env.example` ships and
what `make up` runs as, so `make load-demo-data` works out of the box. `ci`, `staging`
and `production` never see the `demo_fixture` source: `sync_sources` only writes rows for
registered adapters, and the demo adapter is not registered there.

**The audit entry for a password reset uses `after`, not `details`.** `audit_logs` has
`before`/`after` and no `details` column, so `user.password_reset` records
`after = {"via": "cli", "token_version": n}` with a null actor.

**`token_version` is checked on access tokens as well as refresh tokens.** The spec only
requires refresh tokens to be retired, but the user row is already loaded on every
request, so enforcing it on both costs nothing and closes the 15-minute window in which a
stolen access token would otherwise still work. A token minted before the column existed
carries no `tv` claim and is read as version 1, which is where every user starts — so
adding it logged nobody out.

**Demo domains use the reserved `.invalid` suffix.** RFC 2606 guarantees it never
resolves, so nothing in the fixture can be fetched by accident. `*.example.com`
subdomains were tried first and were wrong: they all share the registered domain
`example.com`, which made every demo business look like one business.

**Website and address each survive as one group, not field by field.** Manual testing
found a merged `Oak Hill Plumbing` showing `website = facebook.com/oakhillplumbing` and
`website_kind = social_profile` from one record next to `domain = oakhillplumbing.invalid`
from another — a web presence no source ever reported. Picking each field independently
is only safe for fields that mean something on their own, so two sets are now taken whole
from a single record:

- `website`, `domain`, `website_kind`. The group is chosen by what kind of site it is
  first — `own_site > builder_subdomain > social_profile > none` — and only then by the
  usual ordering. `website_kind` merely describes the other two, so a record with neither
  a website nor a domain is not a candidate and cannot blank out a record that has one.
- `address_line1`, `address_line2`, `street_key`, `city`, `state`, `postal_code`,
  `country`, `lat`, `lng`, `geohash7`. A record that reaches a street (`street_key` or
  `address_line1`) is preferred over one that only knows the town, so a newer but vaguer
  record cannot drop a street address while keeping its own city. A record with no
  address at all is not a candidate.

Within a group, "then most recent" is the survivorship ordering already in use — source
priority, then recency, then the newest row — rather than recency alone, so the two rules
do not contradict each other elsewhere on the same business. A null in the winning group
stays null: the older record's suite number is not filled in behind the newer record's
street. Everything outside the two groups is unchanged.

### Future work, out of scope here

- **Un-merging a business.** Once records are linked there is no way to split them back
  apart; it needs a decision about what happens to the field values and to anything
  downstream that already referenced the merged business.
- **v0.4.0 must not fetch demo websites.** The `demo_fixture` source already carries
  `exclude_from_crm_export`; the website audit should skip it on the same basis, since its
  domains are fictional.
- **Multi-location businesses** (`business_locations`) remain out of scope: one business
  is one physical location, so a chain's branches are separate businesses that a reviewer
  confirms one at a time.

## Blockers

None. The Google Places key remains optional for this spec — the demo fixture covers
every path end to end without it.

The open question under **Human prerequisites** — whether Places-derived business fields
must be purged after `PLACES_CONTENT_TTL_DAYS` — is implemented as **yes**, the
conservative reading: `purge-expired` nulls those field values and recomputes the
business. If the client's legal review says otherwise, only
`survivorship`/`purge_expired` change; nothing else depends on it.
