# v0.4.0 — Website audit engine

**Branch:** spec/v0.4.0-website-audit
**Depends on:** v0.3.0 (merged, tag `v0.3.0`)
**Estimate:** 3–4 working days
**Blueprint refs:** §3 Website acquisition (slide 14), §6 Website audit (slide 34), §4 Background processing (slide 23), §8 Security (SSRF guard, slide 42), Failure handling (slide 44)

## Goal
Every business with its own website gets a **deterministic, evidence-backed audit** of its homepage:
reachability, HTTPS, mobile readiness, basic SEO tags, contact and booking options, e-commerce, tech
stack and PageSpeed. Each gap becomes a **finding** with verbatim evidence and a source URL, worded as an
observation ("Audit found no online booking link on the homepage"), never a verdict ("needs a new website").
Audits run automatically after resolution and can be triggered by hand. Everything is testable offline with demo sites.

Also carries three small items from v0.3.0 review: `make recompute-businesses`, a JWT secret length check,
and silencing the short-key test warning.

## Scope
- SSRF-guarded fetcher for arbitrary public URLs (the blueprint's "SSRF-guard everything")
- robots.txt check (cached) before any page fetch; per-host throttle
- Homepage-only deterministic audit (no crawling)
- PageSpeed Insights (mobile) via the existing `core/http.py` client, metered in `api_calls`
- Findings catalogue with evidence-based wording + service-category mapping
- `website_audits` table; audit retention
- `run_audits` worker task auto-enqueued after a resolution run; manual triggers
- Fixture fetch backend + ~10 demo sites so audits work with no network and no key
- Endpoints to read audits and filter businesses by finding
- `make recompute-businesses`, JWT secret check, test-key warning fix

## Out of scope
- AI summaries / classification / "most relevant service gap" (v0.5.0) — this spec is facts only
- JavaScript rendering (Playwright). JS-heavy sites are flagged, not rendered
- Crawling beyond the homepage + robots.txt; sitemaps; screenshots
- Logging in, submitting forms, or any interaction with a site
- Contact extraction for outreach (only presence of tel:/mailto:/form is recorded, not harvested lists)
- UI (v0.6.0)

## Human prerequisites
- In the same Google Cloud project: enable **PageSpeed Insights API** (free). Either add it to the existing key's API restrictions or create a second key restricted to it → `.env` `PAGESPEED_API_KEY=`. Without a key PSI still works at a low shared quota; the build and tests need no key at all
- Decide the bot contact URL or email shown in our User-Agent (e.g. the agency's site). Put it in `.env` as `BOT_CONTACT=` — polite crawling identifies itself
- Generate a strong JWT secret for any non-local environment: `openssl rand -hex 32`

## Design

### Module layout (fits the v0.3.0 tree)
```

backend/app/core/fetch_backends.py      # NetworkFetchBackend, FixtureFetchBackend (dev-only, *.invalid hosts)
backend/app/modules/audit_web/          # (named audit_web to avoid clashing with the existing audit-log module)
    __init__.py
    models.py        # WebsiteAudit
    checks.py        # deterministic checks → CheckResult(value, evidence, evidence_url)
    fingerprints.py  # tech-stack + booking/ecommerce/social signatures (data, not code paths)
    findings.py      # catalogue: code → severity, service_category, wording template
    psi.py           # PageSpeed client (uses core/http.py, metered)
    service.py       # audit_business(), latest_audit(), purge
    router.py
    schemas.py
    worker.py        # run_audits(parent_run_id), run_single_audit(business_id)
backend/app/demo/sites/                 # fixture HTML per demo *.invalid host + robots files + psi json
backend/app/demo/sites/expected_audits.json
backend/migrations/versions/0004_website_audits.py
```
Register models in `models_registry.py`. Register `pagespeed_insights` as a `sources` row (`kind=api`, config `{"role": "audit_service"}`) so its calls are metered/rate-limited like Places; it must **not** be selectable as a search-job source (422 if used).

### SafeFetcher (`core/safe_fetch.py`)
Every non-Google-API HTTP request in the app goes through this. Rules:
| Rule | Value |
|---|---|
| Schemes | `http`, `https` only |
| Ports | 80, 443 only (explicit other ports → refused) |
| DNS | Resolve host; refuse if **any** resolved address is private, loopback, link-local, multicast, reserved, unspecified, CGNAT (100.64/10) or IPv4-mapped equivalents (IPv4 + IPv6) |
| Redirects | Max 3; every hop is re-validated (scheme, port, DNS) |
| Size | Stream; stop at 2 MB (`truncated=true`) |
| Timeouts | connect 5 s, read 10 s, total 20 s |
| Content | Parse only `text/html`/`application/xhtml+xml`; others recorded, not parsed |
| TLS | Verify certificates. A TLS failure is a result (`tls_valid=false`), **never** retried with verification off |
| User-Agent | `LeadDiscoveryRadarBot/0.4 (+{BOT_CONTACT})` |
| Throttle | Per host: ≥ 5 s between requests (Redis lock); global concurrency `AUDIT_MAX_CONCURRENCY=4` |
| robots.txt | Fetched via the same guard, cached 24 h per host in Redis. Parse with `urllib.robotparser` for our UA token and `*`. 2xx → obey; 4xx → allowed; 5xx/timeout/network error → **disallowed** (RFC 9309, conservative) |
Known limitation (write in Implementation notes): DNS is validated before connecting; a hostile DNS server could in theory re-resolve between check and connect. Production hardening (egress proxy / pinned resolution) is a v0.8.0 item.

### Fixture backend (offline testing)
- `FixtureFetchBackend` answers only for hosts ending in `.invalid` (reserved by RFC 2606, can never be real) and only when `APP_ENV=development` or in tests
- Maps `host + path` → files in `backend/app/demo/sites/<host>/` (`index.html`, `robots.txt`, optional `_meta.json` with status code, headers, redirect target, TLS failure, timeout simulation)
- PSI calls for `.invalid` URLs are answered from `sites/<host>/psi.json` the same way
- Demo sites (≥ 10) must cover: modern HTTPS site with booking widget; old HTTP-only site with no viewport and `© 2016`; WordPress site with no meta description; Wix/Squarespace builder site; Shopify store; robots.txt disallowing `/`; robots.txt returning 503; a redirect chain http→https; an unreachable host (no fixture → connection error); a JS-shell page (tiny body, many scripts); a TLS failure. Map them onto the existing demo businesses' domains (e.g. `oakhillplumbing.invalid`)
- `expected_audits.json` lists, per demo domain, the expected status and finding codes — asserted by an integration test

### Deterministic checks (blueprint slide 34)
Each check returns `{value, evidence_text (≤ 300 chars verbatim), evidence_url}`; unknown stays `null`.
| Check key | How |
|---|---|
| `reachable`, `http_status`, `final_url`, `redirect_chain` | From the fetch |
| `https`, `http_redirects_to_https`, `tls_valid` | Final URL scheme; whether `http://` input ended on `https://`; TLS outcome |
| `viewport_meta` | `<meta name="viewport">` present, content captured |
| `title`, `title_length` | `<title>` text |
| `meta_description`, `meta_description_length` | `<meta name="description">` |
| `h1_present` | at least one `<h1>` with text |
| `tel_link`, `mailto_link`, `contact_form` | any `href="tel:…"`, `href="mailto:…"`, a `<form>` containing an email/tel input. **Store presence + one example, not a list** |
| `booking` | signature match in `fingerprints.py` (e.g. Calendly, Acuity, Square Appointments, Setmore, Housecall Pro, Jobber, ServiceTitan, Booksy, Vagaro, OpenTable, Mindbody) or a link whose text matches `book (now|online)`, `schedule (online|service|appointment)`, `request (a )?quote` |
| `ecommerce` | Shopify / WooCommerce / BigCommerce / Squarespace Commerce signatures, cart/checkout links |
| `social_links` | set of platforms linked (facebook, instagram, x, linkedin, youtube, tiktok, yelp, nextdoor, google) |
| `structured_data` | JSON-LD with `@type` LocalBusiness (or subtype) present |
| `favicon` | link rel icon present |
| `copyright_year` | highest 4-digit year (1995–current) found next to `©`/`copyright` |
| `tech_stack` | generator meta + signatures (WordPress, Wix, Squarespace, Shopify, Webflow, GoDaddy Website Builder, Weebly, Duda, Joomla, Drupal, React/Next.js hints) |
| `js_shell_suspected` | visible body text < 200 chars **and** ≥ 5 `<script>` tags |
| `psi` | mobile: performance score (0–100), LCP ms, CLS, TBT ms, CrUX overall category if present |
Fingerprints live as data in `fingerprints.py` (easy to extend), each with a unit test using a snippet.

### Findings catalogue (`findings.py`)
Each finding: `code`, `severity` (info/low/medium/high), `service_category` (`web_design`, `seo`, `booking`, `performance`, `ecommerce`, `security`, `web_presence`), `wording` template, `evidence_text`, `evidence_url`. Wording rule, enforced by a test that scans every template: must start with "Audit found", "Audit could not", "PageSpeed" or "Listing shows", and must not contain "needs", "should", "bad", "terrible", "outdated website".
| Code | Trigger | Service |
|---|---|---|
| `no_website` | business `website_kind = none` (no fetch) | web_presence |
| `social_profile_only` | `website_kind = social_profile` (no fetch) | web_presence |
| `unreachable` | network error / 5xx on final URL | web_design |
| `no_https` | final URL is http | security |
| `tls_invalid` | TLS failure | security |
| `no_mobile_viewport` | viewport missing | web_design |
| `missing_title` / `missing_meta_description` | absent or empty | seo |
| `no_h1` | no h1 | seo |
| `no_structured_data` | no LocalBusiness JSON-LD | seo |
| `no_online_booking` | booking false (only for industries in a config list where booking is normal: plumbing, hvac, electrical, dental, salon, auto_repair, legal, etc.) | booking |
| `no_contact_on_homepage` | no tel, mailto or contact form | web_design |
| `stale_copyright` | copyright year ≤ current year − 3 | web_design |
| `slow_mobile` | PSI performance < 50 (config) | performance |
| `js_shell_suspected` | flag, severity info — audit may be incomplete | web_design |
| `robots_blocked` | robots disallows us — audit not performed, severity info | — |
Example wording: `no_online_booking` → "Audit found no online booking or scheduling link on the homepage." with evidence `"No known booking widget or 'book online' link in {final_url}"`.

### Data model — migration `0004_website_audits`
- `website_audits`
  `id uuid pk`, `business_id fk businesses`, `job_run_id fk job_runs null`, `url_audited text`, `final_url text null`,
  `status enum[done, skipped, robots_blocked, unreachable, failed]`, `http_status int null`,
  `checks jsonb`, `psi jsonb null`, `tech_stack jsonb`, `findings jsonb` (array),
  `page_text text null` (visible text, ≤ 20 000 chars — input for v0.5.0 AI), `html_sha256 text null`,
  `rules_version text` (e.g. `audit-1`), `content_expires_at timestamptz`, `purged_at null`,
  `started_at`, `finished_at`, `created_at`
  Index `(business_id, created_at desc)`; GIN index on `findings` for filtering by code
- `job_runs.kind` gains `audit`
- `AUDIT_CONTENT_TTL_DAYS=90`: `purge-expired` also nulls `page_text` of expired audits (checks, findings, evidence snippets stay)
- Full HTML is **not** stored (hash only)

### Pipeline
- When `run_resolution` finishes `done`, enqueue `run_audits(parent_run_id)` (`kind=audit`, `params.parent_run_id`)
- It audits businesses linked or created in that resolution run whose latest audit is missing or older than `AUDIT_MAX_AGE_DAYS=30`, skipping `closed_permanently`
- `no_website` / `social_profile_only` are recorded as audits with status `skipped` and that finding, without any network call
- Idempotent within the max-age window; cancellable per business; progress counts; `result_summary` `{audited, skipped, robots_blocked, unreachable, failed, psi_calls}`
- A failure on one business never fails the run (it is recorded as that business's `failed` audit); the run fails only on systemic errors (DB/Redis down)
- PSI errors (quota, 5xx) leave `psi = null` with the reason in `checks.psi_error`; the rest of the audit still completes

### Endpoints (under `/api/v1`)
- `POST /businesses/{id}/audit` — enqueue a fresh audit now (ignores max age); roles `admin`, `tech_admin`, `reviewer`, `sales_rep`; idempotent via `Idempotency-Key`
- `POST /jobs/{id}/audit` — enqueue audits for a resolution run's businesses (`admin`, `tech_admin`)
- `GET /businesses/{id}/audits` — history, newest first
- `GET /website-audits/{id}` — full detail (checks, findings, PSI, tech); `page_text` only for `admin`, `reviewer`, `tech_admin`
- `GET /businesses` gains filters `finding=<code>` (repeatable, AND), `audit_status=`, and each item gains `latest_audit: {status, finding_codes, audited_at}`

### Carry-over items
- **`make recompute-businesses`** → `python -m app.cli recompute-businesses [--business-id ID]`: re-runs survivorship for every business (batched, idempotent, prints counts `changed / unchanged`). Needed whenever survivorship rules change on a live DB
- **JWT secret check**: at startup, if `APP_ENV` is not `development`/`test` and the JWT secret is < 32 bytes → refuse to start with a clear message; in development log a warning. `.env.example` shows `openssl rand -hex 32`
- **Test warning**: test fixtures use a ≥ 32-byte secret so `InsecureKeyLengthWarning` disappears from `make check`

## Implementation notes

Decisions taken where the spec left room, and the conservative option chosen each time.

### Known limitation: DNS is checked before the connection is made

As the spec anticipates, `SafeFetcher` resolves the hostname, refuses every non-public
address, and then lets httpx connect **by name**. A hostile DNS server could in theory
answer differently the second time (a DNS-rebinding attack) and reach a private address.
Closing that needs a pinned resolver or an egress proxy, which is a v0.8.0 item; it is
written at the top of `app/core/safe_fetch.py` so nobody mistakes the current guard for a
complete one.

### The fixture backend answers for checked-in hosts, not only for `.invalid`

The spec says the fixture backend answers only for `*.invalid`. Three of the v0.3.0 demo
businesses are deliberately on **real** builder suffixes — `wixwaterworks.wixsite.com`,
`squaresitesewer.square.site`, `godaddygutters.godaddysites.com` — and one on
`messyformat-demo.com`, because that is what makes them `builder_subdomain` and exercises
the `www.`/upper-case normalization path. Under the literal rule, `make load-demo-data`
would have sent our bot to four domains we do not own.

The more conservative option is the one taken: `FixtureFetchBackend` answers for any host
with a checked-in directory under `app/demo/sites/`, **and** for any `*.invalid` host
whether a fixture exists or not (answering "connection refused", which is what a reserved
name does anyway). It is still only ever installed when `Settings.fixtures_allowed` is
true — `local`, `development` or `ci` — so it can never shadow a real site in staging or
production, and every host it answers for is a directory somebody committed and reviewed.
`demo_site_dir` also falls back from `www.host` to `host`, the way a real site serves both.

### `fixtures_allowed` is wider than `is_development`

`is_development` (`local`, `development`) gates the demo *source*, and must stay narrow so
fictional businesses cannot reach staging. The fixture fetch and PageSpeed backends need
to work in `ci` as well — the whole point is that the suite never touches the network — so
they are gated on a new `Settings.fixtures_allowed`, which adds `ci` and nothing else.

### A TLS failure is reported as `tls_invalid`, not also as `unreachable`

A certificate that does not verify shows up on the **robots.txt** request, before the
homepage is ever asked for. Reporting it as `robots_blocked` would have been misleading,
so `RobotsDecision` carries `tls_valid` and the audit ends as status `unreachable` with the
single finding `tls_invalid`. Emitting `unreachable` alongside it would say the same thing
twice in less useful words, so only `tls_invalid` is recorded — the status still says the
site could not be read.

### A host that cannot connect is `unreachable`, not `robots_blocked`

RFC 9309 says an unreadable `robots.txt` means "stay away", and that is what the robots
policy returns. But when the failure is a *connection* failure the host itself is not
there, and calling that `robots_blocked` would hide it from anybody filtering for dead
websites. `RobotsDecision.error_kind` lets the service tell the two apart: a connect
failure is recorded as `unreachable`, a timeout or a 5xx as `robots_blocked`. Either way
**no page request is made** — the conservative behaviour is unchanged, only the label.

### robots.txt follows redirects

A site that serves `robots.txt` from `https://` after an `http://` request, or from a
canonical host, is not a site refusing us. The robots fetch therefore goes through the same
redirect-following `fetch()` as a page, with every hop validated identically. It is run
with `record=False` so it never counts as a page request, which is what lets a test assert
that a disallowed site was never asked for its homepage.

### The per-host throttle applies only to hosts we actually go out to

Politeness is owed to a real server. A fixture answered from disk has nobody to be polite
to, so `SafeFetcher` skips the throttle when the chosen backend does not resolve DNS. The
SSRF guard, the size cap and the concurrency guard all still apply. Without this, one demo
load would have spent two minutes asleep and the test suite far longer, for no benefit to
anyone.

### The concurrency cap waits, then proceeds

`AUDIT_MAX_CONCURRENCY` is about our own load, not a promise to a site owner — the per-host
throttle is the promise. So `ConcurrencyGuard.acquire()` waits up to 30 seconds for a slot
and then goes ahead with a warning, rather than failing an audit over a queue.

### `checks.psi_error` is a check like any other

The spec asks for `checks.psi_error` to be set when PageSpeed fails. `checks` is otherwise
a uniform map of `{value, evidence_text, evidence_url}`, so `psi_error` is stored in that
same shape with the reason as its `value`. Readers do not need a special case.

### `job_runs.kind` needed no DDL

It is a plain `String(64)`, so the new `audit` kind is a constant in `jobs.service`
alongside `discovery` and `resolution`. Migration `0004` says so in its docstring.

### One `audit` job kind, two shapes of run

The spec names `run_audits(parent_run_id)` and `run_single_audit(business_id)`. Registering
two handlers for one kind is not possible, so the registered handler is `run_audits`, and it
dispatches to `run_single_audit` when the run's params carry a `business_id`. Both functions
exist under the names the spec gives them.

### Failure isolation uses a savepoint

A business whose audit raises could otherwise leave half-written rows in the session the
rest of the run shares, and the `failed` audit would then fail to write too. Each business
is audited inside `session.begin_nested()`, so a failure rolls back exactly that business's
work before `record_failure` writes the row that explains it.

### Two demo listings moved from https to http

`bartoncreekplumbing.invalid` (the "old site" case) and `travisheightsplumbers.invalid`
(the redirect case) needed `http://` listings for `no_https` and `http_redirects_to_https`
to be reachable at all. Neither change touches a domain or a name, so every v0.3.0
resolution expectation still holds — `test_demo_dataset.py` proves it.

### `expected_audits.json` is keyed by domain, with the no-website cases by record id

Two demo businesses have only a social profile and one has no website at all, so they have
no `domain` to key on. They live under `by_record`, keyed by the demo place id, with the
domains under `by_domain`. The permanently closed business is listed under `not_audited`
with the reason.

### `make load-demo-data` now finishes the pipeline

The spec asks for it to "end with audits done". It therefore runs the resolution and audit
runs in-process after loading, instead of only queueing them, and prints each run's counts.
`--queue-only` (`ARGS=--queue-only`) keeps the old hand-to-the-worker behaviour.

### The JWT check treats `ci` as development

`.env` values here are `local | development | ci | staging | production`, where the spec
says "not `development`/`test`". `local`, `development` and `ci` warn; `staging` and
`production` refuse to start. The check runs in the API factory, the worker entrypoint and
the CLI, so there is no way in that skips it.

### Three things the manual read-through fixed, and one rule written down (`audit-2`)

Reading audit `0911c6d9` of `bartoncreekplumbing.invalid` by eye found three places where
a check was true and useless. All three were about *how an audit reads*, not about what it
measured, and none of them changed a single finding code — but an audit nobody trusts is
worth nothing, so `rules_version` is bumped to `audit-2` and each is pinned by a regression
test against that same fixture (`tests/unit/test_audit_evidence.py`).

1. **`tls_valid` claimed a certificate verified where none was ever presented.** The
   fixture is served over plain `http`, and `FetchOutcome.tls_valid` defaults to `True`
   because nothing failed. Nothing *happened* either. `tls_valid` is now `None` whenever
   the final URL is not `https`, with the evidence `not applicable: served over http`. The
   choice made here: `None` rather than `False`, because `False` is what a certificate that
   genuinely does not verify means, and `tls_invalid` (a high-severity security finding)
   hangs off exactly that value.

2. **`null` and `false` meant the same thing in some checks and different things in
   others.** `favicon` and `mailto_link` answered `False` for an absent thing;
   `booking`, `viewport_meta`, `meta_description`, `structured_data` and `ecommerce`
   answered `None` for an absent thing, because they carry a captured value when present
   and `None` was doing double duty as "not present". The rule now holds across every
   check, and is written at the top of `checks.py`: **on a page that was fetched and
   parsed, absent is `False`; `None` means the check could not run** — nothing was parsed,
   or the question does not apply. `title` and `copyright_year` were changed with them even
   though the manual read did not catch them, because a rule that holds for five checks out
   of seven is not a rule. `copyright_year` needed one guard in `findings.py`: `bool` is a
   subclass of `int` in Python, so without `not isinstance(year, bool)` an absent notice
   would read as the year zero and be reported as stale.

3. **Snippet evidence was cut out of the HTML, mid-tag at both ends.** `copyright_year`
   cited `el:+1-512-555-0102">Call ... </footer`. It now reads the *visible text* — what a
   visitor actually sees — forward from the copyright mark, trimmed to whole words, giving
   `© 2016 Barton Creek Plumbing LLC. All rights reserved.`

   The instruction to apply the visible-text rule to any other snippet evidence has one
   honest limit, taken conservatively rather than pretended away: **platform and widget
   signatures do not exist in visible text.** `cdn.shopify.com` lives in a `src`,
   `wp-content` in a stylesheet path; there is no sentence to quote. Those are the only
   other snippets cut out of a larger string, and for them `snippet_around` now returns the
   **whole tag the hit sits in** (`<meta name="generator" content="wordpress 6.5.2">`
   rather than `r" content="wordpress 6.5.2">`), falling back to a whole-word-trimmed
   window when a signature does match the page's text. Every other evidence field was
   already a complete element (`str(tag)`) or a sentence we wrote, so nothing else needed
   touching — a test over every demo homepage asserts no evidence field is cut through a
   tag.

`expected_audits.json` needed no change: no status and no finding code moved. That is the
point of these three fixes, and the demo integration test proves it.

## Blockers

None. `PAGESPEED_API_KEY` and `BOT_CONTACT` are both optional for the build and the tests:
PageSpeed answers without a key at a lower quota, the demo and the suite are answered from
checked-in fixtures, and the User-Agent falls back to a description of where the contact
should go rather than inventing one. Both are listed under **Human prerequisites** for the
first real run.
