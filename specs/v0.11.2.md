# v0.11.2 — Someone else can run it

Status: draft
Branch: `spec/v0.11.2-windows-readme`
Previous: v0.11.1 (safety pass), merged and tagged.

## Goal

The client wants to run this on their own Windows machine to see how much API traffic it
generates before we talk about deployment. They cannot start, because nothing in the repo
tells them how.

This spec produces one document that takes a Windows user from a clean machine to a working
review queue, and proves it by following it. No features. No code changes beyond whatever the
document turns out to need.

Budget: about a day.

## The problem that has to be solved first

Every workflow in this project is a `make` target — `make prod-up`, `make migrate PROD=1`,
`make sync-sources PROD=1`. **Windows has no `make`.** The document has to pick one answer and
commit to it:

- **Run everything inside WSL2 Ubuntu.** Docker Desktop already requires WSL2, so it is
  present. `make`, `bash` and the existing targets all work unchanged, and the client follows
  the same instructions we do. This is the recommended answer unless something breaks it.
- **Give raw `docker compose` equivalents for every target.** A second surface to maintain and
  to get out of step with the Makefile.

Choose, say why in the notes, and write the document for that one path. Do not write both.

## Scope

### 1. The document

`README-WINDOWS.md`, linked from the main `README.md`. It covers, in order:

**Before you start** — what this build is and is not. It is a testing build that runs on one
machine; it is not deployed, it is not backed up off the machine, and it should not be given a
public address. Say this plainly at the top so nobody mistakes it for a product install.

**Prerequisites** — Docker Desktop for Windows with the WSL2 backend, Git, and the WSL2
Ubuntu distribution. Name the minimum versions you actually tested against, and say how much
disk and RAM to give WSL2 — the default is often too small for five containers plus Postgres.

**Line endings.** Git on Windows converts LF to CRLF by default, which breaks shell scripts
once they are inside a Linux container. Either set `core.autocrlf=input` in the instructions
or add a `.gitattributes` that pins the script files — check whether one already exists, and
if it does not, adding it is in scope.

**Getting the code** — clone, and which branch or tag to check out.

**The keys they must obtain themselves.** Three, with a short paragraph each on where to get
it, what it costs, and what happens without it:

- Google Places API (New) — needs a billing account. Say which APIs to enable in the Cloud
  console and which field-mask fields we request. Note that `websiteUri`,
  `nationalPhoneNumber`, `rating` and `userRatingCount` are Enterprise-tier fields and that
  searches are therefore not free.
- PageSpeed Insights — free, 25,000 calls a day. Note that the key goes in a header, not the
  URL.
- OpenAI — optional. Say what the product does with `AI_PROVIDER=disabled` so they can start
  without one.

**Configuration** — copy `.env.prod.example` to `.env.prod` and fill it in. Walk through every
variable that a first-time operator has to set, not just the keys: the admin email and
password, the database credentials, and `PLACES_DAILY_CALL_CAP`. Say explicitly what the cap
is for and that it should be left at its default. We spent 500 real billable calls learning
that lesson; the client should not have to repeat it.

**First run** — build, migrate, seed the sources, start, and where the app appears
(`http://127.0.0.1:3000`). Every command exactly as typed, in order, with what success looks
like after each one.

**Your first twenty minutes** — a guided walkthrough, because an empty review queue tells them
nothing. Run one search in one city for one industry; watch the audit run; open the review
queue; open one lead and read its findings; approve it; see it reach the CRM view. This
section is what turns "it installed" into "I understand what this does", and it is the part
the client will actually judge us on.

**Stopping, restarting, and starting over** — how to shut down without losing data, how to
back up the database to a file, and how to wipe and start clean.

### 2. The Windows-specific failures we already know about

These are not hypothetical. Each one cost us time in this project and belongs in a
troubleshooting section with the symptom first, so the client can find it by what they see.

- **Sleep kills a running job.** Windows Modern Standby drops the network. We proved this
  against the system event log: twelve OpenAI calls failed between standby at 01:05:47 and
  wake at 03:08:50. An audit run of fifty businesses takes twenty-five to thirty minutes, and
  RQ measures wall clock — so a machine that sleeps mid-run produces failed audits. Tell them
  to keep the machine awake for the duration of a run, and say how.
- **Ports 3000 and 8000 already in use.** Both bind to 127.0.0.1. Give the command that finds
  the offender on Windows.
- **The dev and prod compose projects cannot run at the same time.** They bind the same ports.
  Say so, and give the command that shows which is running.
- **`make migrate` without `PROD=1` hits the wrong database.** It silently starts the dev
  project. Give the symptom — a source count that does not match — and the fix.
- **WSL2 runs out of memory or disk.** Give the `.wslconfig` settings.

Add anything else the walkthrough in item 3 turns up.

### 3. Verify the document by following it

A README nobody has followed is a guess. Before this spec is finished:

- Clone the repository into a fresh directory, as a new user would.
- Follow the document literally, command by command, without using knowledge that is not in
  it.
- Every place you had to know something the document does not say, add it.
- Record in the implementation notes what broke and what was missing. That list is the real
  output of this spec; the document is what it produced.

If a full Windows run is not possible from here, say so plainly rather than claiming it was
tested — follow it in WSL2 or a clean Linux container, state exactly which parts remain
unverified on Windows, and mark them in the document so the client knows where to expect
friction.

## Out of scope

- Deployment of any kind. This is a local evaluation build, not a hosted one.
- Any change to the checks, the queue, or the pipeline.
- A Windows-native path without WSL2.
- A GUI installer, a one-click script, or anything that hides the commands. The client is
  testing infrastructure behaviour; they need to see what runs.
- The `v0.12.0` audit-depth work.
