# v0.11.2 — Someone else can run it

Status: draft
Branch: `spec/v0.11.2-windows-readme`
Previous: v0.11.1 (safety pass), merged and tagged.

## Goal

The client wants to run this on their own Windows machine to see how much API traffic it
generates before we talk about deployment. They cannot start, because nothing in the repo
tells them how.

This spec produces one document that takes a Windows user from a clean machine to a working
review queue, and proves it by following it. No features. No code changes beyond whatever the
document turns out to need.

Budget: about a day.

## The problem that has to be solved first

Every workflow in this project is a `make` target — `make prod-up`, `make migrate PROD=1`,
`make sync-sources PROD=1`. **Windows has no `make`.** The document has to pick one answer and
commit to it:

- **Run everything inside WSL2 Ubuntu.** Docker Desktop already requires WSL2, so it is
  present. `make`, `bash` and the existing targets all work unchanged, and the client follows
  the same instructions we do. This is the recommended answer unless something breaks it.
- **Give raw `docker compose` equivalents for every target.** A second surface to maintain and
  to get out of step with the Makefile.

Choose, say why in the notes, and write the document for that one path. Do not write both.

## Scope

### 1. The document

`README-WINDOWS.md`, linked from the main `README.md`. It covers, in order:

**Before you start** — what this build is and is not. It is a testing build that runs on one
machine; it is not deployed, it is not backed up off the machine, and it should not be given a
public address. Say this plainly at the top so nobody mistakes it for a product install.

**Prerequisites** — Docker Desktop for Windows with the WSL2 backend, Git, and the WSL2
Ubuntu distribution. Name the minimum versions you actually tested against, and say how much
disk and RAM to give WSL2 — the default is often too small for five containers plus Postgres.

**Line endings.** Git on Windows converts LF to CRLF by default, which breaks shell scripts
once they are inside a Linux container. Either set `core.autocrlf=input` in the instructions
or add a `.gitattributes` that pins the script files — check whether one already exists, and
if it does not, adding it is in scope.

**Getting the code** — clone, and which branch or tag to check out.

**The keys they must obtain themselves.** Three, with a short paragraph each on where to get
it, what it costs, and what happens without it:

- Google Places API (New) — needs a billing account. Say which APIs to enable in the Cloud
  console and which field-mask fields we request. Note that `websiteUri`,
  `nationalPhoneNumber`, `rating` and `userRatingCount` are Enterprise-tier fields and that
  searches are therefore not free.
- PageSpeed Insights — free, 25,000 calls a day. Note that the key goes in a header, not the
  URL.
- OpenAI — optional. Say what the product does with `AI_PROVIDER=disabled` so they can start
  without one.

**Configuration** — copy `.env.prod.example` to `.env.prod` and fill it in. Walk through every
variable that a first-time operator has to set, not just the keys: the admin email and
password, the database credentials, and `PLACES_DAILY_CALL_CAP`. Say explicitly what the cap
is for and that it should be left at its default. We spent 500 real billable calls learning
that lesson; the client should not have to repeat it.

**First run** — build, migrate, seed the sources, start, and where the app appears
(`http://127.0.0.1:3000`). Every command exactly as typed, in order, with what success looks
like after each one.

**Your first twenty minutes** — a guided walkthrough, because an empty review queue tells them
nothing. Run one search in one city for one industry; watch the audit run; open the review
queue; open one lead and read its findings; approve it; see it reach the CRM view. This
section is what turns "it installed" into "I understand what this does", and it is the part
the client will actually judge us on.

**Stopping, restarting, and starting over** — how to shut down without losing data, how to
back up the database to a file, and how to wipe and start clean.

### 2. The Windows-specific failures we already know about

These are not hypothetical. Each one cost us time in this project and belongs in a
troubleshooting section with the symptom first, so the client can find it by what they see.

- **Sleep kills a running job.** Windows Modern Standby drops the network. We proved this
  against the system event log: twelve OpenAI calls failed between standby at 01:05:47 and
  wake at 03:08:50. An audit run of fifty businesses takes twenty-five to thirty minutes, and
  RQ measures wall clock — so a machine that sleeps mid-run produces failed audits. Tell them
  to keep the machine awake for the duration of a run, and say how.
- **Ports 3000 and 8000 already in use.** Both bind to 127.0.0.1. Give the command that finds
  the offender on Windows.
- **The dev and prod compose projects cannot run at the same time.** They bind the same ports.
  Say so, and give the command that shows which is running.
- **`make migrate` without `PROD=1` hits the wrong database.** It silently starts the dev
  project. Give the symptom — a source count that does not match — and the fix.
- **WSL2 runs out of memory or disk.** Give the `.wslconfig` settings.

Add anything else the walkthrough in item 3 turns up.

### 3. Verify the document by following it

A README nobody has followed is a guess. Before this spec is finished:

- Clone the repository into a fresh directory, as a new user would.
- Follow the document literally, command by command, without using knowledge that is not in
  it.
- Every place you had to know something the document does not say, add it.
- Record in the implementation notes what broke and what was missing. That list is the real
  output of this spec; the document is what it produced.

If a full Windows run is not possible from here, say so plainly rather than claiming it was
tested — follow it in WSL2 or a clean Linux container, state exactly which parts remain
unverified on Windows, and mark them in the document so the client knows where to expect
friction.

## Out of scope

- A GUI installer, a one-click script, or anything that hides the commands. The client is
  testing infrastructure behaviour; they need to see what runs.
- The `v0.12.0` audit-depth work.

## Implementation notes

_(append only)_

**Why this before v0.12.0.** The depth work is five and a half days and nobody is waiting on
it. The client is waiting on this. They also asked for it for a specific reason — to see what
the API traffic actually looks like before committing to anything — and that answer is worth
having before we scope the next phase.

**Write it for someone tired.** The reader is a client evaluating whether to keep paying for
this, on an operating system the project was not built on, probably at the end of a working
day. Symptom first in troubleshooting. Exact commands. No "simply" and no "just".

**Decision 1 — WSL2 Ubuntu, not raw `docker compose`. (Recorded before writing.)**
WSL2, for these reasons, in order of weight:

1. *It is already there.* Docker Desktop's supported Windows backend is WSL2, so every
   client who can run the stack at all already has the WSL2 kernel; adding Ubuntu is one
   command (`wsl --install -d Ubuntu-24.04`). The PowerShell path saves the client nothing
   they would not install anyway.
2. *One surface.* Inside Ubuntu the client runs the exact targets we run: `make prod-up`,
   `make migrate PROD=1`, `make backup PROD=1`, `make restore`. The Makefile is the thing
   we test. A PowerShell table of `docker compose` equivalents is a second copy of it that
   nothing tests, and the copy that already existed had drifted: the old README's 3b route
   skipped `up`'s `chmod a+rwx backups logs` (the containers run unprivileged and write
   there), had no equivalent for `restore`'s typed-confirmation / stop / restore / migrate /
   start sequence, and needed a PowerShell function re-pasted in every new window.
3. *It removes the line-ending problem at the source.* Git inside Ubuntu does not convert
   line endings (see decision 2), and a clone in the Ubuntu filesystem gets Linux file
   permissions and fast bind mounts. A clone under `C:\` via Git for Windows gets neither.
4. *What would break it:* a PC where virtualisation is off or locked (a managed work
   laptop). That breaks Docker Desktop too, so raw compose would not rescue it; the doc
   says so and points at the firmware setting / IT department.

Cost accepted: the client installs one more thing (Ubuntu) and works in a Linux window.
The document is written for that path only; the old README section, which offered both
routes, was removed and replaced with a link.

Ubuntu **24.04** is pinned (`-d Ubuntu-24.04`, not `-d Ubuntu`): `wsl --list --online` on
the build host now offers Ubuntu 26.04 too, and plain `Ubuntu` follows whichever is newest.
24.04 is the version the walkthrough ran on.

**Decision 2 — `.gitattributes` already exists and is kept as it is; one file needed
renormalizing.** Checked before acting: `.gitattributes` was added in `666b011`
(2026-09-24, before v0.11.1, so it is in the tagged release) with `* text=auto eol=lf`,
CRLF only for `*.bat/*.cmd/*.ps1`, and binary for images/fonts/dumps. `eol=lf` makes Git
write LF on checkout *regardless of* `core.autocrlf`, so it covers Git for Windows' default
`autocrlf=true`; a `core.autocrlf=input` instruction would add nothing and is not in the
document. It also does not matter on the chosen path: Git inside Ubuntu has no autocrlf
default. What `.gitattributes` had *not* done was fix files already committed with CRLF —
it governs checkout conversion, and a file whose index copy contains CRLF is written with
CRLF. `git ls-files --eol` found one: `specs/v0.10.0.md` (`i/crlf`). The walkthrough's
line-ending check caught it on the first clean clone (printed `1`, the document said `0`).
Fixed with `git add --renormalize .` (line endings only; `git diff --ignore-cr-at-eol` is
empty). No shell script, Makefile, Dockerfile or `.env*` template was affected. Section 3
of the document explains the problem, why the Ubuntu path avoids it, and what would still
cause it (cloning with Git for Windows / GitHub Desktop or into `/mnt/c`).

**The clean-clone walkthrough — where it ran, and what it could not reach.** A full
Windows run was **not possible from here**, and the document does not claim one. This
session runs inside WSL2 on the build laptop, which already has WSL, Ubuntu and Docker
Desktop installed, and the production stack (`radar-prod-*`) is running on it, holding
`127.0.0.1:3000/8000` under the same compose project name a fresh clone would use — so
following the document on this host would have taken over the real install. Instead:

- *Docker:* a private `docker:28-dind` engine (28.5.2), standing in for Docker Desktop.
- *The evaluator's Ubuntu:* a stock `ubuntu:24.04` container sharing that engine's network,
  with a sudo user `evaluator` and **no** `make`, `git` or `nano` until section 2 installed
  them. The Docker CLI and Compose v2.40.3 were copied in, standing in for Docker Desktop's
  WSL integration.
- *The browser:* Playwright Chromium 1.63 in the same network namespace, so
  `127.0.0.1:3000` meant what it means to the reader.
- *Windows itself:* only one command ran on real Windows (the build host, Windows 11 Pro
  26200, read-only): the `Get-NetTCPConnection` port finder, which reported
  `com.docker.backend` for 3000/8000 held by the running `radar-prod` stack.

Run, in order, from `git clone https://github.com/...` (public; worked without
credentials): section 2's `apt install` and `docker compose version`; section 4's clone and
line-ending check; 6.1; 6.2 (the four values set with `sed`, not interactively in `nano`;
**placeholder keys**, see below); 6.5; 7 steps 1–4 (sign-in, forced password change, empty
queue); section 8 steps 1–3 (Health baseline, the search form, the estimate — *Save and
run* not clicked); 9: `prod-ps`, `prod-logs`, `prod-down`/`prod-up` (data kept),
`backup`, `restore` (confirmation piped in), `reset-password` (prompts driven through
`script`), the wipe sequence; and the troubleshooting reproductions below.

**Deviations from "literally":** `git checkout v0.11.2` fails until the tag exists, so the
walkthrough checked out this branch from a bundle (it is not pushed); `nano` edits were
made with `sed`; keys were placeholders.

**Not run, and marked "Not yet tested" in the document:** every Windows-side step
(installing Docker Desktop / WSL / Ubuntu, firmware virtualisation, `.wslconfig` and
`wsl --shutdown`, Docker Desktop's disk and WSL-integration settings, the `powercfg`
commands — not run because they would change the build host's power settings —
`explorer.exe`, the browser on Windows); the effect of a missing Places or PageSpeed key
(described from the code); and **section 8 from step 4 on**: the real search, review,
approve, *Send now*, *Export CSV* and the Health traffic view. Those need live, billed
Places calls, and CLAUDE.md keeps live calls to a human; the section says so at its top.

**What broke or was missing — the real output of this spec:**

1. *The line-ending check failed on the first clean clone.* It printed `1`, the document
   said `0`: `specs/v0.10.0.md` was stored with CRLF (decision 2). Renormalized; re-cloned;
   prints `0`.
2. *`git checkout v0.11.2` fails until a human tags **and pushes** v0.11.2.* GitHub had
   tags up to v0.11.1. The document tells the reader to stop and tell us if the tag is
   missing rather than continue on another version. **Push the tag before sending the
   document to the client.**
3. *The expected output of `make migrate PROD=1` was invented in the draft*
   (`sources: 3 registered, 0 created`). The real output is `Synced 4 source(s):` and
   four rows. Corrected.
4. *The spec's "source count that does not match" symptom, observed:* `make migrate`
   without `PROD=1` prints `created .env from .env.example …` first, spends minutes
   building the development image, and ends `Synced 5 source(s):` with an extra
   `demo_fixture` row. If it was the first migrate, `make seed-admin PROD=1` then fails
   with `relation "users" does not exist` (reproduced). All three are now the entry's
   heading.
5. *An `ADMIN_EMAIL` on a reserved TLD passes the startup check but fails
   `seed-admin`:* `value is not a valid email address: The part after the @-sign is a
   special-use or reserved name`. `name@corp.local` would hit this. Documented in 6.2 and
   troubleshooting. (A product fix — checking it at startup — is out of scope.)
6. *`seed-admin` prints a UUID*, not `(id 1)`. Corrected.
7. *The industry is "Plumbing"*, not "Plumber". Corrected.
8. *The estimate for 20 results says "Google Places calls (at most) 4"* — the per-run
   safety ceiling, not a forecast; a reader expecting 1–2 would think it wrong. Section 8
   now says what the 4 is.
9. *Opening `localhost:3000` shows "Couldn't reach the API. Check that the api container
   is running (`make prod-ps`)"* while the API is healthy — misleading, and the first thing
   a tired reader would type. It is now the heading of its own entry, address bar first.
10. *A wrong database password (6.1 re-run after the first start) leaves `make prod-up`
    reporting every container **Healthy**.* The api health endpoint says
    `{"status":"degraded","db":false}` and the sign-in page's *API health* box says
    *Database: down*; sign-in returns 500. The entry now leads with the box, not the log.
11. *`WEB_PORT` / `API_PORT` were not in `.env.prod.example`,* so "change these lines"
    changed nothing (reproduced: ports stayed 3000/8000). Added to the template; with them,
    the documented edit moved the app to 3001/8001 and the rebuilt web app reached the API
    on 8001 (the sign-in page's API health box read *ok*).
12. *`make prod-logs` ends with `make: *** … Error 130` on Ctrl+C,* and a slow network fills
    the build with `WARN Tarball download average speed …`. Both harmless, both now said.
13. *A sleep during an audit can record a false `unreachable`,* not only a failure — a
    homepage not loaded because the host's network was down is classified like a site that
    is down (read from the code, not reproduced: a `connect` error on the robots request is
    stored as `unreachable`, `audit_web/service.py`). The entry says to disregard such audits and when they are retried (6 h failed,
    1 day unreachable, on the next run of the search). Not fixed here (pipeline change,
    out of scope); worth a look in a later spec.
14. *The draft's claims were tightened where they outran the evidence:* the Places
    "without it" and PageSpeed "without it" behaviour (from the code), the section 8
    screens (from the app and its e2e test on demo data), and "Docker Desktop 4.27" (not
    verifiable here; replaced with the Compose ≥ 2.24 check the reader can run).
15. *Found, not in the Windows document, not fixed:* `NEW_PASSWORD='…' make
    reset-password`, documented in the main README, does not work — the Makefile's
    `docker compose run` does not forward `NEW_PASSWORD` into the container, so the CLI
    falls through to `getpass` and fails with `EOFError` without a TTY. A code change;
    out of scope for a documentation spec. The interactive form (the one the Windows
    guide uses) works.
16. *The development compose file publishes 3000, 8000, 5432 and 6379 on all interfaces*,
    not 127.0.0.1 as the spec's troubleshooting item assumes for both projects. It matters
    here only because a `make` without `PROD=1` starts dev PostgreSQL and Redis on the LAN
    address; the document's fix (`make down`) stops them.

**Measured on the walkthrough (slow connection):** first `make prod-up` 9 min 42 s; peak
memory of the whole Docker engine during the build ~2.2 GiB (sampled every 5 s); Docker
disk after the first build 4.6 GB (images 1.1 GB, build cache 1.5 GB; `docker builder
prune -f` freed 1.7 GB). These back the document's 16 GB / 8 GB-with-`.wslconfig`
guidance and the 30 GB free / 40 GB disk-limit figures, which leave room for the dev image
a `make` without `PROD=1` builds, backups and growth.
